Hosting sync on a Raspberry Pi 3B

Forge session · 2026-10-25 · poe-crafting-base-price-checker

The Pi runs pnpm sync and publishes the data to master on its own, so the PC can stay off. The plan is generic, tracked infra in ops/pi/, run by the developer agent over SSH. Nothing in packages/ changes.

Locked decisions

  • The Pi publishes itself. A systemd timer runs every 4 h, outside the sync chunk path.
  • One tick: stop the service → commit the sync-owned paths → pull --rebase → push → pnpm install --prod if the lockfile changed → start. It skips the commit when nothing changed, never force-pushes, and retries on the next tick. Code deploys ride the same tick.
  • Drift guard: the tick aborts if any path that isn't sync-owned is dirty, because nobody curates on the Pi.
  • ops/pi/ is git-tracked and generic: runbook, tick script, systemd units and set-poesessid.sh. It uses placeholders and contains no secrets. The Pi commits as your GitHub noreply address.
  • Runbook, not a bootstrap script. The agent executes it and stops at the human-only steps (Imager, secrets, deploy key). AGENTS.md points to it.
  • Provisioning: Pi OS Lite 64-bit with SSH key preset, Ethernet, Node 24 arm64, a repo-scoped deploy key.
  • Recovery after an outage: sync starts at boot, but only after the network and the clock are back (the Pi 3B has no clock battery). A tick missed during the outage runs right after boot, and the tick clears any stale git lock or half-done rebase.
  • Access: home network only, ssh <pi-host>.local. The agent has the same reach.
  • Cookie rotation: you run the script over ssh -t; it reads from stdin and writes .env with mode 600. The agent never sees the cookie.
  • Spine: amend AD-3 (publishing becomes an operator job outside the product). Deployment stays platform-agnostic: "Windows Task Scheduler or systemd".

Rejected, and why

  • The PC keeps publishing: the site would still depend on the PC being on.
  • data branch + Action merge: it solves blast radius, not merge conflicts. The Pi still has to pull master, and a GITHUB_TOKEN push doesn't trigger the deploy.
  • pnpm publish:data: mixes app logic with infra and still needs a timer.
  • A SYNC_HOST guard: discipline is enough, since you run sync by hand today.
  • An attention signal (report record or phone push): not worth building for a cookie that lasts about six months.
  • A bootstrap script: the agent follows the runbook.
  • Tailscale: deferred until you need access from outside the home.

Weak points that survived

  • A sync run on the PC shares the rate budget and can make the Pi's rebase conflict on dataset.json.
  • A dead cookie downgrades silently (AD-30). The six-month lifetime is unverified; the spine re-check is due 2026-11-02.
  • A power cut during a write can leave dataset.json empty or cut off, and the next tick commits it to master. The deploy check keeps it off the site. Fix it by hand on the Pi with git checkout -- data/. An atomic write and a validity guard were both rejected as too much.
  • SD wear: about 5–7 GB written a day, which is years on a decent card. The used card's unknown history and corruption on power loss matter more, so use a high-endurance card. Recovery loses at most one 4 h tick.
