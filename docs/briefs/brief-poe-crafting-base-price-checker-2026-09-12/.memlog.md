- (decision) Audience: primarily the user; published publicly but unadvertised, shared with friends. No growth/monetization goal.
- (decision) Horizon: 1+ year of active build and maintenance while user plays PoE2 -- NOT a weekend project. Sustainability of upkeep is a first-class requirement.
- (decision) Core job: replace the manual 'pick up base -> craft -> price check -> memorize' loop with an overview of which bases and which modifier combos are valuable (chase items).
- (decision) Data source: official PoE2 trade API (public, unauthenticated) for item catalog, modifier catalog, price search. Rate limits are a hard design constraint.
- (decision) Shape: two components -- a sync/aggregation component and a display component. Tech stack deliberately open at brief stage.
- (decision) Dev constraint: built entirely with AI agents. Must be fully testable/debuggable by an agent without a human in the loop, and support several agents working in parallel git worktrees.
- (decision) UI: appearance explicitly not a priority; adopt an existing framework/design system rather than custom design.
- (decision) Working mode: coaching path (section-by-section, adversarial). User chose over fast path.
- (event) Research: trade2 catalog endpoints (/data/items, /data/stats) are open, but the SEARCH endpoint is widely reported to require a POESESSID session cookie + descriptive User-Agent. POESESSID expires on logout / ~30d idle. Contradicts user's 'no auth required' assumption; needs a spike.
- (event) Prior art: poe2scout (open source, documented public API) already covers item base prices + price history; does not appear to cover per-base modifier-combo valuation. May reduce need to hit official trade API for base-level data.
- (assumption) OPEN CHALLENGE 1: trade listings are asking prices, not sale prices. Ranking bases on listings risks confidently recommending junk. Manual loop has a real-sale feedback correction the app would discard. No accepted answer yet.
- (assumption) OPEN CHALLENGE 2: search space (bases x ilvl brackets x mod combos) exceeds what rate limits allow syncing. The choice of WHAT to sync is the core product decision, currently unspecified.
- (decision) Scope narrowed: MAGIC bases only (max 1 prefix + 1 suffix). Endgame filter: ilvl >= ~78, mod tiers 1-2. Still a large combination space.
- (decision) Primary view: ranked list of bases by profitability, with hinted chase modifiers, expandable to full mod-combo list per base. Usage: before a session, or ad hoc during the day to read the economy. Output is a chase decision.
- (decision) Stretch vision: export a generated loot filter so the game highlights what to pick up, removing memorization.
- (assumption) OPEN CHALLENGE 3 (user-raised, unresolved): how to rank base X (one jackpot combo) vs base Y (many moderate combos). Profitability metric undefined -- this is the core product question.
- (event) Research: PoE2 item filters lack a working HasExplicitMod equivalent (absent/behaves differently vs PoE1). A generated filter can express base type + ilvl + rarity, but NOT mod combos -- so filter export can only automate half the memorization.
- (event) Research: RePoE fork publishes a PoE2 data export incl. mod spawn weights; pathofcrafting.net uses community-verified weights covering ~99% of craftable mods. Means P(mod combo) is computable -- true expected-value ranking is feasible, at the cost of a second data source that must track game patches.
- (override) User corrected me that RePoE/pathofcrafting are PoE1-only. Verified otherwise: repoe-fork.github.io/poe2/ publishes a PoE2 export (v4.5.5.2) incl. mods.json and mods_by_base.json. Spawn-weight population for PoE2 still UNVERIFIED. pathofcrafting struck -- attribution page 404s.
- (decision) Price estimator: cheapest ~10 live listings, instant-buyout-only, refreshed every few hours. Rationale: ascending sort makes stale overpriced listings irrelevant; instant-buyout removes snipeable underpricing. Confirmed PoE2 asynchronous trade (Merchant Tabs / NPC Ange) supports real instant buyout.
- (decision) RESOLVES CHALLENGE 3: rank by threshold-truncated expected value, not raw EV -- sum P(combo) x price(combo) over ONLY combos at/above the user's payout threshold, minus full craft cost paid on every attempt. Threshold is the dial that decides X vs Y and must be a UI control.
- (decision) Threshold values: ~0.25 divine in early endgame, >=1 divine once richer/stronger. MVP targets LATE endgame; user judges late-endgame value transfers down to early.
- (decision) Zero-listing combos: assume jackpot, surface for manual investigation, fix the app if the combo turns out to be impossible. Human-in-the-loop is acceptable for a personal tool.
- (decision) Ranking unit is (base x recipe), not base alone -- perfect vs greater transmute/augment change both tier distribution and cost, and currency prices move during a league.
- (decision) Late-endgame workflow: perfect transmute everything picked up, evaluate, then perfect augment only the promising ones. Early endgame triages before crafting. ~12 bases per map, ~5 min per map (~144 bases/hour) -- enough attempts that mean-based math is valid.
- (assumption) OPEN CHALLENGE 4: most specific T1/T2 combos will have zero listings, so 'assume jackpot' may flood the top of the ranking with unknowns. Needs a position on unknown-handling at scale.
- (decision) RESOLVES CHALLENGE 4 (segregate): track a curated list of mod permutations worth checking rather than enumerating the space. Known-junk combos are excluded so they never consume request budget. With ~500k players, anything worth tracking will have listings. The tracked list doubles as the sync budget and is refined over time.
- (decision) Data must be precomputed and available BEFORE a play session -- sync is scheduled/offline, never on-demand at decision time.
- (decision) v1 answers the PICKUP decision only. Assume transmute+augment are always applied; whether to actually augment a given item is the user's judgement (e.g. skip on inc stun threshold) and explicitly NOT a tool feature.
- (decision) White bases ARE in scope, but only at ilvl 82 -- the one case where selling the raw base may beat crafting on it. (Reverses earlier out-of-scope assumption.)
- (decision) Confirmed in scope as named risks/assumptions: league churn (3-4 resets/yr + patch drift) as a first-class problem; behavioural success criteria; stack open with AI-agent dev constraints as hard requirements. Out for v1: loot filter export, rare items, multi-user features.
- (decision) APPROACH SETTLED: market-scan as generator, user curation on top. One search per base (+~2 fetches) reading mods off expensive listings, instead of enumerating combos. ~750 req/refresh vs ~50k, i.e. ~1h vs ~70h. Daily or few-hourly refresh is comfortable.
- (decision) Drop the T1/T2 tier restriction in the scan: a price floor is a strictly better filter than tier, and catches off-tier mods that are valuable due to current build meta.
- (decision) Syncer must read GGG's X-Rate-Limit response headers and adapt, not hardcode a rate. Rate figures in the brief are estimates.
- (event) User confirmed trade2 search exposes rarity, ilvl, price-floor and instant-buyout filters together -- spike closed.
- (override) CORRECTION (user): POESESSID is NOT required. trade2 fetch works unauthenticated; auth only raises rate limits. VERIFIED by fetching the user's URL -- returned item JSON successfully with explicitMods + listing.price. Auth downgraded from risk to optimization.
- (override) CORRECTION (user): RePoE PoE2 export has all spawn weights set to 1 -- placeholders, not real data. Confirmed: modifier weights are NOT in the PoE2 game client. Community derives them (poe2db.tw, craftofexile.com/weightings?game=poe2) via recombinator experiments (Krakenbul / Prohibited Library) and trade-listing parsing + normalization.
- (override) CORRECTION (user, partial): I conflated discovery with pricing. PRICING a specific combination DOES require its own filtered search -- there is no way around it. Verified separately that DISCOVERY without mod filters does work: fetch returns explicitMods, so a base+rarity+ilvl+price-floor search reveals which combos sit on expensive listings. Settled as a two-channel design: cheap scan discovers candidates, per-combination searches price the curated survivors. Curated list size is therefore the request-budget knob -- user's original instinct was right.
- (decision) Terminology: prefer 'currency' and 'value'; avoid 'money'.
- (decision) poe2db's own caveat -- parse the LOWEST-value listings to limit bias toward desirable/high-tier mods -- independently validates the ascending-sort price estimator. The app's own scan output is the same raw material poe2db uses, so deriving in-house weights is a possible byproduct.
- (override) REVERSAL: market-scan discovery REJECTED (user, reaffirmed). Search returns individual listings, not distributions -- a 10-listing sample only surfaces the already-known common combo, while paging for real coverage costs ~4000 requests, the same order as pricing the whole tracked list. Either uninformative or not a discount. My earlier pushback withdrawn.
- (decision) Tracked list is seeded and maintained from the user's own knowledge. Cold start and meta blindness are UNSOLVED in v1 and recorded as risks, not mitigated. Mitigation in v1 is periodic deliberate review of the list.
- (decision) v2 candidate: re-seed the tracked list from community sources (spawn weights for rarity, build-popularity data for demand) rather than inferring from listings. Noted, not designed.
- (decision) Tier 1-2 restriction retained as a request-budget control; valuable off-tier combos are added by hand when the user notices them (no automated surfacing).
- (override) CORRECTION (user, verified): poe2scout does NOT overlap. It is live and PoE2, but covers currency exchange, uniques, price history and unique-BASE reference data (for chancing) -- nothing on magic base prices by mod combination. Prior-art risk removed from the brief.
- (override) CORRECTION (user): no clean public weights dataset exists. poe2db embeds weight JSON in page script elements (e.g. poe2db.tw/us/Bows), scrapeable only via HTML parsing; more data circulates on Discord. Building a weights dataset is explicitly out of scope for this project.
- (decision) Weights are a DECOUPLED INPUT. The app consumes a weights file with a defined schema and is indifferent to its producer (scraper / Discord dataset / in-house derivation). Scraper becomes a separate project. Justification is CADENCE -- prices are hourly, weights are patch-cadence -- not project tidiness.
- (decision) Sequencing: define the weights schema first, ship v1 against a uniform-prior file satisfying it, keep the scraper off the critical path. Do not split the repo until the schema stops moving. UI must visibly distinguish rankings backed by measured weights from those resting on the uniform placeholder.
