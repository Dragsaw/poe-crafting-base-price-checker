# PRD: PoE2 Crafting Base Price Checker

## 0. Document Purpose

This PRD is the requirements layer for a single-player tool. The tool answers one question — *is this base worth picking up?* This PRD is written for the agents that will build the tool, and for the workflows that will turn this PRD into epics and stories. This PRD is deliberately **downstream of a settled architecture**. `ARCHITECTURE-SPINE.md` is final at revision 8, and the spine's decisions AD-1 through AD-29 are **inherited, not re-decided**. **AD ids are stable across every revision.** Every `(AD-n)` citation below therefore still points at the decision that citation always pointed at. What moved is the content of the amended decisions, and no citation in this document went stale. Revision 5 added **AD-29** and raised the Weights File contract to **4.0.0**, a breaking change. AD-29 states that one game modifier may publish several Stat Lines under a single spawn weight, and that the draw is over modifiers. **Revision 6 added no decision and renumbered none — 29 remains the total.** Revision 6 amended **AD-18, AD-28 and AD-29** in place and reissued the contract at **4.1.0**, a **non-breaking minor**. A conforming `4.0.0` file is a conforming `4.1.0` file, and no producer work is invalidated (FR-27, §7.3). **Revision 7 is a single-item pass.** Revision 7 answers the one question that this document's revision 6 raised back (§10 OQ-17). Revision 7 amends **AD-12 and AD-18** in place, adds no decision, reissues no contract, and **changes nothing about what any check is** — only which component must run a check, and when. **Revision 8 is a single-item pass.** Revision 8 answers the one question that this document's own revision 7 raised back against the spine (§10 OQ-18). Revision 8 amends **AD-12, AD-17 and AD-18** in place, adds no decision, reissues no contract, and, exactly as revision 7 did, **changes nothing about what any check is** — only which shells are obliged to run AD-17's two cross-file checks, and when. **Sixteen** decisions have been amended in place across revisions 3 through 8. Revision 8 amends three decisions — AD-12, AD-17 and AD-18 — that earlier revisions had already amended, so the distinct total is unchanged. The earlier rounds' lists are at §10 OQ-15. AD-25 (the committed Trade Catalogue), AD-26 (Refresh Rotation), AD-27 (the pool-coverage gate), AD-28 (value-axis decomposition) and AD-29 all bear on the requirements below. A requirement here sometimes restates something the spine governs. Such a requirement does so because that thing is visible to the player, and therefore belongs in a requirements document. The citation `(AD-n)` points at the decision and at the decision's rationale, which this document does not re-argue.

This document is Glossary-anchored. §3 defines every domain noun, and §4's features and FRs use those terms verbatim. Inferences carry inline `[ASSUMPTION]` tags, and §11 indexes those inferences. `[NOTE FOR PM]` callouts flag items worth revisiting, and this document deliberately does not index those callouts — the callouts are prompts, not commitments.

> **The one live gate is data, not architecture.** The crafted branch of the ranking depends on the external Weights File, and there is no fallback. Until a conforming file exists, every crafted Base Type is Unrankable (§7.3, FR-30). Someone must measure the file's coverage before any view work, and **re-measure that coverage on every regeneration of the file**. The reason is that the result binds a layout decision, and the fraction moves across a game patch (FR-4, AD-27). One question on that dependency is **open by design** and is owned outside this repository: which single quantity the trade stat filter compares for a multi-`#` modifier (§10 OQ-12). That question is blocking for correctness, but not for building.

## 1. Vision

Farming crafting bases is among the most reliable ways to make currency in Path of Exile 2's endgame, and memory gates the method entirely. The method only pays once the player knows which Base Types to pick up and which modifier combinations sell. The player buys that knowledge with weeks of picking up everything, crafting on it, price-checking the result, and slowly committing the answers to memory. League resets destroy that learned knowledge three or four times a year, at exactly the moment the knowledge is worth the most.

This tool replaces the memorisation with a ranked list. A background sync prices a curated set of base-and-modifier combinations against the official trade API. A static web view ranks Base Types by **expected payout per craft**. The view counts only outcomes above a threshold that the player sets, and subtracts the cost of the craft, which the player pays on every attempt including the failures. The player reads the list before a play session, or whenever the economy is worth a look. The list is precomputed, so the list never blocks on a live API call.

The ranking is not "most expensive base," and everything else in the system exists to make that distinction hold. A Base Type with one jackpot combination and a Base Type with many moderate combinations swap places as the threshold moves. For that reason the threshold is a dial the player turns, rather than a constant that someone compiled in. The sync, the schemas and the view all exist to make that one number right, and to make that number honest about what it rests on.

## 2. Target User

### 2.1 Jobs To Be Done

- **Decide, at a glance, what to pick up this week.** Functional: convert a live market into a short ordered list of Base Types worth inventory space.
- **Stop paying the memorisation tax.** Emotional: the relief of not holding a top-five list in your head, and of not losing that list at every league start.
- **Know when the answer has gone stale.** The player must be able to tell a figure resting on real measured weights from a figure resting on a uniform placeholder, and a row priced an hour ago from a row priced yesterday. If the tool does not tell the player, the player will trust the placeholder six months later.
- **Spend time playing, not crafting.** Contextual: the binding constraint is the player's own time. Outcomes below the player's threshold are worth nothing to the player, because that much currency turns up simply from playing. Such outcomes must therefore contribute nothing to the ranking.
- **Keep a tool alive for a year without the tool becoming a second job.** The maintenance surface is a first-class concern: no credentials to rot, no server to patch, no account system.

### 2.2 Non-Users (v1)

- **Anyone who is not the author.** The author publishes the tool openly but does not advertise it. Friends with the link and passers-by are welcome and explicitly not courted — no growth goal, no monetisation, no advertising.
- **Players wanting advice on an item already in hand.** The augment decision is excluded by design (§6).
- **Rare-item crafters.** Magic bases only: at most one prefix and one suffix.
- **Anyone needing their own settings.** No account, no per-user persistence, no sharing (AD-15). The tool may assume one player's thresholds, one player's playstyle, and one player's judgment about when to trust the tool. That freedom is load-bearing.

### 2.3 Key User Journeys

There is a single operator, a single role, no authentication and no multi-device handoff. These journeys are therefore written in the template's lighter form.

- **UJ-1. The pre-session read.** The player is about to map for two hours. The player opens the view, glances at the top five Base Types under his current threshold, notes the two or three Chase Combinations on each Base Type, and closes the view. He picks up accordingly for the rest of the session.
- **UJ-2. The threshold turn.** The player is now richer than at league start. He drags the threshold from a quarter of a Divine to one Divine. The list reorders immediately — steady moderate Base Types fall away, jackpot Base Types rise — and he re-reads the new top five.
- **UJ-3. The drill-down.** The player is unsure why an unfamiliar Base Type ranks third. He expands that Base Type and reads the full tracked Combination list: which Combinations are priced, at what price, how old each price is, and which Combinations returned no listings.
- **UJ-4. The trust check.** The player notices a Base Type that ranks suspiciously high. He sees that the price of that Base Type was observed three days ago, and that the whole ranking is flagged as resting on the uniform prior. He discounts that Base Type rather than acting on it.
- **UJ-5. The curation pass.** The player reviews deliberately after a few weeks. He sees three Combinations that have returned no listings all league, and one Combination flagged unresolvable since the last patch. He opens `data/tracked.json`, tombstones the dead Combinations with a reason, pins one Combination he wants watched closely, and commits. The next sync run reflects the edit.
- **UJ-6. The league reset.** A new league starts. The player edits the active league in `data/config.json` and commits. The ranking goes honestly empty rather than quietly serving last league's numbers, and the ranking refills over the following day.

## 3. Glossary

Downstream readers and workflows use these terms exactly. A synonym introduced anywhere is a discipline violation.

- **Base Type** — a specific item base in PoE2. The trade API's own `baseTypeId` identifies a Base Type. This product never re-encodes `baseTypeId` into an internal id (AD-5). **The rule governs ids the trade API exposes.** The spine's conventions carry one explicit carve-out. **`sourceModifierId`** is producer-assigned. `sourceModifierId` names a thing the trade API has no concept of at all. `sourceModifierId` therefore re-encodes nothing, and the flat-ids rule does not forbid `sourceModifierId` (AD-29).
- **Modifier Reference** — the canonical identity of a **Stat Line**. A Modifier Reference is one of exactly two kinds. A `kind` field discriminates the two kinds (AD-5). **A Modifier Reference names a Stat Line, not a game modifier.** The thing the game actually draws is the **Source Modifier**. A Source Modifier lives on the Weights File and never on a Modifier Reference. A curator can filter only on what the trade API exposes, and the trade API exposes Stat Lines. For this reason `sourceModifierId` is never part of a Modifier Reference, a Tracked Entry, or a Tracked Entry's canonical key (AD-5, AD-29). A **`banded`** reference is a trade API `statId` paired with an inclusive, closed **value band** `(valueMin, valueMax)`. A **`valueless`** reference is a `statId` with **no edges at all**, for a modifier that rolls no number — *"Loads an additional bolt"*. A valueless reference is **not** a degenerate band. A sentinel pair such as `1/1` would pass every containment, straddle and edge-alignment check. That same sentinel pair would also make FR-21 emit a `min`/`max` filter for a stat that has no value. A valueless reference still carries `weight` and `itemLevelMin`, and a valueless reference still counts toward pool completeness. The trade API has no tier concept. "Tier 1" and "tier 2" exist in this product only as bands. On a **`banded`** reference **`valueMax` is required, always**. An omitted ceiling is a floor by another name, and a floor spans tiers. A floor that spans tiers is the defect §10 BQ-1 removed. A requirement that `valueMax` is *present* is not sufficient. A `banded` reference's edges must also **align to edges the Weights File actually declares**. Otherwise a sentinel ceiling reproduces the defect and still satisfies every schema (FR-29).
- **Tracked Entry** — one unit of the curated workload. A Tracked Entry holds a Base Type, an optional prefix Modifier Reference, an optional suffix Modifier Reference, a declared **Item Level Floor**, and a **Curation Status**. An entry with both affixes absent is a **Raw Base**.
- **Raw Base** — a Tracked Entry with no affixes. A Raw Base represents an uncrafted white base at item level 82. A Raw Base is the one case where the sale of the base may beat crafting on the base.
- **Combination** — the outcome a Tracked Entry describes: this Base Type carrying this prefix and this suffix. A Raw Base describes the degenerate Combination of no affixes. The Payout Threshold applies to the degenerate Combination exactly as to any other Combination (FR-3).
- **Chase Combination** — one of the Combinations on a Base Type that contributes most to the Base Type's EV. The collapsed ranked row shows the Chase Combination. The player then knows what to look for without an expansion of the row (FR-2).
- **Tracked List** — the complete curated set of Tracked Entries, held in `data/tracked.json`. The Tracked List is at the same time what the tool watches and the tool's entire request budget (FR-14).
- **Item Level Floor** — the minimum item level a Tracked Entry's search accepts. The curator declares the Item Level Floor per entry. The Item Level Floor comes from the item levels at which the entry's affixes' **Accepted Tiers** become available (FR-22). The Item Level Floor is also a valuation input, because the Item Level Floor scopes the Eligible Pool (FR-29). The crafted entries on one Base Type must share one Item Level Floor. A Raw Base at 82 is exempt (AD-17, FR-16).
- **Accepted Tier** — for a modifier, the highest tier worth chasing. The Accepted Tier is tier 1 normally. The Accepted Tier is tier 2 where tier 1 requires item level 81 or 82 and is therefore too rare to chase. The mechanical expression of the Accepted Tier depends on the modifier (AD-28, FR-22). For a modifier whose text carries **one** `#`, tier and band coincide, and the Accepted Tier is the Modifier Reference's **band** — both edges, not a floor. For a modifier carrying **more than one** `#`, the value axis does not partition the tier axis, and **no pair of value edges isolates a tier**. The reference's edges then align to **cell** edges the Weights File declares, and the curator tracks an **interior cell** rather than a tier.
- **Curation Status** — exactly one of `active`, `pinned` or `pruned` (AD-23, FR-17). A Chunk selects a `pinned` entry **first in every Chunk, and refreshes that entry every Chunk the Chunk can afford it**. A `pinned` entry never waits its turn in the `active` ordering. The tool caps `pinned` entries at load. The tool truncates `pinned` entries for a Chunk whose discovered allowance cannot also fund the rotation below the `pinned` entries. **FR-17's two-row owner table is the binding statement of both the cap and the truncation.** This entry and FR-15 are summaries of FR-17's table. A `pruned` entry is a tombstone that carries the entry's reason. The sync workload excludes a `pruned` entry, and the ranking excludes a `pruned` entry. Curation Status is independent of Price State. An entry is `active` *and* `priced`, or `active` *and* `unresolvable`.
- **Refresh Rotation** — the defined, deterministic order in which a Chunk selects entries to refresh. A full pass takes many Chunks. The order is currencies, then `pinned`, then `active` by oldest `lastAttemptedAt`, then bounded `unresolvable` retries, never `pruned` (AD-26, FR-17).
- **Workload** — the set of Tracked Entries and currencies a Chunk may spend requests on, held in two declared files. The Workload covers two of the four enumerated request sources. The other two sources are the per-run leagues check and the catalogue refresh. Those two sources are fixed overheads rather than workload (FR-14).
- **Price Observation** — an observed price for a Tracked Entry. A Price Observation is normalised to Divine. A Price Observation is stamped with the observation time, the league, and the exchange observation used (AD-16, AD-19, AD-20).
- **Price State** — exactly one of `priced`, `no-listings`, `not-yet-synced`, or `unresolvable`. Absence is never `0`, `null`, or a missing key (AD-9). `not-yet-synced` carries a **reason** that distinguishes the three causes of `not-yet-synced` — `never-synced`, `league-mismatch` and `no-exchange-rate`. The four states are AD-9's. **The reason enum is this PRD's own addition.** No architecture decision requires the reason enum. The reason enum exists because one state that covers three unrelated causes would defeat the point of a distinction between states at all (FR-9).
- **`lastAttemptedAt`** — when `sync` last **issued a request** for a Tracked Entry, whatever the outcome. **Offline work never stamps `lastAttemptedAt`** — FR-24's catalogue validation above all, which runs over every tracked id on every run and costs nothing. If any evaluation stamped `lastAttemptedAt`, every entry's timestamp would advance on every run. FR-17's oldest-first ordering would then flatten to a tie across the whole Tracked List, and the Refresh Rotation would silently degrade to canonical key order (AD-9, AD-26). `lastAttemptedAt` is reachable in **all four** Price States. `lastAttemptedAt` is distinct from a Price Observation's `observedAt`, which exists only where there is an observation. A `no-listings` row therefore has an age even though the row has no observation. `lastAttemptedAt` is **absent on an entry no request has ever been issued for** — the `never-synced` case. That entry is the one row with no age at all, and the absence is the reason FR-17 treats such an entry as infinitely old (AD-9, FR-12, FR-17).
- **Divine** — the single currency denomination that crosses every boundary. All prices, all Craft Costs and the Payout Threshold are denominated in Divine (AD-17 for the threshold and the ranking terms, AD-20 for the unit itself).
- **Payout Threshold** — the player-set gross price, in Divine, below which a Combination's outcome contributes nothing to a ranking.
- **Craft Recipe** — a named crafting currency composition (v1: one perfect transmute plus one perfect augment). The tool computes a Craft Recipe's **Craft Cost** from synced exchange rates.
- **Craft Cost** — the Divine cost of one Craft Recipe attempt. The player pays the Craft Cost on every attempt, including failures.
- **Expected Value (EV)** — the ranking figure: the threshold-truncated expected payout of a Base Type under a Craft Recipe, less Craft Cost (FR-1, AD-17).
- **Stat Line** — one trade-API-visible stat that a Source Modifier publishes. A `statId` identifies a Stat Line. A Source Modifier publishes **one or more** Stat Lines, each with its own value range. **All of a modifier's Stat Lines roll together as a unit**, because the game rolls the modifier as one draw. A Modifier Reference names a **Stat Line**, never a Source Modifier. A Stat Line is what the trade API exposes, and therefore a Stat Line is all a curator can filter on (AD-5, AD-29). The tool counts pool completeness in Stat Lines rather than in source rows (FR-28).
- **Value Cell** — one interval of a `(Base Type, slot, statId)` family's value axis. The producer cuts that axis at every tier endpoint **once across all tiers**, never per Cohort. That single cut is what makes the partition the same at every item level (AD-28, FR-29). **A cell's identity is its value edges, never a tier name.** After decomposition, **more than one tier may reach a cell**, and a cell may not correspond to a single tier at all. In that case the file carries one Modifier Weight per tier that reaches the cell, rather than one merged entry. **At most two** Cohorts may carry a cell. The tool counts the carrying Cohorts per `(Base Type, slot, statId)` across every Source Modifier that publishes that stat. A third Cohort is a hard file error (FR-27). An **interior cell** is a cell that a **single** tier carries. An interior cell's population is therefore homogeneous, and an interior cell's price is that tier's price. The cells at a tier's boundaries are shared with the neighbouring tier, and those boundary cells are neither homogeneous nor single-priced. FR-22's curation rule turns on that distinction.
- **Modifier Weight** — one file entry: the mass that **one tier of one modifier** contributes to **one Value Cell**, within a Base Type and affix slot. The entry sits in the item-level Cohort that the entry's tier belongs to. The entry's weight is `w(t) × P(value ∈ c | t)` for that tier alone — never a sum across the tiers a Cohort holds (§3 *Cohort*). Where two tiers reach one cell, the file carries **two entries**. The two entries are told apart by their `sourceModifierId`. There are two shapes, by kind: `(sourceModifierId, statId, kind, valueMin, valueMax, itemLevelMin, weight, provenance)` banded, and `(sourceModifierId, statId, kind, itemLevelMin, weight, provenance)` valueless. **`sourceModifierId` is required on every entry of both kinds**, not only on entries split from a multi-stat row. **FR-27 states that requirement and its two reasons normatively** (§3 *Source Modifier*, AD-29). `tierLabel`, where present, is **display-only**. `tierLabel` may legitimately name a mixture such as `"T7–T8"`, and `core` must never branch on `tierLabel`. A Modifier Weight is consumed from the **Weights File** and never produced by this app (AD-11, AD-28, AD-5).
- **Source Modifier** — one game modifier as the game actually rolls the modifier: a single source row that carries **one spawn weight**, and that may publish **several distinct trade stats at once**. Those stats always arrive together, because the game rolls the modifier as a unit. The producer splits such a row at the row's Stat Lines. The producer then emits **one Modifier Weight per Stat Line, each carrying the source row's full weight**. That is the only reading that gives each `statId` the correct marginal probability. Every entry names the row the entry came from in **`sourceModifierId`**. `sourceModifierId` is **required on every entry** rather than only on split entries, since a single-stat row is simply a group of one. The id names **one source row — one *tier* of one modifier, never a modifier family.** The contract fixes that granularity rather than leaving the granularity to the producer. Both readings would otherwise conform, and the two readings disagree about which items satisfy two Modifier References at once. The fixed granularity also puts a group in **exactly one Cohort**, which is what makes the denominator's per-group mass well-defined (FR-29). The tool now **checks that property rather than assuming it**: a group, **within one `(Base Type, slot)`**, that carries more than one distinct `itemLevelMin` is a hard file error. An unenforced rule left `mass(g)` with two conforming readings and therefore two different denominators (FR-27). A group may also **declare how many Stat Lines the group publishes**, in the optional `statLineCounts` list. The producer counts that number from the source row as scraped, rather than from the entries emitted (FR-27, FR-29). The id is **producer-assigned and opaque**. The id is stable within one `(Base Type, slot)`. The tool never validates the id against the Trade Catalogue, because the trade API has no concept of the thing the id names. The id is **never part of a Modifier Reference, a Tracked Entry, or a Tracked Entry's canonical key.** In **valuation**, `core` reads the id for exactly two purposes: **de-duplication of the pool denominator** (FR-29) and **detection of co-occurring Stat Lines** in FR-16's overlap check. `core` reads the id again at **load**, in the file validation FR-27 specifies. That load-time read is a different job from either valuation purpose, and that is the reason the "exactly two purposes" above is a statement about **valuation** rather than about the whole app. Why the field is required on **every** entry, rather than only where a row published more than one stat, is a separate question. **FR-27 states both of AD-29's reasons normatively** (AD-29, AD-18, AD-17).
- **Cohort** — the set of a modifier family's tiers that share one `itemLevelMin`. The producer partitions a `(Base Type, slot, statId)` family's value axis into cells once across all tiers. The producer groups tiers into Cohorts by `itemLevelMin`. The producer then emits one Modifier Weight per **`(tier, cell)`** that carries weight. **The emission is per tier, not per Cohort**, because a tier *is* a Source Modifier's source row, and an entry names exactly one source row. Where two tiers share a Cohort, a per-cohort entry would have to name two source rows, which is unrepresentable. The alternative is to discard one source row, which destroys a co-occurrence marker. An entry's weight is therefore `w(t) × P(value ∈ c | t)` for **the entry's own tier**, never a sum across the Cohort. Cohorts remain, and Cohorts remain `itemLevelMin`-**equality** groupings. Membership is never by `<=`, because `cohortTotals` is still declared per Cohort, and `cohortTotals` is the conservation yardstick that check rests on. Every tier belongs to **exactly one** Cohort (AD-28, AD-29, FR-27).
- **Weights File** — the schema-conformant file of Modifier Weights that `WEIGHTS-FILE-SCHEMA.md` defines, at contract version **4.1.0**. An **external project** produces the Weights File. The Weights File is a **v1 prerequisite**, not an enrichment: the Weights File is the only source of pool membership, cell edges and item-level availability, and the trade API exposes none of those three (AD-11, AD-25, FR-30). The Weights File declares a **`gamePatch`** — the GGG patch the file's weights describe. **The operator asserts `gamePatch` at runtime.** The tool never derives `gamePatch` and never defaults `gamePatch`. Neither the producer's sources nor the trade API states a patch version. A producer therefore refuses to run without a patch version, rather than emitting a default that would propagate silently past the one person who could have caught the default. `core` does not parse `gamePatch` and must not branch on `gamePatch`. A missing or empty `gamePatch` value is a hard file error (FR-27). `web` shows `gamePatch` beside `producer.id` and `producer.generatedAt`, so a file left behind by a patch is visible as such (AD-11, FR-10).
- **`cohortTotals`** — the **pre-split** sum of one Cohort's tier weights, declared per `(statId, itemLevelMin)`. The producer computes `cohortTotals` before the producer splits anything. `cohortTotals` is the only mechanical check on AD-28's mass-conservation invariant. `core` validates that a Cohort's emitted cells sum to `cohortTotals`, by a path independent of the cells themselves, and `core` refuses the file otherwise (FR-27).
- **Trade Catalogue** — the committed mirror of the trade API's own data endpoints (`data/catalogue/*.json`). An explicit command refreshes the Trade Catalogue at patch cadence. The Trade Catalogue is an **identity and validation authority only** — base types, stat ids and display text, currency ids and icons. The Trade Catalogue contributes nothing to the Eligible Pool (AD-25).
- **Eligible Pool** — the complete set of Modifier Weight entries that can roll in one `(Base Type, slot)` at **any** item level. Each entry carries the `itemLevelMin` of the Cohort whose mass the entry holds. **The same value interval may legitimately appear more than once, for two independent reasons.** The first reason is once per **Cohort** that reaches the interval. That is how a decomposed family expresses two Cohorts' mass in one interval, where scoping admits at most one of the two Cohorts (AD-28). The second reason is once per **Source Modifier** that publishes that stat over that range. Scoping does **not** collapse the second case, because two distinct game modifiers genuinely both roll there. `core` sums both Source Modifiers into a numerator, and counts each Source Modifier once in the denominator (AD-29, FR-27, FR-29). The tool **scopes** the pool to a Tracked Entry's Item Level Floor before the tool normalises anything. The scoped pool is the **domain the tool computes the denominator over**, not the denominator itself. The denominator is the sum of the **Source Modifier masses** within that domain, counting each modifier once. The denominator is never the sum of a modifier's cells (AD-18, AD-29, FR-29). A pool declared anything other than `complete` makes the pool's Base Type **Unrankable** (AD-18).
- **Provenance** — what a derived figure rests on. Provenance is a **four-value total order**, weakest first (AD-10):

  | Rank | Provenance | Means | Arises from |
  | --- | --- | --- | --- |
  | 0 | `absent` | not an estimate at all — an upper bound | a `partial` pool, and nowhere else (FR-28) |
  | 1 | `uniform-prior` | someone invented the weight | a bootstrap file, or a field filled by hand |
  | 2 | `modelled-split` | someone **measured** the weight, but a **model** distributed the weight across Value Cells | AD-28's decomposition, and nowhere else |
  | 3 | `measured` | someone measured the weight — never ground truth (R-3) | a producer's real spawn weights |

  The ranks are explicit, so that no reader infers "weakest" from an enum's declaration order. `WEIGHTS-FILE-SCHEMA.md` states the same order the same way round, deliberately, so that two builders cannot rank the values differently. `absent` is a `core`-side value that must never appear in a file. Every derived figure carries the *weakest* Provenance and the *oldest* timestamp of the figure's inputs, with one stated exception: **`modelled-split` propagates from the numerator only** (FR-10).
- **Unrankable** — a Base Type that the tool excludes from the ordering, because the Base Type's Eligible Pool is incomplete or absent. The tool returns an Unrankable Base Type in a separate group with the reason (AD-18).
- **Chunk** — one bounded, resumable unit of sync work. A Chunk ends at whichever of three limits runs out first: the remaining search allowance, the remaining fetch allowance, or the workload remainder (AD-7). A Chunk's size is **discovered at runtime** and never configured. `data/config.json`'s **`minChunkSearches`** is not a Chunk bound. `minChunkSearches` is a **declared yardstick** read at exactly one place — FR-17's load-time `pinned` cap (FR-19, FR-31, AD-26).
- **Dataset** — the published snapshot of the latest Price Observation per Tracked Entry (AD-14).
- **Sync Report** — the published structured record of a sync run. A Sync Report holds the requests consumed **per declared source** (FR-14), the unresolvable entries, the **entries not reached in this Chunk** — this PRD's own field, required by no architecture decision (FR-25) — the **pinned-starvation records**, the measured pool-coverage fraction (FR-4), and the date of the last tracked-list edit (AD-12, AD-23, AD-26, AD-27).

## 4. Features

### 4.1 The Ranked Base List

**Description.** The Ranked Base List is the first screen of the product. In most sessions the player reads nothing else. The Ranked Base List is one ordered list of Base Types, most profitable first. Each row carries the Base Type's EV, the Combinations worth chasing on that Base Type, and the Provenance that the EV rests on. The browser computes the ranking on every input change (AD-4). Nothing in the published Dataset carries a rank, a score or an ordering. A precomputed ranking would make the Payout Threshold reorder nothing until the next sync. The Payout Threshold is the product's central control, and a control that reorders nothing does not do what the product shows it to do. The Ranked Base List realises UJ-1, UJ-2, UJ-3.

**Functional Requirements:**

#### FR-1: Rank Base Types by threshold-truncated expected value

The player sees Base Types ordered by EV. The order is computed under the active Craft Recipe and the current Payout Threshold. Realises UJ-1.

**Consequences (testable):**
- For a crafted Base Type, `EV = ( Σ P(combo) × price(combo) over Combinations that are priced and whose price ≥ Payout Threshold ) − Craft Cost` (AD-17).
- The Payout Threshold compares against a Combination's **gross** price, never its price net of Craft Cost.
- `core` subtracts Craft Cost **once** from the summed expected payout, never per Combination.
- A Combination whose Price State is not `priced` contributes nothing — not zero, not a default (AD-9).
- A Combination with Curation Status `pruned` is not a summand. Pruning therefore changes the ranking, and pruning is not a no-op (AD-23).
- `core` computes every ranking term. The view computes none of the ranking terms (AD-4).
- `P(combo)` and `price(combo)` describe the **same population**, and the sum is only meaningful because both describe the same population. A Modifier Reference is a bounded band (AD-5), so the tier that is weighted is the tier that is priced. Both halves of the probability are scoped to the entry's Item Level Floor (AD-18, FR-29).
- **The partition this sum rests on breaks in two non-obvious ways, not one.** The familiar way is intersecting bands. The second way is **co-occurring Stat Lines**: two Modifier References on *different* `statId`s, with no bands intersecting at all, both satisfied by a single item because the two Modifier References name two Stat Lines of one Source Modifier (§3). FR-16 rejects both ways at load. FR-1 names the second way as well as FR-16 does, because **this** is the FR that asserts the `ΣP ≤ 1` premise that those rejections exist to protect (AD-17, AD-29).

#### FR-2: Show chase Combinations on each collapsed row

Each ranked row names the Combinations most worth chasing on that Base Type. The player does not expand the row to read them. Realises UJ-1.

**Consequences (testable):**
- Chase Combinations are ordered by contribution to EV — `P(combo) × price(combo)` — not by raw price. `[ASSUMPTION: the brief says "chase modifiers" without defining the ordering. An ordering by price alone would advertise a Combination that the player will essentially never roll.]`
- The collapsed row shows **at most three** Chase Combinations. `[ASSUMPTION: the brief says "the modifier combinations to look for", which is plural and unbounded. Three is the count that fits a scannable row, and three matches the "top five bases" reading pattern of UJ-1.]`
- Only Combinations at or above the Payout Threshold appear. The set therefore changes when the player changes the Payout Threshold.
- A Base Type whose priced Combinations are all below the Payout Threshold shows no Chase Combination. The EV of that Base Type is negative by its Craft Cost.

#### FR-3: Rank Raw Bases on a separate branch, visibly labelled

`core` ranks uncrafted item-level-82 white Base Types in the same list. `core` values these Base Types differently, and the view labels them as uncrafted.

**Consequences (testable):**
- A Raw Base's EV is its observed price with zero Craft Cost. A Raw Base is never a summand in any crafted Base Type's sum (AD-17).
- **The Payout Threshold applies to a Raw Base exactly as the Payout Threshold applies to a crafted Combination.** A Raw Base priced below the Payout Threshold is truncated out of the list, and is not ranked at its price. Without this rule, the Payout Threshold would silently govern only one of the two branches.
- The view renders a Raw Base distinguishably from a crafted Base Type. Colour alone does not carry that distinction (NFR-10).
- A Raw Base's search uses `normal` rarity (AD-16) and item level 82, which is the brief's white-base scope. `[ASSUMPTION: 82 is the effective item level cap for these bases, so a floor of 82 and "exactly 82" are the same filter. If bases above 82 exist, this needs a ceiling, not a floor.]`

#### FR-4: Surface Unrankable Base Types outside the ordering

Base Types that `core` cannot rank honestly appear in a separate group with the reason. `core` does not drop these Base Types silently, and `core` does not rank them anyway.

**Consequences (testable):**
- A Base Type whose Eligible Pool for either slot is not `complete` is Unrankable, and a Base Type absent from the Weights File entirely is Unrankable. `core` excludes an Unrankable Base Type from the ordering (AD-18).
- **This consequence governs the crafted branch only.** A Raw Base's EV is its observed price with no probability term at all (FR-3). A Raw Base therefore needs no Eligible Pool, and a Raw Base ranks on whatever the Weights File says. A Base Type carrying both a Raw Base and crafted entries can therefore have an Unrankable crafted branch while its raw branch ranks normally. The view shows each branch in its own place, labelled for what that branch is.
- The view shows the reason per Base Type ("pool partial", "base absent from weights file").
- `core` never substitutes an invented pool to make a Base Type rankable.
- The count of Unrankable Base Types is visible without expanding the group. A large count means that the ranked list covers a small fraction of what the player tracks (§10 BQ-3).
- Every probability derived from a `partial` pool carries Provenance `absent`. The view renders such a probability as an **unknown rather than a number**, because the probability is an upper bound and not an estimate. A `partial` pool is the only path by which `absent` arises (AD-18, FR-10, FR-28).
- **A measurement taken before any view work sets the group's prominence.** The measurement is a fraction over Base Types. **Both halves of the fraction are stated as predicates**, because two people who have never spoken must be able to reproduce a fraction that binds a layout decision (AD-27):

```
rankable(base) = base carries at least one tracked entry that is
                 crafted (at least one affix present)
                 and not pruned

covered(base)  = base is PRESENT in weights.json
               ∧ both slots declare poolCoverage "complete"
               ∧ neither slot's pool is empty

coverage = |{ baseTypeId ∈ tracked.json : rankable ∧ covered }|
           ──────────────────────────────────────────────────
           |{ baseTypeId ∈ tracked.json : rankable }|
```

- **The denominator counts only Base Types that need a pool.** A Base Type tracked solely as a Raw Base has no probability term at all and can never resolve to `complete`. Counting such a Base Type would depress a fraction that binds a layout decision. The Unrankable group would then gain prominence on the strength of bases that were never unrankable. `pruned`-only Base Types are excluded for the same reason (FR-15). A Base Type carrying **both** raw and crafted entries **does** count, because its crafted branch needs a pool like any other crafted branch.
- **Each of the numerator's three conditions is load-bearing, and a statement of only the second condition — `both slots declare poolCoverage "complete"` — makes the fraction ambiguous.** "Both slots are `complete`" is **vacuously true** of a Base Type absent from the Weights File entirely, because such a Base Type has no slots to fail. A Base Type that declares `complete` over an *empty* pool passes a naive reading, and FR-4's first consequence excludes that Base Type from the ordering anyway. Either gap lets the same Tracked List and the same file score 100% or 40%, across a gate whose consequences turn at 80% and 50%.
- **`rankable` is decidable from `data/tracked.json` alone**, and deliberately so. Affix presence and Curation Status are both fields of `data/tracked.json`, so the gate runs before any sync has ever happened. Price State is **not** a term of `rankable`. `core` excludes `unresolvable` from the ranking for much the same reason that `core` excludes `pruned`. Folding Price State into `rankable` would move the predicate's inputs into the Dataset and would destroy that property.
- The result binds the layout, in **disjoint** bands (AD-27, §10 BQ-3):

| Measured coverage | What this FR requires |
| --- | --- |
| **≥ 80%** | The Unrankable group is a footer to the ranked list, as specified above. |
| **≥ 50% and < 80%** | The group becomes a **first-class surface** alongside the ranking, and not a footer. At this coverage the group is a large share of what the player tracks, and hiding the group misrepresents the product. |
| **< 50%** | The ranking premise fails. Escalate rather than ship around the failure. Neither `core` nor the view resolves this case. |

- A commitment to a layout before that number exists is a commitment to an assumption about how much of the product there is. For that reason the measurement is sequenced ahead of the view rather than alongside the view.
- **What "first-class surface" looks like is a UX decision, not a requirements one.** This FR fixes *when* the decision turns and *that* the decision turns. This measurement binds the concrete treatment, and the UX pass settles it. The requirement a design must satisfy is that at 50–80% coverage a reader cannot come away with the impression that the ranked list is the whole product.
- **The measurement recurs. The measurement is not a gate that is spent.** `core` re-measures coverage **on every regeneration of the Weights File**. The bands above bind on every measurement, and not only on the first measurement. The fraction moves. A patch introduces modifiers that the producer's source publishes unnamed, the producer must drop those rows, and the affected pools correctly fall back to `partial` (FR-28). A product that measured 85% before launch can therefore sit at 60% the week after a patch, with nothing reporting the drop. Re-measuring is part of **accepting** a regenerated file (AD-27).
- **The figure is published, not merely computed.** `sync-report.json` carries the coverage it measured (FR-25), so a drop across a patch boundary is visible where the rest of the run's health already is. A layout decision made against a stale number is the failure that this measurement exists to prevent.
- The fraction is not meaningful on a very small Tracked List. Three of four Base Types complete is 75%, and 75% lands in the first-class-surface band on a sample of four. `[ASSUMPTION: no source names a minimum denominator. The bands are treated as advisory below ~20 rankable Base Types, and the measurement is reported with its denominator so that the reader can see when that applies.]`

#### FR-5: Bound the ranked list to a readable length

The list answers a question rather than presenting an inventory.

**Consequences (testable):**
- The ranked list shows the top **20** Base Types by default. The player reads the remainder behind an explicit expand. `[ASSUMPTION: no source names a count. 20 is roughly a screen, and 20 comfortably exceeds the "top five" that the player actually acts on.]`
- The bound is a display concern only. `core` ranks the full Tracked List and the view truncates, so the Payout Threshold still reorders across everything (AD-4).

**Feature-specific NFRs:**
- Ranking the full Tracked List completes in **under 100 ms** on a mid-range machine, and re-runs synchronously on a threshold change. If ranking cannot meet that time, the fix is to memoise the pure function. The fix is never to precompute in sync (AD-24).

### 4.2 The Payout Threshold Control

**Description.** The Payout Threshold sets what counts as a win. A change to the Payout Threshold reorders the ranked list. The Payout Threshold is approximately a quarter of a Divine in early endgame. The Payout Threshold is a Divine or more when the player is richer and stronger. The Payout Threshold also increases through a league. For these reasons, the Payout Threshold is a control and not a constant. An outcome below the Payout Threshold is worth nothing to the player, because the player collects that much currency simply by playing. Realises UJ-2.

**Functional Requirements:**

#### FR-6: Set the Payout Threshold and see the list reorder immediately

The player sets a Payout Threshold in Divine. The ranked list then reorders in front of the player. Realises UJ-2.

**Consequences (testable):**
- The Payout Threshold control uses Divine. Divine is also the unit of every price and every Craft Cost that the Payout Threshold filters (AD-17, AD-20).
- A change to the Payout Threshold re-runs the ranking synchronously against the artifacts that are already loaded. The change triggers no network request and no sync.
- A Base Type with one jackpot Combination and a Base Type with many moderate Combinations swap order when the Payout Threshold crosses the moderate prices. This is the correct behaviour and not a bug.

#### FR-7: Remember the threshold between visits

The Payout Threshold and the view preferences survive a page reload.

**Consequences (testable):**
- The tool persists these values only in the viewer's own browser storage. There is no backend, no account, and no authenticated request (AD-15).
- A first visit has no stored value. The Payout Threshold then starts at a documented default. `[ASSUMPTION: 0.25 Divine, the brief's early-endgame figure, as the least-surprising cold start.]`

### 4.3 Combination Detail and Segregated Unknowns

**Description.** The player expands a Base Type. The view then shows every Tracked Entry on that Base Type, priced and unpriced alike. The player can thus see what the ranking is built from. The player can equally see what the ranking deliberately excludes. A Combination with no listings is either a jackpot or junk. Listings cannot tell the two cases apart. Segregation of the unknowns keeps the unknowns out of the ranking, and does not pretend that the unknowns are worthless. Realises UJ-3, UJ-5.

**Functional Requirements:**

#### FR-8: Expand a Base Type to its full tracked Combination list

The player expands any ranked Base Type. The player then sees all Tracked Entries of that Base Type with their prices, their Price States and their ages. Realises UJ-3.

**Consequences (testable):**
- Every Tracked Entry for that Base Type appears, whether or not the Tracked Entry cleared the Payout Threshold. **`pruned` tombstones are included**, visually separated and showing their prune reason. The inclusion of the tombstones is what makes UJ-5's review possible without an open of the file.
- Each row shows its Combination, its Price State, its price in Divine where the entry is priced, the number of listings that the estimate rested on, and its age. The row labels the age as an observation age or as a last-attempted age per FR-12.
- The view visibly marks each entry below the Payout Threshold as an entry that does not contribute to the EV.

#### FR-9: Render the four Price States distinctly, with a reason on `not-yet-synced`

The four Price States are four different things on screen. The view never collapses one Price State into another Price State.

**Consequences (testable):**
- The view renders no Price State as `0`, as blank, or as "—" in a way that reads as worthless (AD-9).
- The view presents `no-listings` as an open question and not as an answer. The view must not imply that the Combination is junk.
- The view shows `unresolvable` entries and does not merely omit them. The existence of an `unresolvable` entry is the symptom of a game patch (AD-6).
- **`not-yet-synced` carries a reason** — `never-synced`, `league-mismatch` (FR-31) or `no-exchange-rate` (FR-23). The reason is necessary because one Price State that covers three unrelated causes would defeat the point of the distinction between Price States. The view displays the reason and does not merely store the reason.
- The view does not carry the distinction between Price States by colour alone (NFR-10).

### 4.4 Provenance and Freshness Surfacing

**Description.** Every price in the system is an asking price. The system never observes a sale. A probability rests on whatever the Weights File's producer could actually source, and that coverage is expected to be uneven, band by band. A view that renders a placeholder identically to a well-founded figure keeps the trust of the player months later, because nothing on screen reveals the difference. That failure is the reason this feature exists. Realises UJ-4.

**Functional Requirements:**

#### FR-10: Propagate and display the weakest Provenance behind every figure

Every displayed derived figure states what that figure rests on. Realises UJ-4.

**Consequences (testable):**
- `core` propagates the **weakest** Provenance and the **oldest** timestamp of every input into each derived figure (AD-10).
- **Three distinguishable render treatments, not two**, and colour alone carries none of the three (NFR-10):

| Provenance | Rendered as |
| --- | --- |
| `measured` | the plain figure |
| `modelled-split` | visibly distinct from **both** other treatments — a measured weight that a model distributed |
| `uniform-prior` / `absent` | visibly degraded. `absent` is an unknown and not a number (FR-4) |

- A collapse of `modelled-split` into the placeholder treatment would **understate a measured weight**. A collapse of `modelled-split` into `measured` would overstate an invented distribution. This distinction is why AD-10 created a fourth value and did not fold the case into `uniform-prior`.
- **`modelled-split` propagates from the numerator only** — from a Modifier Reference's containment set, never from the denominator. AD-28 conserves mass exactly. A scoped pool's total is therefore identical whether or not a family inside that pool was decomposed, because the denominator rests on the same measured weights in both cases. A weakest-Provenance rule across the whole pool would stamp `modelled-split` on nearly every weapon Base Type, since 53 of 63 item classes carry a decomposed family somewhere. A label that universal distinguishes nothing. **Every other Provenance still propagates from every input.** A `partial` pool weakens the denominator in fact and not merely in label, and `absent` still rides over everything (AD-10).
- The view shows the Weights File's declared producer, `generatedAt` and **`gamePatch`** (§3) beside any figure they influenced. A file left behind by a patch is therefore visible as such.
- The exchange observation that normalises a price participates in Provenance exactly like any other input (AD-20).

#### FR-11: State the uniform-prior caveat globally when the per-row badge discriminates nothing

A Provenance badge that is identical on every row conveys no information. The view must not pretend otherwise.

**Consequences (testable):**
- The view **reads the condition from the data and does not assume it of v1**. The Weights File carries `provenance` per cell (`WEIGHTS-FILE-SCHEMA.md`, propagated per AD-10). What v1 ships is therefore whatever the scraper produces, and a probability's Provenance may legitimately be `measured` **or `modelled-split`** (FR-30).
- The banner condition is that **no probability in the loaded set carries `measured` or `modelled-split`** — that is, every probability is `uniform-prior` or `absent`. The view then shows a **persistent, dismissible-per-session banner**. The banner states that the entire ranking rests on a uniform prior, and that relative ordering between Base Types is not evidence-backed.
- **A `modelled-split` figure does not trigger the banner.** A `modelled-split` figure is a *measured* weight that a model distributed. A `modelled-split` figure is therefore not a placeholder, and it is also not a figure to render as plainly as `measured`. That is exactly why FR-10 gives `modelled-split` its own treatment. The likeliest first real file is a decomposed scrape that carries `modelled-split` across most weapon classes and `measured` elsewhere. A builder could read this requirement's condition as binary and then implement FR-10's badge from the same mental model. That builder would move whole weapon classes into the degraded rendering.
- The banner **disappears on its own** once any `measured` or `modelled-split` figure is present. The banner is a function of the data, and not a build-time constant that someone must remember to remove.
- The per-row badge is required regardless (FR-10). The badge is the discriminating signal the moment partial measured weights arrive, which is the likeliest shape of the first real file, because coverage is expected to be uneven.
- Where the badge cannot yet discriminate, **freshness** is the genuinely discriminating per-row signal (FR-12). The view gives freshness the visual weight that Provenance has not earned.

#### FR-12: Show per-row freshness, and say which clock it is reading

Each row carries its own age. The age of an unpriced row is as meaningful as the age of a priced row.

**Consequences (testable):**
- A single dataset-level timestamp is insufficient and must not be the only freshness signal, because Chunked syncing guarantees that rows refresh at different times (AD-7, AD-10).
- Every row carries an age **wherever an age exists**. The view takes the age from the row's `observedAt` where there is an observation, and from the row's `lastAttemptedAt` otherwise (AD-9).
- **A never-synced row is the one case with no age at all.** The view renders a never-synced row as *never attempted*, and not as an age or as a blank. The row's `lastAttemptedAt` is genuinely absent, because only an issued request stamps that field (§3) and no request has been issued. There is therefore nothing to show and nothing to back-fill. This is the `not-yet-synced` reason `never-synced` (FR-9). It is also the same fact that FR-17 uses when FR-17 treats such an entry as **infinitely old** for ordering. An implementation could write a placeholder timestamp to satisfy a non-null field. That implementation would lie on screen and would also give the rotation a key that sorts wrongly.
- **The view labels which of the two ages it shows.** The two ages mean different things — *this price is three days old* versus *nothing has been found here for three days*. A `no-listings` row that the tool retried hourly all week is a different fact from a `no-listings` row that the tool last looked for in the previous league. A collapse of the two ages into one unlabelled "3d" would make the second row indistinguishable from the first row.
- A partially refreshed Dataset publishes and renders normally. Per-row freshness is what makes that honest (AD-14).

#### FR-13: Present estimates as asking prices, never as realised value

The view's language never implies that a player achieved a price.

**Consequences (testable):**
- The view labels prices as current asking prices from live instant-buyout listings (AD-23).
- No copy describes an estimate as "sells for", as "worth", or with any phrasing that implies an observed sale.
- This rule is the *only* mitigation in the system for Risk R-1 (§9). The player's manual loop had a real-sale correction, and the tool discards that correction. A copywriting rule does not replace the correction.

### 4.5 The Curated Tracked List

**Description.** The Tracked List is two things at the same time. The Tracked List is what the tool watches. The Tracked List is also the tool's entire request budget. Every Tracked Entry costs a search on every refresh. Therefore curation discipline is a permanent operating requirement, not a one-time tuning exercise. The Tracked List is a hand-owned, committed file. The browser never writes to the Tracked List (AD-15, AD-21). The system cannot discover a Combination that nobody tells the system to watch. v1 records that limitation and does not solve it. The Tracked List realises UJ-5.

**Functional Requirements:**

#### FR-14: Bound every request to one of four declared sources

Exactly four sources generate a trade API request. No other source generates a trade API request.

**Consequences (testable):**

| Source | Cadence | Cost |
| --- | --- | --- |
| `data/tracked.json` — the Combinations to price | every Chunk | one search + one fetch per entry |
| `data/currencies.json` — the currencies to price for Divine normalisation (FR-23) | every Chunk, **first** (FR-17) | small, fixed |
| League validation against the live leagues endpoint (FR-32) | once per run | one request |
| Catalogue refresh (FR-24) | explicit human-invoked command, patch cadence, **never on the Chunk path** | four requests |

- The first two sources are the recurring **workload**. Both are schema-pinned committed files. Nothing writes either file at runtime (AD-12, AD-21). The last two sources are fixed overheads.
- The tool acquires exchange rates as part of the **workload**. Exchange-rate acquisition is not an exception to the **workload**. `data/currencies.json` is one of the two workload files (AD-12, AD-20).
- The Sync Report records the requests consumed **per source** against the live bucket. Therefore a reader can attribute budget drift to a cause (FR-25, AD-12).
- **Three run-start gates stand in front of those four sources, and two of the three gates cost no request.** Before the first priced entry spends a search, `sync` does three things. `sync` validates every tracked id against the Trade Catalogue (FR-24). `sync` runs `core`'s cross-file validation of `data/tracked.json` against the Weights File — five checks together: edge alignment, the straddle rule and the empty containment set (FR-29), alongside the overlap predicate's `coOccur` branch and cross-file kind agreement (FR-16). `sync` validates the configured league (FR-32). **Only the league check appears in the table above, because only the league check consumes a request.** The other two gates exist to stop the run from spending budget on a configuration that `core` cannot rank. The three checks are gates, not a fifth source.
- **The three gates have different consequences, and the difference is deliberate.** An uncatalogued id is a **per-entry** condition. `sync` marks that entry `unresolvable` and continues the run on the other entries (FR-24). A league mismatch (FR-32) or a cross-file validation failure (FR-16, FR-29) invalidates the **run's premise**. Therefore the run stops, and does not price the remaining entries around the failure. A builder who treats all three gates alike makes one of two errors. The builder stops a whole refresh because of one patched-out id, or the builder spends a full budget on a list that `core` will refuse to rank (AD-12, AD-17, AD-18).
- **A fifth source is an architecture amendment, not an implementation detail.** `minChunkSearches` (FR-17, FR-19, FR-31) is **not** a fifth source. `minChunkSearches` is a validation yardstick that generates no request. `minChunkSearches` does not change this four-source enumeration. `minChunkSearches` does not change the ~1,500-search ceiling below.
- **The ceiling is denominated in searches, not in entries.** A full refresh must stay within **~1,500 searches**, against a measured ceiling of ~2,400 searches a day. The remaining headroom covers retries, the currency set, the catalogue refresh, the per-run leagues check and a second recipe. One Tracked Entry always costs one search. What changes under AD-5's bands is *how many entries a curator needs*. To isolate a jackpot tier, the curator tracks two entries where one entry stood before, and that second band spends from the same ceiling. For a modifier that rolls more than one number, the curator splits at **cell** edges rather than at tier edges (FR-22, AD-28). Because that partition is finer, the isolation a curator wants may cost more entries than the tier count suggests (AD-12).
- **`pinned` entries also spend from that headroom, and they spend differently from every other entry here.** A `pinned` entry costs a search in *every* Chunk, not once per refresh. Therefore a `pinned` entry's daily cost scales with **invocation cadence**, not with the size of the Tracked List. A pinned set at FR-17's cap can consume a large share of the measured ~2,400 searches a day on its own. That cost is the real reason the cap exists. That cost is also why `pinned` is a scarce designation rather than a convenience (AD-12, AD-26).

#### FR-15: Honour Curation Status as schema-level behaviour

`active`, `pinned` and `pruned` are schema members with defined effects, not conventions.

**Consequences (testable):**
- `sync` selects `pinned` entries **first in every Chunk**. A `pinned` entry never waits its turn in the `active` oldest-first ordering. `sync` refreshes every `pinned` entry in every Chunk that can afford the pinned set. A Chunk whose discovered allowance cannot also fund at least one `active` entry truncates the pinned set instead of freezing the rotation, and `sync` records the truncation in the Sync Report. **FR-17 states the cap and the truncation normatively, in both of their owners. This consequence is a summary and defers to FR-17** (FR-17, AD-23, AD-26).
- `pruned` entries are excluded from the sync workload **and** from the ranking sum. A `pruned` entry's last-good price never contributes to the ranking sum (AD-23, AD-17).
- A `pruned` entry carries its reason. Therefore a curator does not add the same Combination again and learn the same lesson again each league. The view shows that reason (FR-8).

#### FR-16: Reject an overlapping Tracked List at load

Tracked Entries for one Base Type must describe mutually exclusive outcomes, because the sum of FR-1 is over a partition rather than a list.

**Consequences (testable):**
- A **predicate defines overlap, not an enumeration**. An enumerated list of shapes has now missed a case twice (AD-17):

```
overlap(a, b)  ⇔  slotOverlap(a.prefix, b.prefix) ∧ slotOverlap(a.suffix, b.suffix)

slotOverlap(x, y) =  true              if x is absent or y is absent
                     true              if x.statId != y.statId ∧ coOccur(x, y)
                     false             if x.statId != y.statId
                     true              if both are valueless
                     bands intersect   otherwise
```

- **Branch order is load-bearing.** The co-occurrence case sits **above** the inequality case. The co-occurrence case must catch exactly a pair of references on *different* `statId`s.
- An absent affix means *any roll in that slot*. For that reason the condition is a conjunction over both slots. The **both-valueless** branch is the one branch that a bands-intersect reading does not give a builder. Two valueless references have no bands to intersect. A builder without the both-valueless branch concludes that two identical valueless entries on one Base Type do **not** overlap. That builder then accepts a Tracked List that double-counts on the same partition that FR-16 protects.
- **`coOccur` stops the tool from counting one game modifier as two outcomes.** A Source Modifier may publish several Stat Lines that always roll together (§3). A single item satisfies **both** of two references that name two of those Stat Lines. Therefore `x.statId != y.statId` is not on its own evidence of disjointness. `coOccur(x, y)` holds when some `sourceModifierId` in the scoped Eligible Pool emits an entry contained by `x` **and** an entry contained by `y`, in the same item-level Cohort. That `sourceModifierId` names one modifier that can satisfy both references at once (AD-17, AD-29).
- **`coOccur`'s Cohort clause restates a property and does not add a condition.** A Source Modifier is one tier, and therefore sits in exactly one Cohort (§3). That same fact lets FR-29 drop `L` from `mass(g)`. A builder who implements the Cohort clause as a cohort-equality test writes a comparison that is always true. The Cohort clause is stated because the clause says *why* the check is well-defined. The clause is not stated because there is a cross-cohort case to exclude.
- **`coOccur`'s scope `L` is the Base Type's own crafted Item Level Floor.** `L` is the same value that scopes every probability on that Base Type. FR-16 and FR-22 give a Base Type exactly one `L` (FR-29, AD-18).
- **The overlap check is a cross-file check, owned by `core`.** The overlap check stands on the same ground as FR-29's straddle and edge-alignment rules. Co-occurrence is a fact of `data/weights.json`, and the references are in `data/tracked.json`. Therefore the check belongs to the component that holds both sides. `core` reports the check against the Tracked Entry, not against either file. **`web` runs the check at load, and `sync` runs the same check as a run-start gate**, before any priced entry consumes budget, with a failure aborting the run — identical to FR-29's three cross-file checks, and for the identical reason: an ungated `sync` run would spend a full refresh's budget on a Tracked List that a `coOccur` failure makes `web` refuse to load in its entirety, which is a worse waste than the per-entry failures those three checks catch (AD-17, AD-18).
- **Where the pool cannot answer, `coOccur` is `false`, and the Tracked List still loads.** There are exactly two such cases. The first case is a Base Type **absent** from the Weights File. The second case is a Base Type whose pool is **`partial`**. The safe behaviour is **not** to refuse the Tracked List. FR-28 and FR-4 have already made such a Base Type Unrankable. Therefore the tool never sums the partition that `coOccur` protects for that Base Type, and a missed double-count cannot reorder anything. **A uniform-prior file is not one of these two cases.** Contract 4.1.0 requires `sourceModifierId` on every entry, whatever the file's Provenance. Therefore a bootstrap file that declares `complete` answers `coOccur` exactly like any other file, and its Base Types rank normally (FR-30). A refusal instead would stop the **whole site** over a Base Type that was never going to rank. FR-16 states this rule explicitly for a reason. Without the explicit rule, one builder short-circuits and renders the view while another builder rejects `data/tracked.json` site-wide, and **both readings satisfy the predicate as written** (AD-17, AD-18).
- **One kind pairing is unreachable rather than handled.** A `statId` either rolls a value or does not roll a value. Therefore one `banded` reference and one `valueless` reference can never share a `statId`. `contracts` rejects that pairing within `data/tracked.json` at load, and does not let `core` pick a reading. The pairing is visible inside one file, so a per-file schema can see the pairing. Kind *agreement between files* is a different question — a `valueless` tracked reference against `banded` Weights File cells for the same `statId`. That question is a cross-file question, and `core` owns it. **`web` runs it at load, and `sync` runs it as a run-start gate**, gated identically to `coOccur` above and to FR-29's three checks, with a failure aborting the run (FR-29).
- Four consequences follow. Successive enumerations missed the last two consequences:
  - **A curator may track adjacent disjoint tiers of one `statId` in one slot.** That is the point of AD-5's bands. Bands that *intersect* still overlap, and `core` still rejects them.
  - A **partial-affix entry subsumes a fuller entry**. An absent slot covers every roll in that slot.
  - **A prefix-only entry and a suffix-only entry on one Base Type overlap each other.** Neither entry subsumes the other entry, and no two bands intersect. But an item that carries both named modifiers satisfies both entries, and the sum counts that item twice.
  - **Two entries in *one* slot that name two Stat Lines of one Source Modifier overlap each other.** The `statId`s differ, so no bands intersect, and the slot-conjunction reading above does not apply. But the two Stat Lines always roll together, so a single item satisfies both entries. This is the same failure as the case above, reached from the other direction. In the case above, one item satisfies two entries across two slots. Here, one item satisfies two entries across two Stat Lines of one modifier. The `coOccur` branch catches this failure.
- **Separately, the crafted entries on one Base Type must share an Item Level Floor** (AD-17, FR-22). Entries at floors 75 and 82 are nested, not disjoint. The 75 search also matches every item that the 82 search returns. The rule has a second, independent reason. EV is an expectation over *one* crafting act on *one* item population. Entries at different floors describe crafts on bases of different item levels, and `core` normalises their `P` terms against pools of different scopes (FR-29). A sum over those entries is not an expectation over anything.
- **A Raw Base is exempt from that floor rule.** A Raw Base is never a summand (FR-3). Therefore a Raw Base's floor cannot break a partition that the Raw Base does not enter. That exemption lets a white base at item level 82 exist together with crafted entries on the same Base Type at a lower floor (AD-17).
- The tool rejects overlap at load and names the offending entries. The tool never reconciles overlap at ranking time.
- Double-counting increases that Base Type's `ΣP × price` by the measure of the overlap. Double-counting does damage even where `ΣP` does not exceed 1. A modest overlap on a high-priced Combination is enough to move a Base Type several places.

#### FR-17: Refresh the Tracked List in a defined, deterministic rotation

The player asks *how often does a row get re-priced?* about every figure on screen. Therefore the rotation is a requirement, not an implementation choice. A Chunk selects entries in exactly this order. A Chunk stops when the Chunk reaches any Chunk bound (AD-26, FR-19).

**Consequences (testable):**

| Order | Selected | Why it sits here |
| --- | --- | --- |
| 0 | **Currency rates**, always, before any priced entry in the same Chunk | FR-23 requires the currency rates. A rotation that omits them produces a Chunk of `not-yet-synced` entries by construction |
| 1 | Every **`pinned`** entry, every Chunk — subject only to the cap below — **by oldest `lastAttemptedAt` first** | this is what `pinned` means (FR-15). FR-17 names the ordering key because under the cap a Chunk normally reaches every `pinned` entry, so the order looks immaterial. The key becomes load-bearing exactly when a Chunk cannot reach every `pinned` entry. The key makes the pinned tail rotate instead of starving behind a fixed key order |
| 2 | **`active`** entries whose Price State is not `unresolvable`, by **oldest `lastAttemptedAt` first** | the ordering is self-levelling. A full pass completes with no separate scheduler |
| 3 | Entries whose Price State **is** `unresolvable`, on a bounded retry — at most one attempt per entry per 24h | a patched-out modifier does not disappear from the rotation, and does not monopolise the rotation |
| 4 | **Never `pruned`** | excluded from the workload entirely (FR-15) |

- **What the `unresolvable` retry bound gives the player.** The bound is *not* budget protection. Detection is offline and costs no request. `sync` checks every tracked id against the committed Trade Catalogue on every run, whatever this rotation does (FR-24). Therefore the bound paces no re-validation and suppresses no reporting. Two definitions make row 3 coherent. Without those two definitions the rule is not decidable:
  - **Only an attempt that issues a request stamps `lastAttemptedAt`** (§3). The offline catalogue check costs no request and never stamps `lastAttemptedAt`. Otherwise every run would stamp every entry. Row 2's oldest-first ordering would then flatten to a single timestamp across the whole Tracked List, and the rotation would lose its ordering key completely. That failure is far larger than the failure row 3 addresses.
  - **An id that resolves again stops being `unresolvable` at that moment.** That entry rejoins row 2 as an ordinary `active` entry, at its true position. That entry does not wait for a retry slot.
- Row 3 therefore covers a narrow residue: **an entry whose id does resolve, but whose pricing attempt continues to fail.** The 24h bound paces *that* retry. The 24h bound guarantees that row 3 terminates, and stops row 3 from selecting a permanently failing entry in every Chunk (AD-26).
- The rotation orders on **`lastAttemptedAt`, not on observation time**. That key keeps a permanently `no-listings` entry in the rotation, and does not let that entry monopolise the rotation. A `no-listings` entry never acquires an observation time, so an observation-ordered rotation would select that entry again forever (AD-9, AD-26).
- **The rotation treats an entry that carries no `lastAttemptedAt` at all as infinitely old.** Therefore a Chunk selects a newly added entry before any refresh. The ordering key is the **absent timestamp**, never the `not-yet-synced` Price State. FR-12 and AD-9 have separated the two. FR-23 writes `not-yet-synced` with reason `no-exchange-rate` for an entry that `sync` *did* attempt and that carries a perfectly fresh `lastAttemptedAt`. To sort that entry as infinitely old would select that entry again in **every** Chunk, and would let that entry monopolise the rotation permanently. That outcome is the same starvation that row 2's ordering exists to prevent, reached through the Price State instead of through the observation time (AD-9, AD-26).
- **Rows 1–4 are a precedence order over two different fields.** Rows 1, 2 and 4 select on Curation Status. Row 3 selects on Price State, and an entry can carry `active` *and* `unresolvable` at once. The rotation selects such an entry at row 3 only. The removal of that entry from row 2 is what makes row 3's bound mean anything. Otherwise the oldest-first ordering would select that entry again in every Chunk anyway.
- **The `pinned` set is capped at both ends, because neither end is sufficient alone.** The binding requirement is that **a Chunk must be able to refresh every `pinned` entry and still make progress on the `active` rotation below it**. An oversized pinned set consumes every Chunk, and starves both its own tail and the rotation. A load-time cap alone cannot be sound. `sync` discovers a Chunk's real allowance at runtime from live headers (FR-19, FR-20), and no declared number governs that allowance. A runtime check alone would let a curator author a list that can never work.

| Where | Owner | Rule |
| --- | --- | --- |
| **Load time**, a `data/tracked.json` validation error | **`sync` only** | `count(pinned) + currencyStepSearches ≤ 0.5 × config.minChunkSearches`. At least half of a minimum Chunk stays available for the `active` rotation. The currency step is a summand, because FR-23 spends the currency step at row 0 of the same Chunk. `currencyStepSearches` is **what that step actually costs in searches**, not the row count of `data/currencies.json`, because one bulk exchange query may price many currencies in one request. `sync` reports the figure it used (FR-25), so the two figures cannot drift. |
| **Runtime**, every Chunk | **`sync`**, surfaced by `web` | If the discovered allowance cannot cover the pinned set **plus at least one `active` entry**, `sync` **truncates the pinned set for that Chunk**. `sync` takes entries in row 1's oldest-`lastAttemptedAt` order, and reserves at least one search for the `active` rotation. `sync` then completes the Chunk normally, and records a **pinned-starvation** record in the Sync Report (FR-25). A truncation is **not an error, and does not change the exit code**. |

- **`minChunkSearches` is a declaration about the player's own invocation cadence, not a constant read from a bucket.** A wrong `minChunkSearches` value is how an oversized pinned set passes validation. In steady state the binding bucket is the long bucket. `600:21600` is **100 searches/hour sustained**. `30:300` is a burst allowance, and a Chunk receives the full burst allowance only at an invocation interval of about 18 minutes or longer. A syncer invoked every 5 minutes gets roughly **8** searches per Chunk once the 6-hour bucket saturates, **not 30**. The player declares the smallest allowance a Chunk will actually receive **at the cadence he schedules**, bounded above by `sustainedRate × interval`. If the player takes `minChunkSearches` from the burst figure at a short cadence, validation certifies a pinned set that starves every Chunk forever. That outcome is the precise failure this cap exists to prevent, and the failure re-enters through the yardstick (AD-26, AD-19, FR-19).
- The runtime half also **audits that declaration**. `sync` records the allowance it actually observed. Therefore a `minChunkSearches` set too high appears as a starvation record within one run. Nobody has to infer the wrong value months later from a refresh that never completes. A declared number that nobody checks would be worse than no cap at all, because that number would carry the authority of a value that passed validation.
- **Neither half alone would do.** Without the runtime half, this requirement says what to *record* rather than what to *do*, and two builders write opposite selection rules. One builder spends the whole allowance on `pinned` and freezes the `active` rotation permanently. The other builder truncates the pinned set. Without the load-time half, a curator can author a Tracked List that no Chunk can ever satisfy. The runtime half also makes the failure **visible**. Without the named shortfall, an oversized pinned set looks exactly like a slow refresh (AD-26).
- **The load-time check belongs to `sync` alone, and `web` is explicitly not obliged to run the load-time check.** `web` also validates `data/tracked.json` on load (FR-33, NFR-8), so an unowned rule would read as a shared rule. But `web` **cannot** evaluate the load-time check. `data/currencies.json` is not among the eight artifacts `web` fetches (FR-33), and the currency step's search cost is a sync-side fact. A `web` that refused to render over a cap it cannot compute would stop the whole product for a curation error that only ever affects a sync run (FR-33, AD-26).
- The rotation breaks ties on the canonical entry key. Therefore a run is reproducible, and a resumed run is explainable (AD-26 — the spine's Consistency Conventions fix the key's encoding).
- The order is a **pure function** of the Tracked List, the Dataset and a clock value the caller passes in. `core` computes the order. Therefore the order is testable with literal inputs, and the order is identical in a dry run and in a real run (AD-1, AD-26).
- **A resumed Chunk computes the order again, and does not replay a frozen plan.** Progress records which entries a Chunk *completed*, not which entries the Chunk intended to visit. A frozen plan would act on a stale view of the Dataset. A frozen plan would also create a second, divergent definition of the rotation (AD-26, FR-19).

#### FR-18: Surface the Tracked List's age

The player can see the time since anyone last reviewed the Tracked List.

**Consequences (testable):**
- The Sync Report records the date of the last tracked-list edit, and the view shows that date (AD-23).
- The tool derives that date from the git commit history of `data/tracked.json`, not from a hand-maintained field. A hand-maintained field would become stale exactly when the date mattered. `[ASSUMPTION: AD-23 requires the date be recorded but names no mechanism.]`
- The view shows the date unconditionally. A Tracked List that runs unattended for months is visible as such, and the player does not have to search for the date.

**Notes:** `[NOTE FOR PM]` The tool cannot show a Combination that nobody told the tool to watch (Risk R-2, §9). FR-18 exists so that the gap prompts a periodic deliberate review. FR-18 does not close the gap.

### 4.6 Background Price Sync

**Description.** A CLI does one bounded Chunk of work and then exits. The player's own scheduler starts the CLI again and again. A full refresh takes ~15 hours and uses ~62% of the daily search budget. That cost is acceptable, precisely because the CLI precomputes every figure and no figure is on a user-facing path. This section fixes how the tool estimates a price. This section does not leave that decision to whichever agent writes `sync`, because every downstream number inherits the estimate method.

**Functional Requirements:**

#### FR-19: Run as a bounded, resumable, single-instance Chunk runner

One invocation performs one Chunk. The invocation then exits.

**Consequences (testable):**
- A Chunk ends at whichever of these three limits comes first: the remaining search allowance, the remaining fetch allowance, or the workload remainder (AD-7).
- **Neither allowance is a configured constant.** The governed client holds a live rate-limit state. That state gives the amount that is still available in the tightest unsatisfied bucket (FR-20). Both allowances are that amount. The tool therefore discovers a Chunk's size at runtime, and no number is compiled in. The ~1,500-search figure of FR-14 is a budget across a full refresh. The ~1,500-search figure is not a per-Chunk bound. Do not confuse the budget with the bound.
- **`config.json`'s `minChunkSearches` is not a counter-example, because `minChunkSearches` bounds no Chunk.** The tool reads `minChunkSearches` at exactly one place — FR-17's load-time `pinned`-cap validation. The rate governor never reads `minChunkSearches`. An implementation that lets `minChunkSearches` cap, pace or shorten a Chunk has violated **this FR**. An implementation that reads `minChunkSearches` anywhere but tracked-list validation has violated **FR-17**. The field answers *"could this Tracked List ever work?"*. The field does not answer *"how much work is there right now?"* (AD-26, FR-31).
- `sync` pins progress to the schema and commits the progress. A killed run therefore loses at most the requests in flight.
- A run acquires an exclusive on-disk lock. A run that finds the lock held writes a log line and **exits 0**. Routine overlap is not a failure, and a non-zero exit would make every scheduler treat routine overlap as a failure (AD-7).
- The syncer assumes nothing about the program that invokes the syncer, the invocation frequency, or the machine that runs the syncer. `minChunkSearches` does not change that property. The **player** declares the cadence that the player schedules, and FR-17's runtime half audits the declaration. The syncer itself still infers nothing about its invoker.

#### FR-20: Route all outbound trade traffic through one rate-limit-adaptive client

Exactly one adapter issues trade API requests. The adapter paces the requests from live headers.

**Consequences (testable):**
- The adapter reads `X-Rate-Limit-Rules` to learn the active rule names. The adapter then parses the policy and `-State` headers for each named rule. The adapter paces against the tightest unsatisfied bucket (AD-8).
- **No rate is hardcoded.** The expected shape is a measured value, never a compiled-in constant.
- On a 429 response the adapter obeys `Retry-After`. The adapter then ends the Chunk instead of retrying in a tight loop.
- The adapter sends a descriptive `User-Agent` that names the tool and a contact address. GGG asks third-party tools for such a `User-Agent`.
- The adapter sends unauthenticated requests. The tool stores no credential and requires no credential.

#### FR-21: Estimate a price as the median of the cheapest instant-buyout listings

For each Tracked Entry, one search and one fetch produce one Price Observation.

**Consequences (testable):**
- The search uses that Base Type. The search uses that entry's Item Level Floor. The search uses `magic` rarity for an entry with affixes, and `normal` rarity for a Raw Base. The search uses the entry's Modifier References as stat filters, **one filter per reference and shaped by the reference's kind**. The search asks for **instant buyout only**. The search is **sorted by price ascending** (AD-16).
- **The stat filter's shape follows the reference's kind** (AD-5, AD-16). A **`banded`** reference carries **both `min` and `max`** from the band. A **`valueless`** reference carries the stat id and **no edges at all**. A `min`/`max` filter for a stat that rolls no value is the operational half of the sentinel defect that §3's *Modifier Reference* rejects. Such a filter does not raise an error. Such a filter silently returns nothing, or returns the wrong population.
- The adapter passes a band's `max` as well as the band's `min`. That is what makes the priced population the same population that FR-29 computes a probability for. A min-only filter returns every higher tier and prices the band at the band's floor. A min-only filter is the defect that BQ-1 identified, reintroduced at the adapter (AD-5, AD-16).
- The Base Type goes in **`query.type`**, not in `type_filters.category`. `category` takes taxonomy ids such as `weapon.bow`, and no committed artifact maps a Base Type to that Base Type's leaf category. The Base Type alone is sufficient and exact (AD-16, AD-25).
- Instant buyout is the option labelled **"Buyout or Fixed Price"**. That option's `id` is JSON `null`. The adapter must emit that `id` explicitly, and a serialiser must not drop it. Instant buyout is **not** `priced_with_info`, whose live label is *"Price with Note"*. The wrong option raises no error. The wrong option silently admits unpriced listings and corrupts every estimate (AD-16).
- The fetch retrieves the **cheapest 10 result ids**. The Price Observation is the **median of those listings' prices after normalisation to Divine**. `sync` records the Price Observation with the sample size that the fetch actually returned (AD-16).
- **On an even sample the median is the lower of the two middle values**, not the mean of the two middle values. Ten results is the common case, so an even sample is the normal path rather than an edge case. An unstated rule here is enough on its own to make two implementations return different prices from identical data. The lower value buys three things. **Every persisted price is a price that someone actually asked**, never a synthetic midpoint. **`sync` normalises and rounds each listing once at the sync boundary (FR-23), so a choice of one listing cannot leave the grid, where a mean could.** That argument holds at any precision, which is why this document states the argument without reference to the number. The lower value also leans very slightly cheap, in the same conservative direction as the ascending sort.
- Fewer than 10 results is valid, and `sync` records the true count. **Zero results is `no-listings`, never a price** (AD-9).
- Where a result set spans several listing currencies, `sync` takes the median over normalised values. The sample may therefore not be the globally cheapest ten. `sync` accepts and records that result. `sync` does not correct that result with extra requests.
- The ascending sort keeps stale overpriced listings out of the estimate. The instant-buyout-only filter removes listings priced below market, because a buyer would already have bought such listings (AD-16).
- **A multi-`#` stat filters on one derived value, and which derived value that is, is a measurement rather than a choice.** *"Adds # to # Lightning Damage"* rolls two numbers, and the filter compares one derived value. Band edges are expressed in **that quantity and no other**, because this adapter passes the band edges into the filter and FR-29 counts the population that comes back. A producer that picks a different quantity emits a file that validates and prices the wrong population. **§10 OQ-12** identifies the quantity, and the weights scraper project owns OQ-12. The quantity is not an assumption to code around.
- **Band edges are numbers, not integers.** Under an averaged unit the value lattice is half-integers, so `56.5` is a legitimate edge (AD-28). Whether the trade filter accepts a non-integer `min`/`max` is part of OQ-12 and is unconfirmed. The exact shape that a `valueless` filter takes is also part of OQ-12 and also unconfirmed — whether the stat-filter object accepts a stat id with `value` omitted entirely, requires `{ "value": {} }`, or rejects the stat id. Both are live-payload facts of the class that this FR's other filter consequences exist to catch, and this document's account of both is **unverified**. `[ASSUMPTION: the valueless filter is emitted with the stat id and no value object. Verified for the four filter details above against live payloads on 2026-09-12; this one was not, and it is owned with OQ-12.]`
- **The estimator prices the cheap end of whatever band the estimator is given, so the band must be homogeneous.** That behaviour is harmless where a reference's population is one tier. That behaviour is dangerous where a reference's population spans a tier boundary, because then the cheapest listings are the neighbouring tier's tail while FR-29 carries the whole span's probability. FR-22's interior-cell curation rule is what keeps the two populations aligned, and that rule is a rule rather than a preference (AD-16, AD-28).

#### FR-22: Derive each entry's Item Level Floor from its Accepted Tier

Each Tracked Entry declares the item level that the entry's search filters on. A stated rule gives that item level, not a global constant.

**Consequences (testable):**
- The **Accepted Tier** of a modifier is tier 1. The **exception** is a modifier whose tier 1 first becomes available at item level 81 or 82. Such modifiers are too rare to chase, and the curator accepts tier 2 instead.
- A Tracked Entry's **Item Level Floor** is the highest item level among that entry's affixes' Accepted Tiers. Worked example: on bows, critical hit chance tier 1 appears at item level 73. Increased physical damage tier 1 appears only at item level 82, and the curator rejects that tier 1 in favour of its tier 2 at item level 75. A bow entry that carries both affixes is therefore floored at **75**.
- The Accepted Tier decision and the Modifier Reference's **band** are **one act** — the trade API has no tier concept (AD-5) — but the mechanical meaning of "accept tier 2" depends on the modifier.
- **For a modifier whose text carries one `#`, tier and band coincide.** "Accept tier 2" means that the curator sets the reference's `valueMin` and `valueMax` to the tier 2 band's edges, exactly as before.
- **For a modifier that carries more than one `#`, no pair of value edges isolates a tier, and the curator must not try.** The game rolls two numbers, and the trade filter compares one derived value. The value axis therefore does **not** partition the tier axis: one value interval genuinely draws spawn weight from several tiers (AD-28). 53 of 63 item classes carry such a modifier. A curator who takes the tier's own value range and writes that range as the reference's edges produces edges that land **mid-cell** — the worked contract example has Bows T8 running 56.0–80.0 while the cells are `[56,56.5] [57,78.5] [79,80]`. The entry then fails FR-29's edge-alignment check at load. The reference's edges must align to **cell** edges that the Weights File declares.
- **A reference that spans a tier boundary necessarily includes the neighbouring tier's tail, and that inclusion is correct rather than a defect** — because the trade search cannot isolate that tier either. The priced population and the weighted population remain the same population, which is the only property that FR-21 and FR-29 jointly require.
- **Curate to interior cells by default.** FR-21 prices a reference from that reference's **cheapest 10** listings, so a reference that spans a boundary cell is priced at the cheap tail of the neighbouring tier while carrying the whole span's probability mass. Below the Payout Threshold that summand does not merely understate the value. The summand **truncates to zero and takes the good tier's mass with it** (FR-1). That is BQ-1's failure mode, re-entered through a heterogeneous band rather than through a floor. The partition already supplies the remedy. The interior cell — `[57,78.5]` rather than `[56,80]`, in the worked example — is a reference whose population is one tier and whose price is that tier's price. The boundary mass is then **untracked, which costs nothing**: FR-1 sums over a partition of *tracked* outcomes and has never required the tracked set to be exhaustive. Span a boundary only where the curator knows that the two tiers' prices are close (AD-28, AD-16).
- **None of this changes the request budget.** The cell count roughly doubles for an affected family, but one tracked Modifier Reference is still one Tracked Entry and one search (FR-14). The finer partition changes how many entries a curator needs to isolate what the curator wants. The finer partition does not change the cost of an entry.
- `itemLevelMin` is a declared field on the Tracked Entry, and a person authors the field by hand. Neither `sync` nor `core` infers `itemLevelMin`, and neither `sync` nor `core` adjusts `itemLevelMin`.
- Raw Bases are pinned to item level 82 (FR-3).
- **A Base Type has one Item Level Floor**, and the curator derives that floor in two steps, both by hand:
  1. Each crafted entry has a **candidate** floor — the highest item level among that entry's own affixes' Accepted Tiers, per the rule above.
  2. The Base Type's Item Level Floor is the **maximum candidate across its crafted entries**, and every crafted entry on that Base Type declares that floor.
- Step 2 is what makes the shared floor reachable rather than merely required: two bow entries that derive candidates of 73 and 75 both declare **75**. Without step 2, FR-16 would reject a Tracked List that FR-22 had just told the curator to author.
- A raise of an entry from that entry's own candidate to the Base Type's floor is **not cosmetic**. The raise widens that entry's scoped Eligible Pool and so changes that entry's probability (FR-29). The curator is choosing one crafting proposition for the base, which is exactly what AD-17 requires. Tracking of the same base at two genuinely different floors is deferred, not available.
- The Base Type's crafted entries share that floor, and the tool enforces the shared floor at load (FR-16, AD-17). A Raw Base at item level 82 is exempt, because a Raw Base is never a summand (FR-3).
- That floor is what scopes the Eligible Pool that normalises every probability on the Base Type (FR-29, AD-18). The floor is a valuation input, not only a search parameter.
- **Two References naming two Stat Lines of one Source Modifier cannot both be tracked in one slot.** The two References look independent — different `statId`s, no bands intersecting — but the two Stat Lines always roll together, so one item satisfies both References. FR-16 rejects such a pair at load through FR-16's `coOccur` branch. This is a **load-time rejection, not a budget question**: the curator is not trading a second search for a finer answer, the curator is writing a Tracked List that will not load. Where the conjunction is the thing that the curator actually wants to price, **isolation of the conjunction is deferred** (§7.2). The tool has no way to express *"I want both of these"* as one outcome, which is why FR-16 rejects the configuration rather than approximating it (AD-17, AD-29).

#### FR-23: Normalise every price to Divine at the sync boundary

Raw listing currency never enters valuation.

**Consequences (testable):**
- `sync` normalises all prices to Divine. `core` sees no other unit (AD-20).
- Every normalised price records the exchange observation used — rate, source, timestamp. That exchange observation takes part in Provenance propagation and in freshness propagation (AD-10, AD-20).
- `sync` acquires the exchange rates for `data/currencies.json` **before any priced entry in the same Chunk**. The exchange rates are a declared part of the workload (AD-12, AD-20).
- If a listing's currency has no current rate, `sync` writes the entry as `not-yet-synced` with reason `no-exchange-rate` rather than stores the entry unnormalised (FR-9). There is no "priced but not yet convertible" state, because a half-normalised Dataset is one where the ranking is silently wrong rather than visibly empty.
- `sync` rounds persisted Divine prices to **4 decimal places**, once, and `core` never re-rounds a persisted price. Two readers of one artifact therefore cannot disagree on a value.
- **The cheapest persisted value pins the precision, not the price.** One rule governs *all* persisted Divine values, and FR-26's Craft Cost is one of them. A crafting currency is worth a small fraction of a Divine — which is the whole reason that this FR normalises rather than compares raw values. On a 2-decimal grid a cheap orb therefore rounds toward `0.00`, the Craft Cost term collapses, and **FR-1's subtraction becomes a silent no-op that inflates every EV in the product**. At 0.0001 Divine a single rule safely covers both the payout side and the cost side. A future coarsening would have to **exempt `CurrencyRate` deliberately** rather than let `CurrencyRate` inherit the rule (AD-20, and the spine's Consistency Conventions).

#### FR-24: Fail loudly on an unresolvable stat id or Base Type

`sync` never silently skips a Tracked Entry that references a `statId` or a Base Type that the trade API no longer exposes.

**Consequences (testable):**
- `sync` writes that entry's Price State as `unresolvable` **and** records that entry in the Sync Report (AD-6).
- `sync` never skips that entry, never defaults that entry, and never leaves that entry at its previous value. A patched-out modifier must not keep ranking on its last-good price forever (AD-6).
- `sync` detects the condition by validation against the **committed Trade Catalogue** (`data/catalogue/*.json`), before `sync` issues any request. `sync` never infers the condition from results. An empty result set is `no-listings` and never `unresolvable`. A tool that conflates the two states would report a patch-out every time a Combination simply had no sellers (AD-6, AD-9).
- An **explicit human-invoked command at GGG patch cadence** refreshes the catalogue. A sync run never refreshes the catalogue (AD-25). The catalogue's diff is how a renamed `statId` or a new Base Type becomes visible — the same mechanism that fixtures use for response shapes (NFR-2).
- **Two checks, two surfaces.** `sync` checks every id in `data/tracked.json`, and a failure there becomes that entry's `unresolvable` state *and* a Sync Report line. `sync` checks every id in the Weights File, and a failure there becomes a Sync Report line **only** — `sync` reads the Weights File and never writes the Weights File, so `sync` reports the failure rather than repairs it (AD-6, AD-21).
- `core` excludes `unresolvable` entries from valuation. The view surfaces the existence of those entries (FR-9).

#### FR-25: Publish a structured Sync Report

Every run's outcome is data that the view reads, not console output.

**Consequences (testable):**
- The report records requests consumed **per declared source** against the live bucket (AD-12, FR-14). The report records unresolvable entries (AD-6). The report records the date of the last tracked-list edit (AD-23). The report records the **pool-coverage fraction** measured against the loaded Weights File (FR-4, AD-27). The report records a **pinned-starvation** record where one arose.
- **The pinned-starvation record** is present only on a Chunk where the discovered allowance could not cover the pinned set plus at least one `active` entry (FR-17). The record carries `discoveredAllowance`, `pinnedCount` and `activeRefreshed`, which AD-26 names. The record also carries **`declaredMinChunkSearches`, `currencyCost` and `pinnedRefreshed`, which are this PRD's own additions** — no architecture decision requires those three fields. Those three fields are here because "the shortfall" is otherwise at least four different numbers, and because the declared yardstick beside the allowance actually observed is what turns the record from a symptom into a diagnosis (FR-19).
- **The pinned-starvation record is distinct from *entries not reached*, and the distinction is the whole point.** *Not reached* is a normal rotation outcome. Starvation is a **curation defect that the player must correct**. A report that folds the two together reproduces exactly the indistinguishability that the record exists to remove. Without the named shortfall, an oversized pinned set looks like a slow refresh (AD-26).
- **`web` surfaces the presence of the pinned-starvation record**, alongside the tracked-list age (FR-18) and the unresolvable count (FR-24). Those three figures are what tell a player that his list is not doing what he thinks it is. A report field that nothing renders is a field that nobody reads (AD-26).
- The report also records entries **not reached in this Chunk**. This field is **this PRD's own addition** — no architecture decision requires the field — and the field exists because a partially refreshed Dataset is otherwise indistinguishable from a stalled Dataset. *Not reached* is a **rotation outcome, not a skip**: AD-6 forbids a skip, and FR-17's defined order is what makes the phrase precise. The entry's turn has not come, and the report states that fact rather than implies that `sync` passed over the entry (AD-26).
- `sync` commits only the files that `sync` owns, by explicit path — never `git add -A` — so an automated commit never includes an in-progress curation edit (AD-21).
- A dirty working tree elsewhere does not block a sync, and a dirty working tree elsewhere does not enter the sync's commit.

### 4.7 Craft Cost

**Description.** Craft Cost is the term that makes the ranking account for failures. The player pays Craft Cost on every attempt. Most attempts produce nothing worth selling, and the player pays Craft Cost on those attempts too. Craft Cost changes during a league, because currency prices change. Therefore `core` computes Craft Cost from synced rates, and nobody configures Craft Cost as a constant.

**Functional Requirements:**

#### FR-26: Compute Craft Cost in valuation, from synced rates

`core` derives Craft Cost. `sync` never stores Craft Cost.

**Consequences (testable):**
- A Craft Recipe is a currency composition. `data/recipes.json` defines each Craft Recipe. `core` computes a Craft Recipe's Craft Cost from synced exchange rates. `sync` never computes a Craft Cost (AD-22).
- v1 contains exactly **one** Craft Recipe: one perfect transmute plus one perfect augment. The file holds a list. Therefore more Craft Recipes need no code change.
- In v1 a Craft Recipe contributes **only a cost offset**. The distribution transform is the identity transform. Therefore the ordering does not change with the Craft Recipe, and two Craft Recipes differ only by the cost that `core` subtracts (AD-18). This is a documented limitation. An implementer must not invent a distribution to fill the gap. `[ASSUMPTION: the v1 Craft Cost is one perfect transmute plus one perfect augment. Larger currency quantities and partial-craft abandonment are not modelled.]`

### 4.8 Weights File Consumption

**Description.** Probabilities depend on how likely each modifier is to roll. PoE2 does not publish that likelihood, and this app never produces it. This app consumes a file with a defined schema. This app does not care *which* producer satisfies the schema. This app does care that some producer satisfies the schema. The trade API exposes no pool membership, no tier, no item-level availability and no spawn weight. Therefore the Weights File is a **prerequisite** and not an enrichment, and without the Weights File nothing ranks (§7.3). Cadence justifies the separation: prices change every hour, but weights change only when GGG patches the game.

**Functional Requirements:**

#### FR-27: Consume a schema-conformant Weights File and never produce one

`core` reads Modifier Weights from a file that conforms to `WEIGHTS-FILE-SCHEMA.md`. `core` does the normalising itself.

**Consequences (testable):**
- The file carries raw spawn weights per Base Type and affix slot, as **Value Cells within item-level Cohorts**. A banded entry is `(sourceModifierId, statId, kind, valueMin, valueMax, itemLevelMin, weight, provenance)`. A valueless entry is `(sourceModifierId, statId, kind, itemLevelMin, weight, provenance)`. **`WEIGHTS-FILE-SCHEMA.md` owns this shape and is the binding copy.** §3 *Modifier Weight* and this consequence restate the shape for readers who will not open the contract (AD-11, AD-5, AD-29).
- **`sourceModifierId` is required on every entry, of both kinds.** The requirement covers every entry, not only the entries that the producer splits out of a multi-stat source row (§3 *Source Modifier*). The requirement applies everywhere for two reasons. First, `core` then has **one** identity notion rather than two code paths. Second, a producer that forgets `sourceModifierId` on a split row cannot emit a file that still validates (AD-29).
- **A producer must not normalise. A producer must not aggregate across cells, and must not aggregate across tiers.** Revision 4 required aggregation across tiers. Under revision 4, a cell's weight was the conserving sum of the mass that the tiers of the cell's Cohort contributed to that cell, and revision 4 made that summation the producer's job. **AD-29 supersedes revision 4.** The producer emits one entry per `(tier, cell)`. Therefore an entry's weight is `w(t) × P(value ∈ c | t)` for the entry's **own tier alone**. A producer that merges two tiers' mass into one entry now makes an error rather than meets an obligation. A tier *is* a source row, and an entry names exactly one `sourceModifierId`. A merged entry would have to name two `sourceModifierId` values or discard one (§3 *Cohort*, §3 *Source Modifier*). Where two tiers reach the same cell, the file carries **two entries**. Aggregation **across cells** stays forbidden, because `core` sums cells and only cells. The producer still performs the **split**. The split distributes one tier's weight across the cells that the tier reaches, and conserves that tier's mass exactly.
- **`itemLevelMin` is required on every entry, and `valueMax` is required on every `banded` entry.** Neither field has a default, and neither field may be `null`. `itemLevelMin` is the only source of the pool scoping that FR-29 performs. An open-topped band would again make a Modifier Reference that covers that band span tiers. A `valueless` entry carries **no edges at all**. Edges on a `valueless` entry are an error rather than an omission. A producer that builds to a 1.x, 2.x or 3.x shape emits a file that `core` refuses (schema **4.1.0**).
- `core` models the effects of a Craft Recipe on the tier distribution. The file never holds those effects. A producer never needs to know that a Craft Recipe exists (AD-11).
- `core` refuses an unknown `schemaVersion` major rather than guesses. `core` refuses to rank from an invalid file rather than ranks partially. **The move to `4.1.0` does not change the refusal rule, and that is what makes the move non-breaking.** `core` checks the **major**. Therefore a conforming `4.0.0` file is a conforming `4.1.0` file, and the two versions interoperate. The minor version adds one optional field (`statLineCounts`), one check on a property that the contract already asserted (§3 *Source Modifier*), and the exactness rules stated below. Those exactness rules are not a new obligation. They are the rules that the contract always intended, now written down. The minor version invalidates no producer work.
- Hard file errors reject the file outright (schema **4.1.0**):
  - an unknown `schemaVersion` major;
  - a missing or unrecognised `kind`, or one `statId` appearing under both kinds;
  - edges present on a `valueless` entry, or missing, `null` or non-numeric on a `banded` one;
  - a duplicate `(sourceModifierId, statId, kind, valueMin, valueMax, itemLevelMin)` within a slot;
  - **overlapping value bands for one `statId` *at the same `itemLevelMin` and under the same `sourceModifierId`***. Overlap across **different** `itemLevelMin` values is **legal**, and is how a decomposed family expresses two Cohorts' mass in one interval. Overlap between **two distinct Source Modifiers** is **legal** for a separate reason. Two game modifiers may genuinely publish the same stat over the same values. A refusal of that file would force a producer to merge the two modifiers, and the merge would destroy the co-occurrence marker on both (AD-28, AD-29);
  - a missing or negative `weight`;
  - a missing `itemLevelMin`;
  - **a missing `sourceModifierId`**;
  - a missing `poolCoverage`;
  - `provenance: "absent"` appearing in a file. `provenance: "absent"` arises only from a `partial` pool, and only in `core` (FR-28);
  - a missing or empty `gamePatch` (§3);
  - a missing `cohortTotals` row for a family carrying a `modelled-split` entry, or **a Cohort whose emitted cells do not sum to its declared total**;
  - **a `sourceModifierId` group, within one `(Base Type, slot)`, whose entries carry more than one distinct `itemLevelMin`**. This document states the scope because the id is opaque and **stable only within one `(Base Type, slot)`** (§3 *Source Modifier*). A builder that groups globally would therefore refuse conforming files. A source row is one tier and therefore one Cohort (§3 *Source Modifier*). Such a group is therefore malformed. AD-29 always held the property, but nothing enforced the property. That gap left `mass(g)` with **two conforming readings** — whole-group, or per-Cohort — and therefore two different denominators. The check refuses **nothing that conforms** (AD-29);
  - **a `sourceModifierId` group, within that same `(Base Type, slot)`, whose per-`statId` weight sums disagree**. Each Stat Line's cells conserve the same underlying mass. Therefore the sums can disagree only if the producer dropped, duplicated or misattributed a cell. The rule above makes the group one Cohort. Therefore this check is a **single unqualified comparison** rather than a comparison made within a Cohort. This check has the same shape, and the same reasoning, as the `cohortTotals` check (AD-29);
  - **a group listed in `statLineCounts` whose distinct `statId` count disagrees with its declared `statLineCount`, or a listed `sourceModifierId` matching no entry**. `core` applies this check only to the groups that the list names, because the field is optional;
  - **a cell carried by more than two Cohorts**, counted per **`(Base Type, slot, statId)`** across **every** Source Modifier publishing that stat.
- **The "at most two Cohorts" bound rests on a stated assumption, and a producer is owed that assumption.** Only *adjacent* tiers overlap. Therefore a correct partition yields cells that belong to one tier or to exactly two tiers. The assumption is that **no three tiers of one family overlap at a value**. **Here "family" spans every Source Modifier publishing that `statId`.** That is the same key the bound is counted on, and not one modifier's own tier ladder. Therefore a cell to which two modifiers each contribute two overlapping tiers is **not** a conforming file that this rule refuses in error. Such a cell is exactly the case the assumption excludes. If real game data ever breaks that assumption, a person must **escalate a contract amendment**. A producer must not work around the assumption. §7.3 makes this document the document that the producer's owner reads. Therefore this document states the assumption rather than leaves the assumption in the contract alone (AD-28).
- **Two of those keys are deliberately different, and the difference carries load.** `sourceModifierId` **narrows** the non-overlap rule, so that two game modifiers' mass stays separable. `sourceModifierId` does **not** narrow the cohort-carriage bound. A source row is one tier and therefore has exactly one Cohort. A per-row count could therefore never exceed 1, and the check would be **vacuous**. A vacuous check would silently disable AD-28's only mechanical defence against a partition cut too coarsely. Only a family-wide count, across every Source Modifier publishing that stat, can detect that defect (AD-28, AD-29).
- **An id absent from the committed Trade Catalogue is deliberately *not* on that list.** That check belongs to `sync`, and the check is **report-only** (FR-24, AD-6). `core` could not run that check in any case. AD-24 keeps `catalogue/items.json` out of `web`'s fetch set. Therefore the only component that could refuse the file cannot evaluate the Base Type half of the check. **`WEIGHTS-FILE-SCHEMA.md` agrees.** Through 3.0.0 the contract listed the row as a hard file error. 4.0.0 removes the row, states AD-6's reasoning, and routes the finding to `sync-report.json` instead. This consequence used to record a disagreement, and that disagreement is now closed (§10 OQ-14).
- **The unscoped non-overlap rule of schema 2.0.0 would refuse a conforming 4.1.0 file.** The contract's own worked example emits `[56, 56.5]` twice by construction, once per Cohort. 4.x also admits a second legal overlap, between two distinct Source Modifiers publishing one stat over one interval. Non-overlap was only ever a **proxy**. The invariant is the **straddle** rule. `core` checks the straddle rule directly (FR-29) rather than infers the straddle rule from disjointness. A straddle is a **cross-file** error. `data/tracked.json` owns that error, and `core` reports it. A straddle is never grounds for refusing the Weights File. The same file straddles nothing against a Tracked List aligned differently.
- **`statLineCounts` is the optional declaration that guards the explosion, and `statLineCounts` is a sibling of `cohortTotals` in placement and in terms.** `statLineCounts` is a per-`(Base Type, slot)` list of `{ sourceModifierId, statLineCount }`. **A producer may supply `statLineCounts` everywhere. `core` checks `statLineCounts` wherever a producer supplies it. A producer omits `statLineCounts` for any group the producer cannot vouch for.** `statLineCount` is the number of **distinct Stat Lines the source row as scraped publishes**, taken *before* the explosion into entries. **A producer that recomputes `statLineCount` from the entries just emitted makes the check vacuous.** A producer that cannot source `statLineCount` honestly should omit the field rather than derive the field that way. The whole value of the field rests on the field reaching `core` by a path **independent of the entries themselves**, so that a bug in the explosion is caught rather than mirrored. `statLineCount` is not a denominator, and is not part of any identity. A producer that handles multi-stat rows should treat `statLineCounts` as **effectively mandatory**. `statLineCounts` is the only check standing behind the silent dropped-line case of FR-29 (AD-29).
- **`cohortTotals` is the only mechanical check on mass conservation.** That check guards the denominator of every affected Base Type. `core` cannot recover the pre-split tier weights from the cells. Therefore the producer declares those weights. The producer declares, per `(statId, itemLevelMin)`, the plain sum of that Cohort's tier weights. The producer computes that sum **before** any splitting, and therefore by a path independent of the cells themselves. That independence is what catches a dropped, duplicated or misattributed cell. That arithmetic slip is the slip that actually happens.
- **Exact equality means something specific. Until this document wrote that meaning down, three conforming `core` implementations returned three different verdicts on one file.** The rules never fixed a decimal precision, a rounding rule, a float epsilon **or a summation order**. The external producer reads this copy (§7.3). Therefore the six consequences below state the meaning here rather than leave the meaning to the contract alone.
- **Exactness — comparison basis.** `core` compares **parsed IEEE doubles**, summed in the **file's own entry order**, with **no tolerance and no pre-rounding**. Both halves bind. `core` reads the file with a standard JSON parse and compares the resulting numbers. A comparison of serialised decimals at a common scale is a **different** test, and that different test accepts files that this test refuses. Float addition is also not associative. A left fold in array order, a fold in value-lattice order and a sum of per-group subtotals can all reach different totals. Without a pinned order, "exact equality" has no definition at all.
- **Exactness — what `core` checks at load.** `core` applies exactly **two** checks. First, a Cohort's emitted cells sum to that Cohort's declared `cohortTotals` weight. Second, a group's per-`statId` weights sum to the same value. A **third** check is the sum of a tier's split against that tier's own weight. `core` **cannot** apply that third check at all, because tier weights never enter the file. That is precisely **why this document does not soften the two checks `core` can apply**. Those two checks are the only mechanical hold on conservation there is (AD-28).
- **Exactness — band edges are exact for a separate reason**, and a reader must not conflate the two reasons. Binary represents an integer or half-integer lattice exactly. Therefore a correct edge compares equal with no tolerance. An edge that misses by a very small amount is not a rounding artefact. Such an edge is a cell that **straddles** (FR-29), and the partition exists to remove that defect.
- **Exactness — how a producer discharges it.** **Preferred:** the producer emits values that binary represents exactly. Those values are integers, or fractions with a power-of-two denominator, at magnitudes well inside `2^53`. A largest-remainder split onto an integer grid conserves mass exactly, and makes the question disappear rather than manages it. **Fallback:** the producer lets a residue-absorbing cell close each sum, in the file's own entry order. The fallback is **unsound where both sums constrain one cell**. A cell whose `statId` another Source Modifier also publishes answers to its Cohort total *and* to its group's per-`statId` agreement. The two adjustments then fight, and there may be no assignment that satisfies both. The trap is that the fallback fails **intermittently**. Over random two-decimal splits of round totals, two cells never failed, three cells failed ~9% of the time, four cells ~16%, and eight cells ~33%. Therefore a producer that spot-checks narrow families sees nothing wrong, and still ships a file that `core` refuses on a wide family.
- **Exactness — what a refusal reports.** A refusal reports the observed sum, the expected total and the **signed difference** between the two. A refusal never reports merely that the two disagreed. A delta of `1e-13` is a serialisation artefact. A delta the size of a cell is a dropped cell. Without the number nobody can tell which of the two occurred. The external producer can tell least of all, because the external producer otherwise sees only that `core` rejected the file. That figure is also the evidence that any future revisit turns on (§7.2).
- **Exactness — why the two checks differ in shape, and why the rule above is written for only one of them.** A Cohort's conservation has a **declared total**, `cohortTotals`. Therefore "expected" names something in the file. A group's per-`statId` agreement has **none**. That check is a mutual equality among the group's Stat Lines. Therefore no declared figure exists to be wrong against. **For that check the refusal reports every `statId`'s observed sum and the signed differences between those sums, and names no expected total.** An implementation that invents an expected total, by electing one Stat Line as authoritative, has made a choice the file does not license. Two `core` builders electing different Stat Lines would report contradictory diagnoses of one file. The same asymmetry bounds the producer's fallback route. A residue-absorbing cell has a total to close to under the first check, and has nothing to close to under the second check. That is the mechanism behind the both-sums unsoundness stated above (AD-28, AD-29).
- **Two producer obligations here are unverifiable, and this document names those two rather than implies them.** `core` holds no tier data. `core` can check that cells tile, that Cohorts sum to their declared totals, and that no more than two Cohorts carry one cell. `core` **cannot** check that the producer cut the partition at the real tier endpoints. `core` also cannot check that a split's conditional distribution is right. The *"at most two Cohorts"* error is what makes the degenerate case detectable. A producer that emits one wide cell per Cohort gives that interval to every Cohort in the family. Such a file would otherwise satisfy every mechanical check, and would force every curator into a full-span reference — BQ-1 through a coarse cell instead of a sentinel value. `modelled-split` is precisely the label for the residue that stays unverifiable (AD-28, FR-10).
- A `partial` pool, a Base Type absent entirely and a slot with an empty pool are **degraded but loadable**. The Base Type leaves the ordering, and `core` does not refuse the file (FR-4, FR-28).

#### FR-28: Enforce the pool-completeness contract in both directions

The producer obligation and the consumer treatment are two halves of one rule. An implementation of only one half produces a ranking that is wrong and that carries no warning.

**Consequences (testable):**
- **Producer side:** a `(Base Type, slot)` declaring `poolCoverage: "complete"` must enumerate **every** modifier that can roll there **at any item level**. That enumeration includes worthless modifiers, and carries true weights and true `itemLevelMin` values. `weight: 0` means "cannot roll here" and is meaningful. A producer that omits the entry instead breaks the completeness claim. There is no third option. A producer that cannot guarantee completeness declares `partial`.
- **Completeness counts Stat Lines, not rows.** A `complete` pool enumerates **every Stat Line every rollable modifier publishes**. Therefore a producer that emits one line of a Source Modifier and drops the other lines of that Source Modifier makes the same defect as a producer that drops a modifier outright. Without this statement, a producer reading this FR alone can drop the second Stat Line of each of the 560 multi-stat rows and still believe it declared `complete` honestly. That omission shrinks **numerators** without touching the denominator. That defect is the exact mirror of the defect the rest of this FR argues against. It is also the one direction the source-modifier denominator does **not** protect against, because the denominator counts the row once either way. `WEIGHTS-FILE-SCHEMA.md` states the stat-line reading of completeness. AD-29 supplies the underlying fact that one modifier may publish several lines.
- **A dropped source *row* has effectively no mechanical check, and that gap is the larger of the two gaps.** `statLineCounts` guards the Stat Lines **within** a row (FR-27). **Nothing guards the set of rows.** The one exception marks the boundary rather than closes the gap. A row **lost in the explosion after the producer counted it** surfaces as a listed `sourceModifierId` matching no entry, which is a hard file error. That error surfaces only where the producer listed that group, and only because the count came from the source row rather than from the entries. **A row absent from the source in the first place is listed nowhere, and every check in the contract is blind to that row.** That case is the case this consequence is about. `cohortTotals` catches a row missing from a family `cohortTotals` already covers. However, `cohortTotals` is *required* only where a family carries a `modelled-split` entry, and most rows are single-stat and undecomposed. A row dropped from a pool still declaring `complete` **shrinks the denominator and inflates every probability on that Base Type**, which reorders the ranked list. That outcome is **strictly worse than a dropped Stat Line**. A dropped Stat Line shrinks one numerator. Where that `statId` has a second publisher, a dropped Stat Line does so silently and reorders that Base Type too (FR-29). A dropped source **row** moves **every** Combination on the Base Type, and nothing stands behind that row but the `poolCoverage` declaration itself. **What stands between the file and that outcome is the producer's assertion**, which is the same trust already extended to every weight in the file. A producer that cannot vouch for that assertion declares `partial` instead. **The mitigation is real and cheap: a producer may emit `cohortTotals` for every family, and this document encourages that.** That practice narrows the gap considerably. `WEIGHTS-FILE-SCHEMA.md` states this gap and the `modelled-split` predicate that limits the reach of `cohortTotals`. AD-29 supplies the underlying source-row model.
- **Completeness does not depend on item level.** A cell that only rolls at item level 82 belongs in a `complete` pool, and carries `itemLevelMin: 82`. `core` scopes that cell out for an entry floored below 82 (FR-29). A producer that omits the cell because "we only care about ilvl 75" breaks `complete`. The claim is about the slot, and not about one curator's floor.
- **An unnamed placeholder row still counts.** Where the producer's source publishes a modifier as an unnamed `TBD`, **the modifier exists and carries real spawn weight**. A producer that drops that modifier shrinks the denominator and inflates every other probability on that Base Type. The pool is therefore `partial`, not `complete`. The producer emits the rest of the pool and declares `partial`. The Base Type returns to the ranking when the source names the rows.
- **There is deliberately no field for anonymous weight.** A per-`(Base Type, slot)` scalar entering the denominator but never a numerator was considered and **rejected**. Such a scalar would let a producer hide an arbitrary share of the pool behind a number nobody can check. To add such a field is an architecture amendment, and not a producer convenience.
- This obligation binds an **external project** (§7.3). This document plus `WEIGHTS-FILE-SCHEMA.md` are that project's entire contract. This document states the obligation as a requirement rather than leaves the obligation as a schema footnote, and that statement is what gives the external project something to build to. This document also states the two ways a producer will try to satisfy completeness cheaply. That statement is part of the contract, and not an aside.
- **Consumer side:** a `partial` pool is a *lower bound on the denominator*. Therefore every probability derived from a `partial` pool is an **upper bound**. `core` assigns such probabilities Provenance `absent`, and the Base Type is Unrankable (FR-4). This path is the only path by which `absent` arises. Without this path, the weakest of §3's four Provenance values would be unreachable.
- A Base Type absent from the file entirely is likewise Unrankable. `core` has no other pool source, and `core` must not invent one (AD-18).

#### FR-29: Aggregate weights by cell within an item-level-scoped pool

This PRD specifies how to derive probability exactly. Two implementers cannot diverge.

**Consequences (testable):**
- A Modifier Reference's weight is the sum of the weights of every Weights File entry the reference **contains**, within that same `(Base Type, slot)`. Containment depends on the reference's kind (AD-5, AD-18):

| Reference kind | Contains a Weights File entry when |
| --- | --- |
| `banded` | the entry is `banded`, shares the `statId`, and lies **wholly inside** the reference — `band.valueMin >= ref.valueMin` **and** `band.valueMax <= ref.valueMax` |
| `valueless` | the entry is `valueless` and shares the `statId` |

- **Whole cells only.** `core` handles no open-top form. A reference without a ceiling is a floor. A floor is the BQ-1 defect that §3's *Modifier Reference* exists to remove. `core` therefore never encounters a floor, because `contracts` rejects a floor at the schema. The `(Base Type, slot)` scoping is not optional. To ignore the scoping is the commonest way that two implementations diverge.
- **Both numerator and denominator are drawn from the same item-level-scoped pool**, scoped to the entry's Item Level Floor `L`: `scoped(base, slot, L) = { cell ∈ pool(base, slot) : cell.itemLevelMin <= L }`. `core` writes the conditional as `P(ref | base, slot, L)`. The conditional is over the **Modifier Reference**, which names a Stat Line. The conditional is not over a Source Modifier (AD-18, AD-5).
- **The two halves sum over different things. That difference is the whole of AD-29's consequence for valuation.** The **numerator** sums over **entries** in the reference's containment set. The **denominator** sums over distinct **`sourceModifierId`**:

```
Σ { mass(g) : g ∈ sources(scoped(base, slot, L)) }
```

- `sources(S)` is the set of distinct `sourceModifierId` values in `S`. `mass(g)` is the weight of that one source row. `mass(g)` is the common value of `Σ { e.weight : e ∈ g, e.statId == s }` taken over each `statId s` that the group publishes. **`mass(g)` carries no `L`.** A source row is one tier. A source row therefore sits in exactly one item-level Cohort (§3 *Source Modifier*). The scope admits a group whole or not at all, and there is nothing to reconcile across Cohorts. Where the per-`statId` sums disagree, `core` never has to choose a reading. Such a disagreement is a hard file error, and `core` refuses the file before `core` evaluates this ratio (FR-27).
- **The reason, because the defect is invisible to any single-stat test.** An affix draw selects a **modifier**. A modifier that publishes several Stat Lines must therefore contribute its weight **once**. If an implementation sums the denominator over entries instead, each multi-stat modifier's surplus lines inflate the denominator. The inflated denominator **understates every probability on the base, and understates them unevenly**. A Base Type whose pool holds more such modifiers is distorted more. The error therefore **reorders the ranked list** rather than shifts the ranked list uniformly. For a pool of single-stat modifiers the two readings **coincide exactly**. A builder can therefore implement this FR from the scoping rule alone and pass every test built from a single-stat fixture. That same builder is still silently wrong on the 560 of 8,437 real rows that publish more than one stat (AD-18, AD-29).
- If an implementation scopes only the denominator, the numerator still counts bands that cannot roll at `L`. That numerator inflates one modifier's probability and changes no other modifier's probability. The error therefore **reorders the ranked list** rather than shifts the ranked list uniformly (AD-18).
- A Modifier Reference whose containment set is **empty** under that scope is a **validation error**, not a `P = 0`. The empty set means that the curator tracks a tier that cannot roll on the item being crafted. To contribute zero would hide that fact (AD-18).
- That error is against **`data/tracked.json`**, not against the Weights File. The error is therefore `core`'s, and `core` reports the error the way FR-24 reports a tracked-list failure. The empty-containment-set check is the third of this FR's cross-file checks, together with edge alignment and the straddle rule. `core` runs the empty-containment-set check exactly as `core` runs those two — `web` at load, `sync` at run start — per the ownership clause below (AD-18).
- **The report must name both possible causes, because `core` cannot tell the two causes apart.** The usual cause is the curator's: a reference on a tier that cannot roll at this floor. The other cause is the **producer's**: a file that declares `complete` and dropped a Stat Line. FR-28 forbids that dropped line, and FR-27 checks for the dropped line only where the group declares `statLineCount`. The group-consistency check cannot catch the dropped line. The group-consistency check compares sums across the Stat Lines that a group *does* publish, so a line dropped entirely leaves the remaining sums in agreement. Both causes present identically as an empty containment set. To blame the curator unconditionally would send him to hunt a defect in his own file for a pool that is genuinely missing a line. The error therefore names the reference, names the reference's floor, and states that the scoped pool contains no cell for that `statId`. The error leaves which document is wrong to the reader.
- **That error is only half the dropped-line story, and the half the error misses is the dangerous half.** The error fires only where the dropped Stat Line's `statId` had a **single** publisher. Where a **second Source Modifier publishes the same `statId`** — which AD-29 expressly permits (§3 *Eligible Pool*) — the other modifier still supplies cells. The containment set is then **not** empty, and `core` reports **nothing at all**. The reference's **numerator** silently loses that modifier's share. The probability deflates on that Base Type alone, so the deflation **reorders** the ranked list rather than shifts the ranked list uniformly. The Base Type still reads `complete` and still counts as covered under FR-4, because both of those are declarations rather than content. **The silent case is what `statLineCounts` exists for** (FR-27). `statLineCounts` is the only thing standing behind the silent case. A builder who reads the empty-containment-set error as the whole defence reads a check that cannot fire (AD-18, AD-29).
- **Treatment of an empty containment set as an error is deliberately harsher than FR-27's treatment of a Base Type missing from the file entirely**, which is merely Unrankable. A missing base is an absence that the curator can see in the Unrankable group. An unrollable band is a *silently* empty summand in a list that otherwise looks healthy.
- **A `banded` reference's edges must be edge-aligned to the scoped pool, which is what closes the sentinel loophole.** A requirement that `valueMax` is *present* closes only the **syntax** of an open top. Consider a curator who writes `valueMax: 9999`, or who writes `valueMin: 0` against a pool whose lowest cell starts at 40. That reference is schema-valid, passes containment, passes the empty-set check above, and passes FR-16's overlap predicate. `core` then sums two tiers' weight, while FR-21's stat filter is **operationally min-only** and prices the cheaper tier. That is BQ-1 verbatim, re-entered through a sentinel, with its worst consequence intact: below the Payout Threshold the blended summand truncates out of the sum and takes the jackpot mass with it (FR-1). The hole exists symmetrically at the **bottom**. To close one edge only would close half of a symmetric hole. So, for every tracked **`banded`** reference — a `valueless` one has no edges to align — these two conditions hold over its containment set under the item-level scope:

```
ref.valueMin == min { band.valueMin : band ∈ contained }
ref.valueMax == max { band.valueMax : band ∈ contained }
```

- A reference must begin exactly where its lowest contained cell begins and end exactly where its highest contained cell ends. A sentinel ceiling above the pool's top cell fails that rule. A sentinel floor below the pool's bottom cell fails that rule too. Like the empty-containment-set rule beside it, this rule is a **validation error against `data/tracked.json`**. It is not a wide band, and it is not a file error.
- **Edge alignment is a cross-file check. `core` defines the check once, and every component that holds both files runs it.** The check reads `data/tracked.json` and `data/weights.json` together, so the check belongs to the component that holds both files — and **two** components hold both. `web` runs the check **at load**, which is what keeps an unrankable configuration out of the view. **`sync` holds both sides as well.** `data/tracked.json` is `sync`'s declared workload, and `sync` already reads the Weights File to validate its ids (FR-24). `sync` therefore runs **the same `core` check as a run-start gate**, after `sync` acquires the lock and before any priced entry consumes budget. That gate is in the same class as FR-24's catalogue check and FR-32's league check. This follows FR-24's pattern, which assigns a check by which component holds the file: one definition, two callers. A check re-implemented in either shell would be the divergence that this rule exists to prevent (AD-18, AD-12).
- **In `sync`, a failure aborts the run.** `sync` records the failure in the Sync Report and exits non-zero. `sync` leaves the progress file untouched. The configuration is wrong, not busy. FR-19's quiet exit on a held lock is therefore not the precedent here. FR-32's loud league failure is the precedent. `sync` never prices around the misaligned entry and never skips the misaligned entry silently into a partial Chunk (FR-25).
- **The `sync` gate prevents a wasted refresh, not a wrong number.** The gate is therefore an ordering rule rather than a further check. If the check were `web`'s alone, `sync` would price `min..9999` on Monday and `core` would refuse the configuration in the browser on Tuesday. The budget would be gone. The observation would be written, committed and ranked, and the row would be unrankable anyway. The defect would surface a day after `sync` spent the requests that proved the defect (AD-18, AD-12).
- **`core` evaluates alignment under the scope, and alignment is floor-dependent by design.** The containment set shrinks as the floor drops. A reference can therefore align at one floor and fail at a lower floor. That failure is the rule working: the curator has written a ceiling that the scoped pool cannot reach, which is the same defect as the empty-containment-set case. FR-16 and FR-22 give a Base Type exactly one crafted Item Level Floor. `core` therefore evaluates the check once per Base Type and never ambiguously. A builder who computes the containment set **unscoped** silently accepts exactly the references that this check catches (AD-18).
- Every Weights File cell carries `itemLevelMin`. A cell without `itemLevelMin` is a hard file error (FR-27), because the scoping above has no other source for the item level.
- `P(Combination)` treats prefix and suffix as independent draws: `P(prefix) × P(suffix)`. An absent affix takes `P = 1`. Mod-group exclusion makes the second draw weakly conditional. This PRD defers that refinement (§7) and does not overlook it.
- **A Weights File cell that straddles a tracked reference's edge is a validation error, not a pro-rata split.** A cell straddles when the cell shares the reference's `statId`, lies within the scope, and **overlaps the reference without being contained by the reference**:

```
straddles(cell, ref)  ⇔  cell.statId == ref.statId
                       ∧ cell ∈ scoped(base, slot, L)
                       ∧ cell overlaps ref
                       ∧ ¬ contains(ref, cell)
```

  Such a cell describes a population that the trade filter does not match (FR-21 filters on rolled value). No arithmetic in `core` can recover the difference. `core` reports the straddle against the Tracked Entry whose edge was straddled, by `core`'s check wherever that check runs — `web` at load, `sync` at run start — for the reason FR-27 gives: the error is a property of the two files read together, never of the Weights File alone. **The straddle rule is the invariant. Non-overlap is only a proxy for the straddle rule** (FR-27). Two cells that share a `statId` may cover the same value interval when their `itemLevelMin` differs. Those two cells are distinct Cohorts' contributions to one interval, and the scoping above admits each cell at most once. `core` therefore double-counts nothing (AD-18).
- Straddling is **floor-invariant by construction**, because the producer cuts a family's value axis at every tier endpoint **once across all tiers**, never per Cohort (AD-28). A reference whose edges sit on that partition's boundaries straddles no cell at any item level. The straddle check therefore cannot pass for one Tracked Entry and fail for the next. That invariance does **not** extend to edge alignment, which is floor-dependent on purpose.
- `core` models the craft as a craft on a base at **exactly** the entry's Item Level Floor, while the `ilvl >=` search returns a slightly higher-level superset. This PRD accepts and records that difference. To correct the difference would need an exact-item-level filter that the trade API does not offer (AD-18).

#### FR-30: Depend on an externally produced Weights File as a v1 prerequisite

v1 ranks against a real file that satisfies the real contract. The external scraper project produces that file. **There is no fallback.**

**Consequences (testable):**
- The Weights File is a **release dependency**, not an enrichment (§7.3). The Weights File supplies pool membership, cell edges, `itemLevelMin` and weights. The trade API supplies none of those four, so nothing in this system can derive what the file carries (AD-11, AD-25).
- Until a conforming file exists, **every crafted Base Type is Unrankable** (FR-4). That is the honest outcome rather than a degradation to design around. There is no other pool source, and `core` must not invent one (AD-11, AD-18). Raw Bases are the exception and rank without the file, since a Raw Base carries no probability term (FR-3). What survives a missing file is therefore a white-base price list, not the product.
- A **uniform-prior variant** — every cell `weight: 1`, `provenance: "uniform-prior"`, `producer.id: "uniform-prior"` — remains a legal file and a valid *weighting* placeholder. The variant is never a *sourcing* placeholder. The variant must still carry genuinely sourced pool membership and `itemLevelMin`, which are exactly the two fields that nothing can fake.
- Whatever the file's weighting, the system exercises the probability code path from day one. The ranking formula does not change shape when measured weights arrive.
- Every figure that a `uniform-prior` band influences carries that label (FR-10). FR-11's global caveat applies for as long as any `uniform-prior` band remains.
- Where the producer cannot guarantee completeness, the producer emits the affected `(Base Type, slot)` with `poolCoverage: "partial"`. The producer does not pretend to completeness (FR-28). The system measures the resulting coverage before any view work (FR-4, §10 BQ-3).

### 4.9 League Lifecycle

**Description.** Three or four league resets a year wipe prices entirely. The tool is least useful at league start, which is when the knowledge is worth the most. League resets are the central threat to the one-year horizon. The requirement is not to survive a league reset gracefully. The requirement is to fail *honestly*. An empty ranking is correct. Last league's numbers served as current are not correct. Realises UJ-6.

**Functional Requirements:**

#### FR-31: Refuse to value an observation from a different league

`core` treats a Price Observation from any league but the active one as absent rather than as stale-but-usable. Realises UJ-6.

**Consequences (testable):**
- The active league is configuration in `data/config.json`. Every Price Observation records the league it was observed in (AD-19).
- **`data/config.json` carries exactly three things: the active league, `minChunkSearches`, and `schemaVersion`.** `core` and `sync` read the first. **Only** FR-17's load-time `pinned`-cap validation in `sync` reads the second (FR-19). NFR-8 requires the third of every artifact. The file is player-owned (NFR-5). `web` fetches and validates the file on load (FR-33), even though `web` reads neither of the first two for behaviour. **The file is not a settings bag. A fourth field is an architecture amendment**, not a config addition (AD-19, AD-26).
- `core` refuses to value an observation whose league differs from the active league. `core` treats such an observation as `not-yet-synced` with reason `league-mismatch` (FR-9) rather than as stale-but-usable.
- A league change is a config edit plus a natural re-sync. The ranking is honestly empty until data arrives, and the ranking refills without anyone rewriting the Dataset.
- `sync` does **not** filter the Dataset on write. League filtering happens once, in `core`, so a league change does not blank the site while a re-sync runs (AD-14). `[ASSUMPTION: this makes a league change a config edit plus a natural re-sync with no manual purge. It follows from AD-14 and AD-19 but has not been exercised against a real reset.]`

#### FR-32: Validate the configured league against the live leagues endpoint

`sync` checks that the configured league is real before `sync` spends any budget against that league.

**Consequences (testable):**
- `sync` validates `data/config.json`'s league against the live leagues endpoint at the start of each run, and fails loudly on a mismatch (AD-19).
- The validation happens before any priced entry consumes budget. The validation's single request is one of FR-14's four declared sources. That request is a fixed per-run overhead, and the Sync Report reports it separately.

### 4.10 Dataset Delivery

**Description.** How data reaches the view looks like an implementation detail, and it is not one. The delivery method decides whether a sync commit refreshes the site on its own or needs an application rebuild. That decision in turn decides whether the daily refresh is a background fact or a chore.

**Functional Requirements:**

#### FR-33: Fetch published artifacts at runtime as a consistent set

`web` reads its data at runtime rather than at build time.

**Consequences (testable):**
- `web` **fetches exactly eight artifacts** at runtime as separate cache-busted requests. `web` never bundles the eight artifacts into the JS, so a sync commit updates data without a rebuild of the app (AD-24). The eight artifacts are `dataset.json`, `sync-report.json`, `weights.json`, `recipes.json`, `tracked.json`, `config.json`, `catalogue/stats.json` and `catalogue/static.json`.
- The two catalogue files are what let the view render a `statId` as its human text and a currency as its icon **without a runtime call to pathofexile.com**, which is forbidden (AD-15, AD-25). Without the two catalogue files the view would show raw stat ids, which is the same list in a form the player cannot read.
- **Four** files are deliberately **not** fetched. `sync-progress.json` is internal to `sync`. Only `sync` needs `catalogue/items.json` and `catalogue/filters.json`. **`data/currencies.json`** is a sync-side workload declaration that `web` has no use for (AD-3, AD-24, AD-21). The eight are the complete set. A ninth artifact is an architecture amendment.
- **Two rules depend on that last omission rather than merely tolerate it.** The Base Type cross-check of FR-24 belongs to `sync` because `web` cannot read `catalogue/items.json`. FR-17's load-time `pinned` cap belongs to `sync` because `web` cannot read `data/currencies.json` and cannot know what the currency step costs in searches.
- Each artifact carries `schemaVersion`, and `web` validates each artifact on load. `web` refuses to render an invalid artifact rather than degrade (AD-3).
- **"Refuses to render" applies to a *schema-invalid* artifact.** `web` reports a schema-valid artifact that fails a **cross-file policy check**, and never meets such a failure with a file-level refusal. FR-17's `pinned` cap is such a check, and `sync` alone owns it. Read together with the refusal rule and without this qualification, a builder could land on a refusal to render the entire site because the player pinned one row too many. That refusal would be a total outage of a product whose premise is a static page that always renders, over a sync-budget concern that the browser cannot even evaluate. FR-29's edge-alignment, straddle and empty-containment-set errors are cross-file checks of the same class. `core` defines those three checks, and **`web` reports them at load rather than meets them with a file-level refusal**. The same three checks abort the run in `sync`. That abort is not an exception to this rule but the other half of the rule: a shell that can still stop before it spends anything should stop, and a shell that can only render should render (FR-29, AD-3, AD-24, AD-26, AD-18).
- `web` renders from a **single consistent set** and does not mix artifacts across a refresh (AD-24).

## 5. Cross-Cutting NFRs

- **NFR-1 — Zero network in the test path.** No test at any level makes a real network call. MSW runs in `onUnhandledRequest: "error"` mode. An unfixtured request therefore fails loudly and does not escape (AD-13). This is the hardest requirement in the brief. It lets an agent iterate against a service that would otherwise rate-limit the agent into uselessness. It also makes a red test mean "the code is wrong" rather than "GGG was slow."
- **NFR-2 — Fixtures are real captured responses.** A fixture is a committed real payload, never a hand-written mock. Re-recording is a separate command that a human invokes explicitly. Re-recording is never part of a test run. The fixture diff that re-recording produces is the mechanism that makes GGG's changes visible (AD-13).
- **NFR-3 — Determinism.** Valuation is pure. Time, randomness and configuration enter only as passed-in values. No test depends on wall-clock timing. A test of rate-limit backoff injects header values and does not wait (AD-1, `AGENT-WORKFLOW.md`).
- **NFR-4 — Parallel worktree development.** Packages own disjoint directories with a one-way acyclic dependency graph. CI enforces the graph mechanically, rather than review enforcing it. Two agents in two packages therefore touch no common file (AD-2). `contracts` changes are **serialised and land alone, first**, and dependent work rebases onto those changes. `contracts` is the one package everything depends on, so a change there causes a broad rebuild and a likely conflict. **No worktree runs a live sync or a live catalogue refresh**: only the scheduled invoker on the player's machine runs `pnpm sync`, and `pnpm catalogue:refresh` is a human act on a game patch (FR-24). An agent that verifies sync behaviour uses `pnpm sync:dry`. `pnpm sync:dry` runs the full pipeline against recorded fixtures and writes nowhere. These partitioning rules are `AGENT-WORKFLOW.md`'s. AD-2 supplies only the dependency graph that the partitioning rules rest on.
- **NFR-5 — One writer per file.** Every shared file has exactly one writer. Hand-owned inputs belong to the player, and sync-owned outputs belong to the syncer. An agent that needs different data uses a fixture, never an edit (AD-21).
- **NFR-6 — Read-time budget.** A full ranking pass takes under 100 ms (§4.1).
- **NFR-7 — Static delivery, zero upkeep.** The view is a static bundle that CI deploys. There is no server to patch, no secret material, and no credential that expires (AD-15).
- **NFR-8 — Schema versioning at every trust boundary.** Every published artifact and input file carries `schemaVersion`, and the consumer validates the file on load. A consumer refuses an unknown major version rather than guessing. The producer validates before it writes (AD-3, and the spine's Consistency Conventions).
- **NFR-9 — Third-party citizenship.** Requests identify the tool and a contact address, pace from live rate-limit headers, and honour `Retry-After` (AD-8). The product must keep API access. This is a standing requirement, because the product depends entirely on API access (R-7).
- **NFR-10 — Accessibility floor.** AD-24 requires that colour alone must not carry the distinctions AD-10 mandates. This PRD **extends** that rule to every product-meaningful distinction — Price State (FR-9), crafted versus Raw Base (FR-3) and Provenance (FR-10). The reason AD-24 gives applies identically to all three distinctions. `[ASSUMPTION: the extension beyond AD-24's literal scope is this PRD's, not the spine's.]`

## 6. Non-Goals (Explicit)

- **Producing modifier weight data.** The scraper is a separate project. The app consumes a file and is indifferent to the producer of that file (AD-11). This is a non-goal for *this repository*. The file is not an optional input: the file is a release dependency (§7.3).
- **Advising whether to augment an item already in hand.** The player makes this decision dozens of times a session, far more often than the player reads the ranked list. The decision is excluded by design. The player can already tell that an increased-stun-threshold roll is dead. This decision is the strongest v2 candidate if the pickup list proves its value.
- **Loot filter export in v1.** PoE2's filter syntax has no working equivalent of `HasExplicitMod`. A generated filter can therefore express base type, item level and rarity, but never modifier Combinations. Loot filter export remains a **roadmap item** that automates the base-name half of the knowledge. It has a permanent ceiling: the modifier half stays in the web view. The web view is therefore the permanent product rather than an intermediate step toward another product. The brief's "eventually I won't have to memorize anything" outcome is not achievable.
- **Rare items.** Magic only: at most one prefix and one suffix.
- **Accounts, sharing, per-user preferences, anything multi-user.** Any requirement that appears to need a backend is escalated and not implemented (AD-15).
- **Visual design beyond an off-the-shelf framework.** Appearance is explicitly not a priority.
- **Price history features.** Git carries the history through sync commits. No v1 feature reads that history (AD-14). UJ-5's "returned no listings all league" judgment is therefore the player's own recollection plus the current Price State. That judgment is not a trend that the tool renders.
- **Market scanning as candidate generation.** Rejected on both shallowness and cost — see the brief's addendum.
- **Sell-through speed as a ranking term.** Considered and rejected: the player was explicit that sell speed is not a factor.
- **Ranking on variance, median outcome, or an exposed risk preference.** At ~144 crafting decisions an hour, attempt volume makes mean-based math sound.
- **Discovering Combinations the player did not think to track.** Recorded as Risk R-2 (§9), and not addressed.

## 7. MVP Scope

### 7.1 In Scope

- Magic Base Types — one prefix, one suffix — at per-entry Item Level Floors derived by the Accepted Tier rule (FR-22).
- Raw Bases at item level 82, threshold-truncated like any other outcome.
- Ranked Base Type list, bounded for readability, with chase Combinations, expandable to the full tracked Combination list including tombstones.
- Player-set Payout Threshold, re-ranking at read time.
- Background sync: unauthenticated, rate-limit adaptive, bounded, resumable, with a defined Refresh Rotation.
- Four-state pricing with reasons on `not-yet-synced`, and unknowns segregated from the ranking.
- Provenance and per-row freshness throughout, plus the global uniform-prior caveat.
- Curation through hand-edited committed files, surfaced read-only in the view with tracked-list age.
- One Craft Recipe with cost computed from synced rates.
- A defined Weights File **schema**, with its pool-completeness contract enforced in both directions. The **file** itself is an external deliverable, and is not in scope here (§7.3).
- Divine normalisation at the sync boundary, with exchange observations carried in Provenance.
- League-scoped observations with an honest empty state across a reset.

### 7.2 Out of Scope for MVP

- **A second Craft Recipe** — AD-18 makes ordering recipe-invariant in v1. A second recipe therefore adds a cost column and no ordering information. Revisit when distribution mechanics exist.
- **Producing Modifier Weights** — v1 ranks on whatever the scraper project delivers, gated by the coverage measurement of §10 BQ-3. The ranking improves as the file improves, and the app does not change. What is out of scope is this repo producing weights. The app having good weights is not out of scope.
- **Authenticated sync** — a quantified lever that would raise the rate limit. The cost is that authenticated sync reintroduces a credential that expires. Revisit only if a full refresh must exceed ~1,500 searches.
- **Mod-group conditional probability** — FR-29 assumes independent affix draws. Deferred until measured weights make the error estimable.
- **Pricing a deliberate conjunction of co-occurring stats** — a curator may genuinely want *"this base carrying both Stat Lines of this hybrid modifier"* as one priced outcome. v1 cannot express that outcome. The two Stat Lines share one Source Modifier and one weight. FR-16 therefore rejects tracking the two Stat Lines as two entries, and there is no third form that means *both at once*. This record matters because the deferral is **why** FR-16 rejects a configuration that a curator will plausibly try, and **why** that rejection is not a defect (FR-22, AD-29).
- **Coarser fallback pricing for zero-listing Combinations** — widening the search to "base + this prefix, any suffix" as a marked estimate. Held as the named option if the unknown bucket proves unusable. `[NOTE FOR PM]` This is the likeliest thing to be missed if `no-listings` turns out to be a large fraction of the Tracked List. Check after the first full refresh (§10 OQ-6).
- **Spawn-weight disambiguation of the unknown bucket** — use of modifier rarity to separate "rare and unlisted" (plausible jackpot) from "common and unlisted" (junk). This is the only identified route that actually *resolves* a `no-listings` entry rather than segregates it, and it is contingent on measured weights arriving. It is the reason the weights deferral above has a cost beyond provenance labelling.
- **Re-seeding the Tracked List from community sources** — spawn weights for rarity, build popularity for demand. This is the most promising answer to Risk R-2, and the single largest gap v1 leaves open.
- **Making `statLineCounts` required** — this change would close the silent dropped-line gap (FR-29) for **every** file rather than only for producers that opt in. Deferred because a requirement now would be a **breaking** revision against a producer that already builds to `4.x`. The optional form already gives any producer that wants the check a way to have the check. **To be included in the next breaking revision rather than deferred again** (FR-27, §7.3).
- **A relative epsilon on the two sum rules** — `cohortTotals` conservation and per-`statId` group agreement are exact comparisons with no tolerance (FR-27). A producer that takes neither discharge route therefore emits a file that is arithmetically correct and still refused at load. That outcome was accepted because the failure is loud and immediate, and fails **closed**. **Revisit if a conforming producer reports spurious refusals in practice.** The signed difference that the refusal reports is the evidence that the revisit turns on. A relative epsilon would never extend to band edges, which stay exact for a separate reason.
- **Repository split for the weights schema** — deferred until the schema stops moving. Extraction is then mechanical.
- **A hosted syncer** — AD-7 makes a hosted syncer a configuration change rather than a rewrite. Revisit if a day-stale Dataset becomes intolerable.
- **Observability beyond the Sync Report** — a committed structured report is the whole story. There is no metrics stack.

### 7.3 Release Dependencies

One dependency sits outside this repository, and that dependency gates the release rather than merely enriches it. This section states the dependency, because a prerequisite left implicit inside an FR is discovered only at integration.

- **The Weights File, from the external scraper project (FR-30).** The Weights File supplies pool membership, cell edges, `itemLevelMin` and weights. The trade API supplies none of those four things (AD-25). Until a conforming file exists, every **crafted** Base Type is Unrankable (FR-4), and what remains is a Raw Base price list rather than the product. The dependency is **accepted rather than worked around**. The alternative is a locally generated file, and a locally generated file cannot honestly source the two fields that matter. **What is verifiable about the project's state is the contract, not the project's progress** — which version a file must satisfy, stated below at *A second breaking contract revision* (FR-27). The contract is the fact to plan against. Any characterisation of how near completion the project is would be undated the moment someone wrote it.
- **Its first gate is a measurement, not a delivery.** Pool coverage across the Tracked List is measured before any view work begins, and the result binds a layout decision — **FR-4 states the bands normatively** (§10 BQ-3 carries the argument). A file that arrives is not the same as a file that covers enough. The measurement is **not spent once**: the measurement recurs on every regeneration, and the bands bind on every measurement (FR-4).
- **Its second gate is an open question, owned by the same project.** **§10 OQ-12** asks which single quantity the trade stat filter compares for a multi-`#` modifier, and whether the filter accepts a non-integer `min`/`max`. OQ-12 is blocking for **correctness**, not for building. A producer that picks the wrong quantity emits a file that validates and prices the wrong population, silently, across 53 of 63 item classes. A file that covers enough is not the same as a file whose edges mean what `sync` thinks they mean.
- **A second breaking contract revision has landed against a near-complete producer.** The contract moved 3.0.0 → **4.0.0**, so a 3.0.0 file in flight is **refused at load** (FR-27). To satisfy 4.0.0, that project must add two things: a **`sourceModifierId` on every entry**, and **group consistency** — a source row's exploded Stat Lines must carry the source row's full weight, and their per-`statId` sums must agree. This PRD is the document that the project's owner reads for the version number. That is why this PRD states the version number here rather than leaves the version number to the contract alone (AD-11, AD-29).
- **The contract has since moved to `4.1.0`, and the producer can schedule that move as work rather than treat it as a re-gate.** `4.1.0` is a **non-breaking minor**: a conforming `4.0.0` file is a conforming `4.1.0` file, `core` refuses only an unknown **major** (FR-27), and **the release dependency above is therefore not re-gated**. What `4.1.0` offers is the optional `statLineCounts` declaration. The producer **adopts `statLineCounts` when the producer is ready**. `statLineCounts` is effectively mandatory for any producer that handles multi-stat rows, because it is the only check standing behind a silently dropped Stat Line (FR-27, FR-29). `4.1.0` also makes the one-Cohort-per-group property a checked error rather than an assumed one, and writes down exactness rules that were always meant. Neither change refuses anything that already conformed (FR-27).
- **It recurs on GGG patch cadence**, alongside the Trade Catalogue refresh (FR-24). Neither the Weights File nor the Trade Catalogue is on the Chunk path. A stale Weights File degrades Provenance, and a stale catalogue degrades id validation and display text. Neither stale file breaks the app, and both surface as a reviewable diff.
- **`partial` is a recurring state, not a transitional one.** A patch introduces modifiers that the producer's source publishes unnamed. The producer must drop those rows, and must correctly declare the affected pools `partial` (FR-28). **Freshly scraped classes may therefore go Unrankable immediately after a patch, until the source becomes current.** This is a known operating cost of the decision to decline an anonymous-weight escape hatch. It is also why coverage is re-measured and published rather than measured once (FR-4, FR-25).

## 8. Success Metrics

Behavioural, not numeric. There is one user, and instrumenting the tool would be more work than the signal is worth. Each metric is therefore observed by the player's own recollection — the only instrument available.

**Primary**
- **SM-1: The trade site stays closed mid-session.** The player stops opening the trade site to price-check while mapping. Validates FR-1, FR-2, FR-8.
- **SM-2: The mental top-five goes away.** The player stops keeping a list of chase bases in his head. Validates FR-1, FR-6.
- **SM-3: A league start costs days, not weeks.** The list is useful within days of a reset rather than after weeks of relearning. Validates FR-31, FR-32.
- **SM-4: The list holds up against reality.** Chase decisions made from the list match what actually sells. The player judges this by noticing that his sales agree with the list, because the tool observes no sale (Risk R-1). Validates FR-21, FR-1.

**Secondary**
- **SM-5: The tool is still running in a year.** No credential expired. No server needed a patch. No maintenance task was skipped until something broke. Validates NFR-7, FR-20.
- **SM-6: Agents ship without a human unblocking them.** Development proceeds with tests passing offline and no live API in the loop. Validates NFR-1, NFR-2, NFR-4.

**Counter-metrics (do not optimise)**
- **SM-C1: Searches per full refresh.** A larger Tracked List makes the tool appear comprehensive and makes a daily refresh impossible: ~10,000 searches would need ~4× the ~2,400 searches a day the measured rate limit allows. Held at ~1,500 **searches**, which is the quantity the rate limit actually constrains. A count of entries would miss a curator who splits one entry into two bands to isolate a jackpot tier. That split costs a second search while the entry count looks unchanged (FR-14). Counterbalances SM-4.
- **SM-C2: Refresh frequency.** A faster refresh spends budget that retries, currency rates and a second recipe need, and prices are stable at daily resolution. Counterbalances SM-1.
- **SM-C3: Number of ranked Base Types shown.** A longer list is not a better one. Bounded by FR-5. Counterbalances SM-2.
- **SM-C4: Apparent confidence.** Rendering `uniform-prior` figures as cleanly as measured ones would make the tool feel more authoritative and be more dangerous. Counterbalances SM-4, and is why FR-10 and FR-11 exist.

## 9. Risks

R-1 through R-6 are carried from the brief, which named them and did not solve them. R-7 is carried from the architecture. v1 closes none of them.

- **R-1 — Listings are supply, not demand.** Every price is what someone asks, filtered to be plausible. **No sale is ever observed.** The manual loop that the tool replaces had a correction that the tool discards: the player actually sold things and learned the result. Mitigation is honesty only (FR-13), not correction.
- **R-2 — The tool cannot discover what it is not told to watch.** A Combination that becomes valuable mid-league stays invisible. The list needs periodic deliberate review rather than unattended running (FR-18). Re-seeding from community sources is the identified answer, and re-seeding is out of v1.
- **R-3 — `measured` weights will carry the same listing bias.** Community weight sources derive from parsing trade listings, which skew toward desirable and higher-tier modifiers. `provenance: "measured"` therefore means *measured by someone*, not *ground truth*, and the honesty apparatus must not imply otherwise. This bias also independently validates FR-21's ascending sort — the same reasoning poe2db uses when it parses lowest-value listings.
- **R-4 — Request budget is the permanent binding constraint.** Every Tracked Entry costs a search every refresh. Discipline is an operating requirement, not a one-time tuning exercise (SM-C1).
- **R-5 — Zero-listing Combinations are unresolvable in v1.** A Combination with no listings is either a jackpot or junk, and listings cannot distinguish the two cases. Segregation (FR-9) keeps such Combinations out of the ranking without resolving them.
- **R-6 — League and patch churn.** Resets wipe prices, and patches move the modifier data underneath. The tool is least useful at league start, which is when the knowledge is worth most. This is the central threat to the one-year horizon.
- **R-7 — Every endpoint the product depends on is undocumented.** GGG's developer documentation covers the OAuth API and makes no mention of the trade or `trade2` endpoints. Search, fetch and all four catalogue endpoints are therefore unsupported surface that happens to work, and they may change or close without notice or deprecation (AD-8). Nothing in the product can prevent that change. What the product does instead is make a break **loud and cheap**: one governed client (FR-20), committed fixtures whose re-record diff exposes a reshape (NFR-2), a committed catalogue whose refresh diff exposes a rename (FR-24), and no user-facing path that calls the API live (NFR-7). Recorded so that nobody rediscovers the risk as a surprise.

12. **OQ-12 — Which quantity does the trade stat filter compare for a multi-`#` modifier, and does it accept non-integer edges?** *"Adds # to # Lightning Damage"* rolls two numbers, and the filter compares one derived value — average, first, second, sum or span. Band edges must be expressed in **that quantity and no other**. FR-21 passes the band edges into the filter, and FR-29 counts the population that comes back (AD-28, AD-16). The evidence that the quantity is an average is indirect but real: a cell edge of `56.5` can only arise from averaging two integers, which puts the value lattice on half-integers. Two facts are unconfirmed — **which quantity**, and **whether the filter accepts a non-integer `min`/`max`**. A third question follows from those two facts: what `sync` should do with a half-integer edge if the filter turns out to be integer-only. `sync` could round the edge, and then silently reprice a different population. `sync` could reject the edge at load. `sync` could refuse the file. **Consequence of getting it wrong:** a file that validates and prices the wrong population, silently, across 53 of 63 item classes. Every price on those item classes is then corrupted, and nothing reports the corruption. **Blocking for correctness, not for building**: `contracts` can land ahead of the answer, because band edges are typed as `number` rather than `integer` precisely so the answer does not reshape the schema. **Owner: the weights scraper project**, by live verification against `trade2` search and `/data/stats`. OQ-12 is the second gate on the §7.3 release dependency. The first gate is FR-4's coverage measurement.

6. **OQ-6 — What fraction of the Tracked List returns `no-listings`?** The fraction is unknown until the first full refresh. If the fraction is large, the deferred coarser-fallback pricing (§7.2) moves from "held option" to "needed." **Revisit after first full refresh.**
7. **OQ-7 — Cold-start seeding.** The first Tracked List must be authored from the player's existing knowledge — the very knowledge the tool exists to supply. v1 has no mechanism beyond sitting down and writing the list. OQ-7 is not a blocker. It is the acknowledged price of the curation approach.

### Resolved by spine rev 2 — retained as the record of why the valuation model is shaped this way

These were defects in the **inherited** valuation model, surfaced by validation of this PRD. `AGENT-WORKFLOW.md`'s definition of done states that "any invariant the task discovered is raised against the spine rather than encoded locally". Under that definition, this document raised the three defects against the spine rather than patched the three defects in `core` — and **Architecture Spine revision 2 absorbed all three**. This document keeps the analysis because none of the analysis is visible in the amended decisions themselves. A reader who wants to know why a Modifier Reference must carry a ceiling, or why the pool is scoped before it is summed, will find the argument only here.

1. **BQ-1 — A floor-spanning probability is multiplied by a lowest-tier price.** AD-18 makes a Modifier Reference "a floor spanning tiers," summing T1 and T2 weight into one probability. AD-16 then prices that reference by sorting **ascending** and taking the median of the cheapest ten. Lower tiers are commoner and cheaper, so that median is essentially the **T2** price. EV therefore computes `P(T1 ∪ T2) × price(T2)`. The T1 jackpot is not merely understated. If the T2 price falls below the Payout Threshold, the entire entry truncates to zero and takes the jackpot mass with it — the exact outcome threshold-truncated EV exists to prevent. AD-17's overlap rule blocks the obvious workaround, because tracking T1 and T2 as separate nested floors is a validation error by construction. **Proposed amendment:** make `ModifierRef` a bounded band `(statId, valueMin, valueMax?)` rather than a floor. Tiers then become disjoint, AD-17's partition is restored, and each tier carries its own price. The Weights File already models bands this way. Trade stat filters accept both a min and a max, so the amendment is tractable. **Resolved:** AD-5 adopted the amendment. AD-5 now makes `valueMax` required everywhere with no open-top form, because an omitted ceiling is a floor by another name. The change is carried into AD-16's stat filters, AD-17's overlap predicate and AD-18's containment rule. Reflected in FR-16, FR-21 and FR-29.
2. **BQ-2 — The Eligible Pool has no item-level dimension.** Which modifiers can roll depends on item level. FR-22's own example has bow physical-damage T1 unable to roll below item level 82. AD-18 and the Weights File model exactly one pool per `(Base Type, slot)`. A probability normalised over that pool describes a population the search does not return, so both numerator and denominator are wrong for any entry whose floor sits below the top of its pool. **FR-22 does not create this defect** — AD-16 already filtered on "endgame item level" — but per-entry floors make the defect explicit and unavoidable. **Proposed amendment:** either add an `itemLevelMin` to each Weights File band, so `core` can scope the pool to the entry's floor, or declare a single canonical item level per Base Type and require all its entries to share that item level. The first amendment is correct. The second amendment is cheaper. **Resolved: both were adopted, because they fix different defects.** Weights File schema 2.0.0 — 4.1.0 at the current revision — requires `itemLevelMin` on every band, and AD-18 scopes both halves of the ratio by `itemLevelMin`. That fixes the denominator. AD-17 independently requires the crafted entries on one Base Type to share an Item Level Floor. That fixes the partition, because entries at different floors are crafts on differently-levelled populations, and their sum is not an expectation over anything. Reflected in FR-16, FR-22, FR-27 and FR-29.
3. **BQ-3 — Pool coverage is unmeasured, and it gates how much of v1 exists.** Every incomplete `(Base Type, slot)` declares `partial`, which makes that Base Type **Unrankable** (FR-4, FR-28). The Base Type is removed from the ordering rather than annotated, because an inflated denominator reorders the list and a provenance label does not change a sort. So the size of the ranked list is a direct function of the Weights File's coverage, and nobody has measured that coverage. If coverage is poor, v1's ranked list is a small fraction of what the player tracks, and the product does not work on day one. **Decision rule, so this does not sit open.** **FR-4** states the rule normatively and is the copy to build to. What follows is the argument for FR-4. Measure coverage *before* building the view. If **≥ 80%** of tracked Base Types resolve to `complete` pools in **both** slots, proceed as specified. If **50–80%**, proceed, but make FR-4's Unrankable group a first-class surface rather than a footer. If **< 50%**, the ranking premise fails, and the build escalates the failure rather than ships around it. **Resolved:** the decision rule was promoted verbatim into **AD-27**. AD-27 fixes the denominator as the Tracked List rather than the catalogue, and AD-27 is deliberately **source-agnostic**. AD-27 binds whatever produces the Weights File, and AD-27 survives a change of producer untouched. Reflected in FR-4. **Owner: build, first task, before any view work.** **Since narrowed twice, and this paragraph's arithmetic is superseded on both counts:** revision 3 narrowed the denominator to Base Types that actually need a pool, and gave the numerator a predicate that is not vacuously true of a Base Type absent from the file. Revision 4 then made the measurement recur on every regeneration rather than once. **FR-4 carries the current fraction and is the copy to build to.** What survives here is the argument for why an incomplete pool leaves the ordering rather than being labelled, and that argument is stated nowhere else.

### Raised against the spine by revision 2 — resolved by spine rev 3 and rev 4

Four items were found while reconciling this PRD against revision 2. Each item is a place where two decisions did not compose. Under `AGENT-WORKFLOW.md`'s definition of done, this document raised the four items against the spine rather than patched the four items locally, and **all four are now closed**. This document retains the analysis for the same reason the BQ record above is retained: none of the analysis survives in the amended decisions, and OQ-8's and OQ-10's arguments in particular exist nowhere else.

8. **OQ-8 — The `pinned` cap is denominated against the wrong quantity.** AD-26 capped the pinned set at *25% of AD-12's search ceiling*. That ceiling is ~1,500 searches across a **full refresh** of many Chunks, while `pinned` costs a search **every Chunk**. The two quantities do not compose into an inequality an implementer can write. **Resolved:** AD-26 re-denominates the cap against a Chunk, and enforces the cap at both ends — a load-time `tracked.json` inequality against `0.5 × config.minChunkSearches`, plus a runtime truncate-and-reserve with a named starvation record. The 25% figure is gone from the spine entirely. Reflected in FR-17, FR-19, FR-25 and FR-31.
9. **OQ-9 — The `unresolvable` retry bound is justified by a cost AD-6 removed.** AD-26 bounded retries so a patched-out modifier would not "consume the budget every chunk". AD-6 detects unresolvability offline against the committed catalogue before any request is issued, so retries are free until a human refreshes the catalogue. The bound was harmless. The bound's stated reason was not the real one. **Resolved:** AD-26's rationale was replaced rather than patched. AD-26 now defines when `sync` stamps `lastAttemptedAt`, states that a recovering id leaves `unresolvable` immediately, and narrows row 3 to the residue those two definitions leave — an entry whose id resolves but whose pricing attempt keeps failing. Reflected in FR-17 and §3.
10. **OQ-10 — AD-27's coverage denominator counts Base Types that need no pool.** The gate divided by every distinct `baseTypeId` in `data/tracked.json`. A Base Type tracked only as a Raw Base ranks with no Eligible Pool at all (FR-3, FR-4), and can never resolve to `complete`. Including such a Base Type depresses a fraction that binds a **layout decision**. **Resolved:** AD-27 supplies a `rankable(base)` predicate narrowing the denominator to Base Types carrying at least one crafted, non-`pruned` entry. AD-27 also supplies, beyond what OQ-10 asked, a `covered(base)` predicate fixing the **numerator**, which was vacuously true of a Base Type absent from the file entirely. Reflected in FR-4.
11. **OQ-11 — The spine still writes `valueMax?` in two places.** AD-5 makes `valueMax` required everywhere with no open-top form. AD-11 and AD-18 still spelled the band `(statId, valueMin, valueMax?, …)`, and AD-18 still said "an omitted `ref.valueMax` is unbounded above". **Resolved twice over:** revision 3 removed both spellings, and revision 4 rewrote both entries again. AD-11 now gives two kind-specific shapes, and AD-18 now says there is no open-top form to handle, because `contracts` rejects an open-top form at the schema. **The closure was syntactic, not semantic.** Requiring a ceiling to be *present* does not stop a curator writing `valueMax: 9999`. AD-18's edge-alignment rule closes that residue separately, and FR-29 now states the rule. Retiring OQ-11 does not finish the ceiling question. FR-29 finishes it.
