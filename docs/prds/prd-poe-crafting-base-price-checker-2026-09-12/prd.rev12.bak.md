# PRD: PoE2 Crafting Base Price Checker

## 0. Document Purpose

This PRD is the requirements layer for a single-player tool. The tool answers one question — *is this base worth picking up?* This PRD is written for the agents that will build the tool, and for the workflows that will turn this PRD into epics and stories. This PRD is deliberately **downstream of a settled architecture**. `ARCHITECTURE-SPINE.md` is final at revision 10, and the spine's decisions are **inherited, not re-decided**. The live set is **AD-0 and nineteen of the original twenty-nine**, and every `(AD-n)` citation below names one of those live ids.

**An amended decision kept its id for nine revisions, and revision 10 broke that rule once, deliberately.** Through revision 9 the content of many decisions changed in place while the id did not, so a citation stayed good across an amendment (§10 OQ-15 lists which decisions each early round amended; git history carries the rest). Revision 10's authorised simplification pass then **merged ten decisions into their neighbours and retired their ids** — AD-2, AD-6, AD-14, AD-18, AD-21, AD-22, AD-23, AD-26, AD-28 and AD-29 no longer resolve. That break was taken while nothing had been built, which is the only condition under which it is cheap, and **no id is ever reused**. Revision 11 of this document retargets every affected citation onto the absorbing decision; the spine's *Retired AD map* is the authority, and §10's historical records are annotated rather than rewritten, because an id there names what a past revision decided.

**Revision 12 closes three defects a validation gate found in revision 11, and adds no requirement.** No FR is added, removed or renumbered — 33 remains the total — and §7.1 *In Scope* is unchanged. (1) Five sites named FR-17 as the binding statement of the `pinned` cap and its truncation, and FR-17 stated neither; AD-7 delegates both to `IMPLEMENTATION-NOTES.md` §6, so every pointer now names §6 and FR-17's dangling "the cap below" is resolved. That was also an **AD-0 inversion** — this document cannot bind what a companion section binds. (2) FR-29 stated a bolded "two cross-file checks now, not three" as though it were a system-wide register; AD-17 defines **four** and AD-12 runs all four as one gate, so FR-29 and FR-16 now each say which two are theirs, FR-14 states the gate, and FR-16 gains AD-17's universal quantifier on kind agreement. (3) FR-21 and FR-29 generalised AD-11's "sits at the top of the band by construction", which AD-11 claims **only** of a tier excluded at the band's ceiling; the qualifier is restored and the opposite case — a tier intruding at the band's floor, which the ascending sort prices rather than blunts — is stated, with §10 OQ-21 widened to carry it. That third item is BQ-1's shape reachable through a band FR-22 instructs the curator to write, which is why it is corrected rather than deferred. The validation report and its four reviewer files sit beside this document in the run folder.

AD-25 (the committed Trade Catalogue), AD-27 (the pool-coverage gate), AD-11 (the consumed weights file, which absorbed value-axis handling and per-modifier Stat Lines), AD-17 (valuation, which absorbed weight aggregation) and AD-7 (the chunk runner, which absorbed the Refresh Rotation) bear most directly on the requirements below.

**One companion is now binding alongside the Weights File schema.** Under **AD-0**, a companion section an AD delegates to carries the full force of the delegating AD, which makes `IMPLEMENTATION-NOTES.md` binding — it holds the arithmetic revision 10 moved out of the ADs. This PRD cites that file by section wherever a requirement here leans on material that now lives there.

A requirement here sometimes restates something the spine governs, because that thing is visible to the player and therefore belongs in a requirements document; the citation `(AD-n)` points at the decision and at its rationale, which this document does not re-argue.

This document is Glossary-anchored. §3 defines every domain noun, and §4's features and FRs use those terms verbatim. FRs are numbered globally (FR-1 … FR-33), so the FR numbers stay stable if features are reorganised — a removed or fully merged FR leaves a numbering gap rather than being renumbered. Inferences carry inline `[ASSUMPTION]` tags, and §11 indexes those inferences. `[NOTE FOR PM]` callouts flag items worth revisiting, and this document deliberately does not index those callouts — the callouts are prompts, not commitments.

> **This PRD is buildable, and validation's defects were all in the *inherited* valuation model, not in the requirements written here.** Three early defects — a floor-spanning probability priced at its cheapest tier, a pool with no item-level dimension, and unmeasured pool coverage — were absorbed into AD-5, AD-16, AD-17, AD-27 and the Weights File schema; §10's *resolved by spine rev 2* record keeps the analysis, because it is the only place that explains why the valuation model has the shape it has. Eight further amendment rounds followed, each reconciling this PRD, the spine, or the Weights File's external producer with one another; every round's outcome is folded into the current FR and glossary text, and §10 retains a one-line retirement record per round rather than the argument (see git history for the argument behind any of them).
>
> **The current Weights File contract is `WEIGHTS-FILE-SCHEMA.md` `5.0.0`, effective 2026-09-18 — the third breaking revision, and the first that asks the producer to build *less*.** `5.0.0` withdraws the producer's value-decomposition machinery entirely (Value Cells, `cohortTotals`, the per-`statId` group-consistency check, `statLineCounts`, the `kind` field, band non-overlap, the two-cohort bound and the six exactness rules) and instead reports poe2db's tier weights and stat ranges as published, plus trade-API identity, and nothing else. Entries are tiers again, not cells: one entry per source row, its Stat Lines nested as `lines[]` with `ranges` verbatim, and a per-tier `weightSource: "published" | "absent"`. Tier overlap is left in the raw data; the consumer-side rule for it — **whole-tier containment** — is stated normatively in FR-29 and in *Eligible Pool* (§3), which also carry its costs and the rejected alternatives. Provenance collapsed from four values to three in the same round, because `modelled-split` had exactly one source (the now-withdrawn decomposition) and is unreachable (§3 *Provenance*). **33 FRs remain; none is added, removed or renumbered by this contract change** (FR-29 is retitled from "…by cell" to "…by tier", its number unchanged), and **§7.1 In Scope is unchanged**. A new contract-level question this change raised — whether a Stat Line's derived edge is always exactly representable — is open as **§10 OQ-19**.
>
> **The one live release gate is data, not architecture: the external Weights File, with no fallback (§7.3, FR-30).** Until a conforming file exists, every crafted Base Type is Unrankable. Pool coverage must be measured before any view work and re-measured on every regeneration of the file, because the fraction binds a layout decision and moves across a game patch (FR-4, AD-27). One further question on that dependency is open by design and owned outside this repository: **§10 OQ-12**, which single quantity the trade stat filter compares for a multi-`#` modifier. Both open questions are blocking for correctness, not for building.
>
> **Revision 11 adds two open questions that are *not* release-dependency gates, and that distinction is the point of stating them here.** OQ-12 and OQ-19 gate the external file. **§10 OQ-20** (what `query.status` must carry, and whether it duplicates the `sale_type` rule FR-21 already requires) is `sync`'s builder's, and blocks a correct first price rather than the contract. **§10 OQ-21** (how far whole-tier containment can understate) is the spine's, with the player, and blocks *trusting the ordering* rather than producing one. OQ-21 also withdraws a claim revision 10 made: FR-29 asserted that two mitigations **bounded** the containment understatement, and that assertion is false — neither is a bound, and §7.2's deferred measurement is re-framed accordingly.

## 1. Vision

Farming crafting bases is among the most reliable ways to make currency in Path of Exile 2's endgame, and memory gates the method entirely. The method only pays once the player knows which Base Types to pick up and which modifier combinations sell. The player buys that knowledge with weeks of picking up everything, crafting on it, price-checking the result, and slowly committing the answers to memory. League resets destroy that learned knowledge three or four times a year, at exactly the moment the knowledge is worth the most.

This tool replaces the memorisation with a ranked list. A background sync prices a curated set of base-and-modifier combinations against the official trade API. A static web view ranks Base Types by **expected payout per craft**. The view counts only outcomes above a threshold that the player sets, and subtracts the cost of the craft, which the player pays on every attempt including the failures. The player reads the list before a play session, or whenever the economy is worth a look. The list is precomputed, so the list never blocks on a live API call.

The ranking is not "most expensive base," and everything else in the system exists to make that distinction hold. A Base Type with one jackpot combination and a Base Type with many moderate combinations swap places as the threshold moves. For that reason the threshold is a dial the player turns, rather than a constant that someone compiled in. The sync, the schemas and the view all exist to make that one number right, and to make that number honest about what it rests on.

## 2. Target User

### 2.1 Jobs To Be Done

- **Decide, at a glance, what to pick up this week.** Functional: convert a live market into a short ordered list of Base Types worth inventory space.
- **Stop paying the memorisation tax.** Emotional: the relief of not holding a top-five list in your head, and of not losing that list at every league start.
- **Know when the answer has gone stale.** The player must be able to tell a figure resting on real measured weights from a figure resting on a uniform placeholder, and a row priced an hour ago from a row priced yesterday. If the tool does not tell the player, the player will trust the placeholder six months later.
- **Spend time playing, not crafting.** Contextual: the binding constraint is the player's own time. Outcomes below the player's threshold are worth nothing to the player, because that much currency turns up simply from playing. Such outcomes must therefore contribute nothing to the ranking.
- **Keep a tool alive for a year without the tool becoming a second job.** The maintenance surface is a first-class concern: no credentials to rot, no server to patch, no account system.

### 2.2 Non-Users (v1)

- **Anyone who is not the author.** The author publishes the tool openly but does not advertise it. Friends with the link and passers-by are welcome and explicitly not courted — no growth goal, no monetisation, no advertising.
- **Players wanting advice on an item already in hand.** The augment decision is excluded by design (§6).
- **Rare-item crafters.** Magic bases only: at most one prefix and one suffix.
- **Anyone needing their own settings.** No account, no per-user persistence, no sharing (AD-15). The tool may assume one player's thresholds, one player's playstyle, and one player's judgment about when to trust the tool. That freedom is load-bearing.

### 2.3 Key User Journeys

There is a single operator, a single role, no authentication and no multi-device handoff. These journeys are therefore written in the template's lighter form.

- **UJ-1. The pre-session read.** The player is about to map for two hours. The player opens the view, glances at the top five Base Types under his current threshold, notes the two or three Chase Combinations on each Base Type, and closes the view. He picks up accordingly for the rest of the session.
- **UJ-2. The threshold turn.** The player is now richer than at league start. He types a new threshold over the old one, from a quarter of a Divine to one Divine. The list reorders immediately — steady moderate Base Types fall away, jackpot Base Types rise — and he re-reads the new top five. **The control is a number input rather than a slider** (UX memlog 36/37). The player gives up the continuous sweep in which the list visibly reorders as the value moves, and gains exactness and masthead width. FR-6's requirement that the list reorder immediately is unaffected, and is satisfied by re-ranking on a valid parse of the input rather than on commit.
- **UJ-3. The drill-down.** The player is unsure why an unfamiliar Base Type ranks third. He expands that Base Type and reads the full tracked Combination list: which Combinations are priced, at what price, how old each price is, and which Combinations returned no listings.
- **UJ-4. The trust check.** The player notices a Base Type that ranks suspiciously high. He sees that the price of that Base Type was observed three days ago, and that the whole ranking is flagged as resting on the uniform prior. He discounts that Base Type rather than acting on it.
- **UJ-5. The curation pass.** The player reviews deliberately after a few weeks. He sees three Combinations that have returned no listings all league, and one Combination flagged unresolvable since the last patch. He opens `data/tracked.json`, tombstones the dead Combinations with a reason, pins one Combination he wants watched closely, and commits. The next sync run reflects the edit.
- **UJ-6. The league reset.** A new league starts. The player edits the active league in `data/config.json` and commits. The ranking goes honestly empty rather than quietly serving last league's numbers, and the ranking refills over the following day.

## 3. Glossary

Downstream readers and workflows use these terms exactly. A synonym introduced anywhere is a discipline violation.

- **Base Type** — a specific item base in PoE2. The trade API's own `baseTypeId` identifies a Base Type. This product never re-encodes `baseTypeId` into an internal id (AD-5). **The rule governs ids the trade API exposes.** The spine's conventions carry one explicit carve-out. **`sourceModifierId`** is producer-assigned. `sourceModifierId` names a thing the trade API has no concept of at all. `sourceModifierId` therefore re-encodes nothing, and the flat-ids rule does not forbid `sourceModifierId` (AD-11).
- **Modifier Reference** — the canonical identity of a **Stat Line**. A Modifier Reference is one of exactly two kinds. A `kind` field discriminates the two kinds (AD-5). **A Modifier Reference names a Stat Line, not a game modifier.** The thing the game actually draws is the **Source Modifier**. A Source Modifier lives on the Weights File and never on a Modifier Reference. A curator can filter only on what the trade API exposes, and the trade API exposes Stat Lines. For this reason `sourceModifierId` is never part of a Modifier Reference, a Tracked Entry, or a Tracked Entry's canonical key (AD-5, AD-11). A **`banded`** reference is a trade API `statId` paired with an inclusive, closed **value band** `(valueMin, valueMax)`. A **`valueless`** reference is a `statId` with **no edges at all**, for a modifier that rolls no number — *"Loads an additional bolt"*. A valueless reference is **not** a degenerate band. A sentinel pair such as `1/1` would pass every containment and edge-alignment check. That same sentinel pair would also make FR-21 emit a `min`/`max` filter for a stat that has no value. A valueless reference still carries `weight` and `itemLevelMin`, and a valueless reference still counts toward pool completeness. The trade API has no tier concept. "Tier 1" and "tier 2" exist in this product only as bands. On a **`banded`** reference **`valueMax` is required, always**. An omitted ceiling is a floor by another name, and a floor spans tiers. A floor that spans tiers is the defect §10 BQ-1 removed. A requirement that `valueMax` is *present* is not sufficient. A `banded` reference's edges must also **align to edges the Weights File's tier intervals actually reach**. Otherwise a sentinel ceiling reproduces the defect and still satisfies every schema (FR-29).
- **Tracked Entry** — one unit of the curated workload. A Tracked Entry holds a Base Type, an optional prefix Modifier Reference, an optional suffix Modifier Reference, a declared **Item Level Floor**, and a **Curation Status**. Each present Modifier Reference carries, beside its band, a declared **`acceptedTier`** label (§3 *Accepted Tier*, FR-22). An entry with both affixes absent is a **Raw Base**.
- **Raw Base** — a Tracked Entry with no affixes. A Raw Base represents an uncrafted white base at item level 82. A Raw Base is the one case where the sale of the base may beat crafting on the base.
- **Combination** — the outcome a Tracked Entry describes: this Base Type carrying this prefix and this suffix. A Raw Base describes the degenerate Combination of no affixes. The Payout Threshold applies to the degenerate Combination exactly as to any other Combination (FR-3).
- **Chase Combination** — one of the Combinations on a Base Type that contributes most to the Base Type's EV. The collapsed ranked row shows the Chase Combination. The player then knows what to look for without an expansion of the row (FR-2).
- **Tracked List** — the complete curated set of Tracked Entries, held in `data/tracked.json`. The Tracked List is at the same time what the tool watches and the tool's entire request budget (FR-14).
- **Item Level Floor** — the minimum item level a Tracked Entry's search accepts. The curator declares the Item Level Floor per entry. The Item Level Floor comes from the item levels at which the entry's affixes' **Accepted Tiers** become available (FR-22). The Item Level Floor is also a valuation input, because the Item Level Floor scopes the Eligible Pool (FR-29). The crafted entries on one Base Type must share one Item Level Floor. A Raw Base at 82 is exempt (AD-17, FR-16).
- **Accepted Tier** — for a modifier, the highest **tier, or run of adjacent tiers,** worth chasing. The Accepted Tier is tier 1 normally. The Accepted Tier is tier 2 where tier 1 requires item level 81 or 82 and is therefore too rare to chase. The mechanical expression of the Accepted Tier depends on the modifier (AD-11, FR-22). For a modifier whose text carries **one** `#`, tier and band coincide, and the Accepted Tier is the Modifier Reference's **band** — both edges, not a floor. For a modifier carrying **more than one** `#`, tiers overlap in value space and the trade filter compares one derived value, so the curator writes a band that **contains a whole tier, or a run of whole adjacent tiers** — never a band that clips one (§3 *Eligible Pool*, FR-22, FR-29). **The Accepted Tier is also a declared label, and not only a curation act.** The curator writes `acceptedTier` beside the Modifier Reference's band, in the same authoring act that chooses the band (AD-5). The label is a **string** — `"T1"`, or `"T1–T2"` where the curator accepted a run of adjacent tiers (AD-11, FR-22). **The label is display-only.** `core` and `sync` never read it, never branch on it and never validate it against a band. `web` prints it, and `web` is its only consumer. **Three properties are load-bearing, and each closes a reading a builder would otherwise reach for.** First, the label is **never derived from the band**, even where the band now names exactly one tier's own interval. A derivation would still be wrong the moment a curator accepts a run of tiers, so the field stays hand-authored uniformly rather than derived in the single-tier case and hand-written in the multi-tier one — a rule with two paths is a rule two builders will implement differently. Second, the label is **never joined to the Weights File's own tier data**, even though `5.0.0`'s per-tier entries make that join newly *possible* in the single-tier case — an entry now names exactly one tier, so a curator who wrote exactly `"T1"` could technically resolve it against the file. The prohibition stands anyway, for the identical run-of-tiers reason as before: a run of adjacent tiers has no single tier identity to join against, and a rule that worked only for the single-tier case would be a silent trap for the multi-tier one. Third, the label is **never part of a Tracked Entry's canonical key** (AD-5, and the spine's Consistency Conventions; the key's encoding is `IMPLEMENTATION-NOTES.md` §4.1, binding under AD-0). Two entries that differ only in their label are the same entry, and a key that included the label would make a curator's relabelling orphan an entry's price history. **What the label buys, and what it costs.** It buys a Combination that reads as the comparison the player actually makes — the player operates on tiers, and does not carry value spreads in their head — so the ranked row prints `T1 Cold Res · T1 Mana` rather than `+35% Cold Res · +180 Mana`. It costs one more hand-authored field per affix, and a curator who omits it gets a visibly marked fallback rather than a wrong label (FR-22).
- **Curation Status** — exactly one of `active`, `pinned` or `pruned` (AD-12, FR-17). A Chunk selects a `pinned` entry **first in every Chunk, and refreshes that entry every Chunk the Chunk can afford it**. A `pinned` entry never waits its turn in the `active` ordering. The tool caps `pinned` entries at load. The tool truncates `pinned` entries for a Chunk whose discovered allowance cannot also fund the rotation below the `pinned` entries. **AD-7 delegates both the cap and the truncation to `IMPLEMENTATION-NOTES.md` §6, which binds under AD-0, and FR-19 carries that citation.** This entry, FR-15 and FR-17 are summaries of §6. A `pruned` entry is a tombstone that carries the entry's reason. The sync workload excludes a `pruned` entry, and the ranking excludes a `pruned` entry. Curation Status is independent of Price State. An entry is `active` *and* `priced`, or `active` *and* `unresolvable`.
- **Refresh Rotation** — the defined, deterministic order in which a Chunk selects entries to refresh. A full pass takes many Chunks. The order is currencies, then `pinned`, then `active` by oldest `lastAttemptedAt`, then bounded `unresolvable` retries, never `pruned` (AD-7, FR-17).
- **Workload** — the set of Tracked Entries and currencies a Chunk may spend requests on, held in two declared files. The Workload covers two of the four enumerated request sources. The other two sources are the per-run leagues check and the catalogue refresh. Those two sources are fixed overheads rather than workload (FR-14).
- **Price Observation** — an observed price for a Tracked Entry. A Price Observation is normalised to Divine. A Price Observation is stamped with the observation time, the league, and the exchange observation used (AD-16, AD-19, AD-20). **A Price Observation exists only where there is an observation**, so `no-listings` and `unresolvable` entries have none. A fact that must survive on an entry in every Price State therefore belongs on the **Dataset entry** alongside `lastAttemptedAt`, and never on a Price Observation — `lastSearchId` is the case in point (FR-21).
- **Price State** — exactly one of `priced`, `no-listings`, `not-yet-synced`, or `unresolvable`. Absence is never `0`, `null`, or a missing key (AD-9). `not-yet-synced` carries a **reason** that distinguishes the three causes of `not-yet-synced` — `never-synced`, `league-mismatch` and `no-exchange-rate`. The four states are AD-9's. **The reason enum is this PRD's own addition.** No architecture decision requires the reason enum. The reason enum exists because one state that covers three unrelated causes would defeat the point of a distinction between states at all (FR-9).
- **`lastAttemptedAt`** — when `sync` last **issued a request** for a Tracked Entry, whatever the outcome. **Offline work never stamps `lastAttemptedAt`** — FR-24's catalogue validation above all, which runs over every tracked id on every run and costs nothing. If any evaluation stamped `lastAttemptedAt`, every entry's timestamp would advance on every run. FR-17's oldest-first ordering would then flatten to a tie across the whole Tracked List, and the Refresh Rotation would silently degrade to canonical key order (AD-9, AD-7). `lastAttemptedAt` is reachable in **all four** Price States. `lastAttemptedAt` is distinct from a Price Observation's `observedAt`, which exists only where there is an observation. A `no-listings` row therefore has an age even though the row has no observation. `lastAttemptedAt` is **absent on an entry no request has ever been issued for** — the `never-synced` case. That entry is the one row with no age at all, and the absence is the reason FR-17 treats such an entry as infinitely old (AD-9, FR-12, FR-17).
- **Divine** — the single currency denomination that crosses every boundary. All prices, all Craft Costs and the Payout Threshold are denominated in Divine (AD-17 for the threshold and the ranking terms, AD-20 for the unit itself).
- **Payout Threshold** — the player-set gross price, in Divine, below which a Combination's outcome contributes nothing to a ranking.
- **Craft Recipe** — a named crafting currency composition (v1: one perfect transmute plus one perfect augment). The tool computes a Craft Recipe's **Craft Cost** from synced exchange rates.
- **Craft Cost** — the Divine cost of one Craft Recipe attempt. The player pays the Craft Cost on every attempt, including failures.
- **Expected Value (EV)** — the ranking figure: the threshold-truncated expected payout of a Base Type under a Craft Recipe, less Craft Cost (FR-1, AD-17).
- **Stat Line** — one trade-API-visible stat that a Source Modifier publishes, held in a Modifier Weight entry's `lines`, each carrying a `statId` (or `null`, where the producer resolved none) and its `ranges` verbatim. A Source Modifier publishes **one or more** Stat Lines, each with its own value range. **All of a modifier's Stat Lines roll together as a unit**, because the game rolls the modifier as one draw. A Modifier Reference names a **Stat Line**, never a Source Modifier. A Stat Line is what the trade API exposes, and therefore a Stat Line is all a curator can filter on (AD-5, AD-11). **Pool completeness has two halves, and both are the producer's obligation**: every rollable tier is present, and every one of that tier's lines is present. A `statId: null` line does not make a pool `partial`, and is never a reason to treat one as though it did — it is data, not a file error (FR-28).
- **Modifier Weight** — one file entry: one tier of one modifier, within a Base Type and affix slot. Contract `5.0.0` reports the tier's weight **once**, carried directly rather than distributed across any value partition. The entry holds `sourceModifierId`, `itemLevelMin`, `weight`, `weightSource` and `lines` — the tier's Stat Lines nested inside the entry, each line carrying its own `statId` (or `null`, where the producer resolved none) and its `ranges` **verbatim**, exactly as poe2db published them. **An entry and a source row are the same thing**, and tiers **overlap** in value space rather than partition it — the overlap is reported, and this contract does not resolve it (§3 *Eligible Pool*, AD-11). A Modifier Weight is consumed from the **Weights File** and never produced by this app (AD-11, AD-5).
- **Source Modifier** — one game modifier as the game actually rolls the modifier: a single source row that carries **one spawn weight**, and that may publish **several distinct trade stats at once**, always together, because the game rolls the modifier as a unit. **Under contract `5.0.0` a Source Modifier *is* a Modifier Weight entry** — the producer performs no split, no aggregation and no derivation, and emits the row as scraped, its several Stat Lines nested as that one entry's `lines`. The id names **one source row — one *tier* of one modifier, never a modifier family** — and is **producer-assigned, opaque, and required on every entry**. The id is stable within one `(Base Type, slot)`. The tool never validates the id against the Trade Catalogue, because the trade API has no concept of the thing the id names. The id is **never part of a Modifier Reference, a Tracked Entry, or a Tracked Entry's canonical key.** In **valuation** `core` never reads the id at all — the denominator is now a plain sum over entries (§3 *Eligible Pool*, FR-29). `core` reads the id only at **load**, for the duplicate-entry check FR-27 specifies (AD-11, AD-17).
- **Weights File** — the schema-conformant file of Modifier Weights that `WEIGHTS-FILE-SCHEMA.md` defines, at contract version **`5.0.0`**. An **external project** produces the Weights File. The Weights File is a **v1 prerequisite**, not an enrichment: the Weights File is the only source of pool membership, tier value ranges and item-level availability, and the trade API exposes none of those three (AD-11, AD-25, FR-30). The Weights File declares a **`gamePatch`** — the GGG patch the file's weights describe. **The operator asserts `gamePatch` at runtime.** The tool never derives `gamePatch` and never defaults `gamePatch`. Neither the producer's sources nor the trade API states a patch version. A producer therefore refuses to run without a patch version, rather than emitting a default that would propagate silently past the one person who could have caught the default. `core` does not parse `gamePatch` and must not branch on `gamePatch`. A missing or empty `gamePatch` value is a hard file error (FR-27). `web` shows `gamePatch` beside `producer.id` and `producer.generatedAt`, so a file left behind by a patch is visible as such (AD-11, FR-10).
- **Trade Catalogue** — the committed mirror of the trade API's own data endpoints (`data/catalogue/*.json`). An explicit command refreshes the Trade Catalogue at patch cadence. The Trade Catalogue is an **identity and validation authority only** — base types, stat ids and display text, currency ids and icons. The Trade Catalogue contributes nothing to the Eligible Pool (AD-25).
- **Eligible Pool** — the complete set of Modifier Weight entries that can roll in one `(Base Type, slot)` at **any** item level. Each entry carries the `itemLevelMin` of the tier whose weight the entry holds. **Two entries may legitimately cover one value interval**, and that coincidence is now **expected rather than merely tolerated**, because contract `5.0.0` leaves tier overlap in the raw data (AD-11). `core` scopes the pool to a Tracked Entry's Item Level Floor before `core` normalises anything. The scoped pool is the **domain the tool computes the denominator over**, not the denominator itself. **The denominator is a plain sum over entries** — one entry, one tier, one weight, counted once (AD-17, AD-11, FR-29). **A partly-covered entry is in the denominator and not the numerator**: whole-tier containment means a tier only partly covered by a tracked band contributes nothing to that band's numerator, while its weight still counts in the denominator like any other entry in scope (§3 *Provenance*, FR-29). A pool declared anything other than `complete` makes the pool's Base Type **Unrankable** (AD-17).
- **Provenance** — what a derived figure rests on. Provenance is a **three-value total order**, weakest first (AD-10):

  | Rank | Provenance | Means | Arises from |
  | --- | --- | --- | --- |
  | 0 | `absent` | not an estimate at all — an upper bound | a `partial` pool, and nowhere else (FR-28) |
  | 1 | `uniform-prior` | someone invented the weight | `weightSource: "absent"`, or a bootstrap file |
  | 2 | `measured` | someone measured the weight — never ground truth (R-3) | `weightSource: "published"` |

  The ranks are explicit, so that no reader infers "weakest" from an enum's declaration order. `WEIGHTS-FILE-SCHEMA.md` states the same order the same way round, deliberately, so that two builders cannot rank the values differently. `absent` is a `core`-side value that must never appear in a file. Every derived figure carries the *weakest* Provenance and the *oldest* timestamp of the figure's inputs — **every Provenance now propagates from every input**, with no exception (FR-10). Revision 9's fourth value, `modelled-split`, had exactly one source — the producer's decomposition — and is unreachable now that the decomposition is gone; it was retired rather than merged into `uniform-prior`, because merging it would have understated a measured weight. **If consumer-side pro-rating is ever adopted, this value must return in the same change**, or the product would carry an unlabelled model inside every ranked number.
- **`weightSource`** — a per-tier field on a Modifier Weight entry, `"published" | "absent"`, that `core` reads for **exactly one purpose**: deriving that entry's Provenance (`"published"` → `measured`, `"absent"` → `uniform-prior`; §3 *Provenance*, FR-10). The mapping is stated once and explicitly, because `"absent"` reads as an invitation to map straight to Provenance `absent`, and that reading is wrong — `weightSource: "absent"` means the producer invented the weight, not that the weight is missing. `web` never prints `weightSource`'s own words on screen, because `weightSource: "absent"` beside Provenance `absent` would collide in front of the player and read as the same fact twice or as a contradiction.
- **Unrankable** — a Base Type that the tool excludes from the ordering, because the Base Type's Eligible Pool is incomplete or absent. The tool returns an Unrankable Base Type in a separate group with the reason (AD-17).
- **Chunk** — one bounded, resumable unit of sync work. A Chunk ends at whichever of three limits runs out first: the remaining search allowance, the remaining fetch allowance, or the workload remainder (AD-7). A Chunk's size is **discovered at runtime** and never configured. `data/config.json`'s **`minChunkSearches`** is not a Chunk bound. `minChunkSearches` is a **declared yardstick** read at exactly one place — the load-time `pinned` cap of `IMPLEMENTATION-NOTES.md` §6, which `sync` evaluates (FR-19, FR-31, AD-7).
- **Dataset** — the published snapshot of the latest Price Observation per Tracked Entry (AD-19).
- **Sync Report** — the published structured record of a sync run. A Sync Report holds the requests consumed **per declared source** (FR-14), the unresolvable entries, the **entries not reached in this Chunk** — this PRD's own field, required by no architecture decision (FR-25) — the **pinned-starvation records**, the measured pool-coverage fraction (FR-4), and the date of the last tracked-list edit (AD-12, AD-7, AD-27).

## 4. Features

### 4.1 The Ranked Base List

**Description.** The Ranked Base List is the first screen of the product. In most sessions the player reads nothing else. The Ranked Base List is one ordered list of Base Types, most profitable first. Each row carries the Base Type's EV, the Combinations worth chasing on that Base Type, and the Provenance that the EV rests on. The browser computes the ranking on every input change (AD-4). Nothing in the published Dataset carries a rank, a score or an ordering. A precomputed ranking would make the Payout Threshold reorder nothing until the next sync. The Payout Threshold is the product's central control, and a control that reorders nothing does not do what the product shows it to do. The Ranked Base List realises UJ-1, UJ-2, UJ-3.

**Functional Requirements:**

#### FR-1: Rank Base Types by threshold-truncated expected value

The player sees Base Types ordered by EV. The order is computed under the active Craft Recipe and the current Payout Threshold. Realises UJ-1.

**Consequences (testable):**
- For a crafted Base Type, `EV = ( Σ P(combo) × price(combo) over Combinations that are priced and whose price ≥ Payout Threshold ) − Craft Cost` (AD-17).
- The Payout Threshold compares against a Combination's **gross** price, never its price net of Craft Cost.
- `core` subtracts Craft Cost **once** from the summed expected payout, never per Combination.
- A Combination whose Price State is not `priced` contributes nothing — not zero, not a default (AD-9).
- A Combination with Curation Status `pruned` is not a summand. Pruning therefore changes the ranking, and pruning is not a no-op (AD-12).
- `core` computes every ranking term. The view computes none of the ranking terms (AD-4).
- `P(combo)` and `price(combo)` describe the **same population**, and the sum is only meaningful because both describe the same population. A Modifier Reference is a bounded band (AD-5), so the tier that is weighted is the tier that is priced. Both halves of the probability are scoped to the entry's Item Level Floor (AD-17, FR-29).
- **The partition this sum rests on breaks in two non-obvious ways, not one.** The familiar way is intersecting bands. The second way is **co-occurring Stat Lines**: two Modifier References on *different* `statId`s, with no bands intersecting at all, both satisfied by a single item because the two Modifier References name two Stat Lines of one Source Modifier (§3). FR-16 rejects both ways at load. FR-1 names the second way as well as FR-16 does, because **this** is the FR that asserts the `ΣP ≤ 1` premise that those rejections exist to protect (AD-17, AD-11).

#### FR-2: Show chase Combinations on each collapsed row

Each ranked row names the Combinations most worth chasing on that Base Type. The player does not expand the row to read them. Realises UJ-1.

**Consequences (testable):**
- Chase Combinations are ordered by contribution to EV — `P(combo) × price(combo)` — not by raw price. `[ASSUMPTION: the brief says "chase modifiers" without defining the ordering. An ordering by price alone would advertise a Combination that the player will essentially never roll.]`
- The collapsed row shows **at most three** Chase Combinations. `[ASSUMPTION: the brief says "the modifier combinations to look for", which is plural and unbounded. Three is the count that fits a scannable row, and three matches the "top five bases" reading pattern of UJ-1.]`
- Only Combinations at or above the Payout Threshold appear. The set therefore changes when the player changes the Payout Threshold.
- A Base Type whose priced Combinations are all below the Payout Threshold shows no Chase Combination. The EV of that Base Type is negative by its Craft Cost.

#### FR-3: Rank Raw Bases on a separate branch, visibly labelled

`core` ranks uncrafted item-level-82 white Base Types in the same list. `core` values these Base Types differently, and the view labels them as uncrafted.

**Consequences (testable):**
- A Raw Base's EV is its observed price with zero Craft Cost. A Raw Base is never a summand in any crafted Base Type's sum (AD-17).
- **The Payout Threshold applies to a Raw Base exactly as the Payout Threshold applies to a crafted Combination.** A Raw Base priced below the Payout Threshold is truncated out of the list, and is not ranked at its price. Without this rule, the Payout Threshold would silently govern only one of the two branches.
- The view renders a Raw Base distinguishably from a crafted Base Type. Colour alone does not carry that distinction (NFR-10).
- A Raw Base's search uses `normal` rarity (AD-16) and item level 82, which is the brief's white-base scope. `[ASSUMPTION: 82 is the effective item level cap for these bases, so a floor of 82 and "exactly 82" are the same filter. If bases above 82 exist, this needs a ceiling, not a floor.]`

#### FR-4: Surface Unrankable Base Types outside the ordering

Base Types that `core` cannot rank honestly appear in a separate group with the reason. `core` does not drop these Base Types silently, and `core` does not rank them anyway.

**Consequences (testable):**
- A Base Type whose Eligible Pool for either slot is not `complete` is Unrankable, and a Base Type absent from the Weights File entirely is Unrankable. `core` excludes an Unrankable Base Type from the ordering (AD-17).
- **This consequence governs the crafted branch only.** A Raw Base's EV is its observed price with no probability term at all (FR-3). A Raw Base therefore needs no Eligible Pool, and a Raw Base ranks on whatever the Weights File says. A Base Type carrying both a Raw Base and crafted entries can therefore have an Unrankable crafted branch while its raw branch ranks normally. The view shows each branch in its own place, labelled for what that branch is.
- The view shows the reason per Base Type ("pool partial", "base absent from weights file").
- `core` never substitutes an invented pool to make a Base Type rankable.
- The count of Unrankable Base Types is visible without expanding the group. A large count means that the ranked list covers a small fraction of what the player tracks (§10 BQ-3).
- Every probability derived from a `partial` pool carries Provenance `absent`. The view renders such a probability as an **unknown rather than a number**, because the probability is an upper bound and not an estimate. A `partial` pool is the only path by which `absent` arises (AD-17, FR-10, FR-28).
- **A measurement taken before any view work sets the group's prominence.** The measurement is a fraction over Base Types. **Both halves of the fraction are stated as predicates**, because two people who have never spoken must be able to reproduce a fraction that binds a layout decision (AD-27; the same predicates are `IMPLEMENTATION-NOTES.md` §3, binding under AD-0):

```
rankable(base) = base carries at least one tracked entry that is
                 crafted (at least one affix present)
                 and not pruned

covered(base)  = base is PRESENT in weights.json
               ∧ both slots declare poolCoverage "complete"
               ∧ neither slot's pool is empty

coverage = |{ baseTypeId ∈ tracked.json : rankable ∧ covered }|
           ──────────────────────────────────────────────────
           |{ baseTypeId ∈ tracked.json : rankable }|
```

- **The denominator counts only Base Types that need a pool.** A Base Type tracked solely as a Raw Base has no probability term at all and can never resolve to `complete`. Counting such a Base Type would depress a fraction that binds a layout decision. The Unrankable group would then gain prominence on the strength of bases that were never unrankable. `pruned`-only Base Types are excluded for the same reason (FR-15). A Base Type carrying **both** raw and crafted entries **does** count, because its crafted branch needs a pool like any other crafted branch.
- **Each of the numerator's three conditions is load-bearing, and a statement of only the second condition — `both slots declare poolCoverage "complete"` — makes the fraction ambiguous.** "Both slots are `complete`" is **vacuously true** of a Base Type absent from the Weights File entirely, because such a Base Type has no slots to fail. A Base Type that declares `complete` over an *empty* pool passes a naive reading, and FR-4's first consequence excludes that Base Type from the ordering anyway. Either gap lets the same Tracked List and the same file score 100% or 40%, across a gate whose consequences turn at 80% and 50%.
- **`rankable` is decidable from `data/tracked.json` alone**, and deliberately so. Affix presence and Curation Status are both fields of `data/tracked.json`, so the gate runs before any sync has ever happened. Price State is **not** a term of `rankable`. `core` excludes `unresolvable` from the ranking for much the same reason that `core` excludes `pruned`. Folding Price State into `rankable` would move the predicate's inputs into the Dataset and would destroy that property.
- **An unresolved Stat Line does not affect coverage.** A line carrying `statId: null` is data about the source, not a completeness defect (§3 *Stat Line*, FR-28), so `covered(base)` turns on `poolCoverage` alone and is never depressed by a `null` `statId` it happens to contain.
- The result binds the layout, in **disjoint** bands (AD-27, §10 BQ-3):

| Measured coverage | What this FR requires |
| --- | --- |
| **≥ 80%** | The Unrankable group is a footer to the ranked list, as specified above. |
| **≥ 50% and < 80%** | The group becomes a **first-class surface** alongside the ranking, and not a footer. At this coverage the group is a large share of what the player tracks, and hiding the group misrepresents the product. |
| **< 50%** | The ranking premise fails. Escalate rather than ship around the failure. Neither `core` nor the view resolves this case. |

- A commitment to a layout before that number exists is a commitment to an assumption about how much of the product there is. For that reason the measurement is sequenced ahead of the view rather than alongside the view.
- **What "first-class surface" looks like is a UX decision, not a requirements one.** This FR fixes *when* the decision turns and *that* the decision turns. This measurement binds the concrete treatment, and the UX pass settles it. The requirement a design must satisfy is that at 50–80% coverage a reader cannot come away with the impression that the ranked list is the whole product.
- **The measurement recurs. The measurement is not a gate that is spent.** `core` re-measures coverage **on every regeneration of the Weights File**. The bands above bind on every measurement, and not only on the first measurement. The fraction moves. A patch introduces modifiers that the producer's source publishes unnamed, the producer must drop those rows, and the affected pools correctly fall back to `partial` (FR-28). A product that measured 85% before launch can therefore sit at 60% the week after a patch, with nothing reporting the drop. Re-measuring is part of **accepting** a regenerated file (AD-27).
- **The figure is published, not merely computed.** `sync-report.json` carries the coverage it measured (FR-25), so a drop across a patch boundary is visible where the rest of the run's health already is. A layout decision made against a stale number is the failure that this measurement exists to prevent.
- The fraction is not meaningful on a very small Tracked List. Three of four Base Types complete is 75%, and 75% lands in the first-class-surface band on a sample of four. `[ASSUMPTION: no source names a minimum denominator. The bands are treated as advisory below ~20 rankable Base Types, and the measurement is reported with its denominator so that the reader can see when that applies.]`

#### FR-5: Bound the ranked list to a readable length

The list answers a question rather than presenting an inventory.

**Consequences (testable):**
- The ranked list shows the top **20** Base Types by default. The player reads the remainder behind an explicit expand. `[ASSUMPTION: no source names a count. 20 is roughly a screen, and 20 comfortably exceeds the "top five" that the player actually acts on.]`
- The bound is a display concern only. `core` ranks the full Tracked List and the view truncates, so the Payout Threshold still reorders across everything (AD-4).

**Feature-specific NFRs:**
- Ranking the full Tracked List completes in **under 100 ms** on a mid-range machine, and re-runs synchronously on a threshold change. If ranking cannot meet that time, the fix is to memoise the pure function. The fix is never to precompute in sync (AD-24).

### 4.2 The Payout Threshold Control

**Description.** The Payout Threshold sets what counts as a win. A change to the Payout Threshold reorders the ranked list. The Payout Threshold is approximately a quarter of a Divine in early endgame. The Payout Threshold is a Divine or more when the player is richer and stronger. The Payout Threshold also increases through a league. For these reasons, the Payout Threshold is a control and not a constant. An outcome below the Payout Threshold is worth nothing to the player, because the player collects that much currency simply by playing. Realises UJ-2.

**Functional Requirements:**

#### FR-6: Set the Payout Threshold and see the list reorder immediately

The player sets a Payout Threshold in Divine. The ranked list then reorders in front of the player. Realises UJ-2.

**Consequences (testable):**
- The Payout Threshold control uses Divine. Divine is also the unit of every price and every Craft Cost that the Payout Threshold filters (AD-17, AD-20).
- A change to the Payout Threshold re-runs the ranking synchronously against the artifacts that are already loaded. The change triggers no network request and no sync.
- A Base Type with one jackpot Combination and a Base Type with many moderate Combinations swap order when the Payout Threshold crosses the moderate prices. This is the correct behaviour and not a bug.

#### FR-7: Remember the threshold between visits

The Payout Threshold and the view preferences survive a page reload.

**Consequences (testable):**
- The tool persists these values only in the viewer's own browser storage. There is no backend, no account, and no authenticated request (AD-15).
- A first visit has no stored value. The Payout Threshold then starts at a documented default. `[ASSUMPTION: 0.25 Divine, the brief's early-endgame figure, as the least-surprising cold start.]`

### 4.3 Combination Detail and Segregated Unknowns

**Description.** The player expands a Base Type. The view then shows every Tracked Entry on that Base Type, priced and unpriced alike. The player can thus see what the ranking is built from. The player can equally see what the ranking deliberately excludes. A Combination with no listings is either a jackpot or junk. Listings cannot tell the two cases apart. Segregation of the unknowns keeps the unknowns out of the ranking, and does not pretend that the unknowns are worthless. Realises UJ-3, UJ-5.

**Functional Requirements:**

#### FR-8: Expand a Base Type to its full tracked Combination list

The player expands any ranked Base Type. The player then sees all Tracked Entries of that Base Type with their prices, their Price States and their ages. Realises UJ-3.

**Consequences (testable):**
- Every Tracked Entry for that Base Type appears, whether or not the Tracked Entry cleared the Payout Threshold. **`pruned` tombstones are included**, visually separated and showing their prune reason. The inclusion of the tombstones is what makes UJ-5's review possible without an open of the file.
- Each row shows its Combination, its Price State, its price in Divine where the entry is priced, the number of listings that the estimate rested on, and its age. The row labels the age as an observation age or as a last-attempted age per FR-12.
- The view visibly marks each entry below the Payout Threshold as an entry that does not contribute to the EV.

#### FR-9: Render the four Price States distinctly, with a reason on `not-yet-synced`

The four Price States are four different things on screen. The view never collapses one Price State into another Price State.

**Consequences (testable):**
- The view renders no Price State as `0`, as blank, or as "—" in a way that reads as worthless (AD-9).
- The view presents `no-listings` as an open question and not as an answer. The view must not imply that the Combination is junk.
- The view shows `unresolvable` entries and does not merely omit them. The existence of an `unresolvable` entry is the symptom of a game patch (AD-9).
- **`not-yet-synced` carries a reason** — `never-synced`, `league-mismatch` (FR-31) or `no-exchange-rate` (FR-23). The reason is necessary because one Price State that covers three unrelated causes would defeat the point of the distinction between Price States. The view displays the reason and does not merely store the reason.
- The view does not carry the distinction between Price States by colour alone (NFR-10).

### 4.4 Provenance and Freshness Surfacing

**Description.** Every price in the system is an asking price. The system never observes a sale. A probability rests on whatever the Weights File's producer could actually source, and that coverage is expected to be uneven, band by band. A view that renders a placeholder identically to a well-founded figure keeps the trust of the player months later, because nothing on screen reveals the difference. That failure is the reason this feature exists. Realises UJ-4.

**Functional Requirements:**

#### FR-10: Propagate and display the weakest Provenance behind every figure

Every displayed derived figure states what that figure rests on. Realises UJ-4.

**Consequences (testable):**
- `core` propagates the **weakest** Provenance and the **oldest** timestamp of every input into each derived figure (AD-10). `core` derives that Provenance from **`weightSource` and nothing else in the file** — `weightSource: "published"` → `measured`, `weightSource: "absent"` → `uniform-prior` (§3 *Provenance*, *`weightSource`*).
- **A probability's inputs are pool-wide: every entry in its scoped pool, numerator and denominator alike** (AD-10). This is the scope, and the narrower containment-set-only reading is wrong. The player-visible consequence is what FR-11 turns on, and the consequence is deliberate rather than a defect: one entry carrying `weightSource: "absent"` anywhere in a scoped pool makes **every** probability on that Base Type read `uniform-prior`, however many of that pool's other tiers were published.
- **Two render treatments, not three**, and colour alone carries neither (NFR-10):

| Provenance | Rendered as |
| --- | --- |
| `measured` | the plain figure |
| `uniform-prior` / `absent` | visibly degraded. `absent` is an unknown and not a number (FR-4) |

- **The view must not print `weightSource`'s own words.** `weightSource: "absent"` on screen beside Provenance `absent` would collide — the two mean different things, and the shared word invites the reader to conflate them (§3 *`weightSource`*).
- **The propagation rule loses its one exception.** `4.x`'s `modelled-split` propagated from the numerator only, because it labelled a decomposition that never touched the denominator. That value is retired, and **every Provenance now propagates from every input**, with no carve-out. A `partial` pool weakens the denominator in fact and not merely in label, and `absent` still rides over everything (AD-10).
- **What the product gives up, stated as an assumption.** `4.x` could distinguish a measured weight the producer's model redistributed from an outright invented one. `5.0.0` cannot: a tier's weight is either `measured` or `uniform-prior`, with nothing in between, and the retired middle ground is not recoverable from the file. `[ASSUMPTION: the two-value distinction (measured vs. uniform-prior) is enough for the player to judge trust by, without the retired middle ground. If consumer-side pro-rating is ever adopted, a middle Provenance value must return in the same change, per §3 Provenance's revisit condition.]`
- The view shows the Weights File's declared producer, `generatedAt` and **`gamePatch`** (§3) beside any figure they influenced. A file left behind by a patch is therefore visible as such.
- The exchange observation that normalises a price participates in Provenance exactly like any other input (AD-20).

#### FR-11: State the uniform-prior caveat globally when the per-row badge discriminates nothing

A Provenance badge that is identical on every row conveys no information. The view must not pretend otherwise.

**Consequences (testable):**
- The view **reads the condition from the data and does not assume it of v1**. The Weights File carries `weightSource` per entry (`WEIGHTS-FILE-SCHEMA.md`, mapped to Provenance per AD-10, §3 *`weightSource`*). What v1 ships is therefore whatever the scraper produces, and a probability's Provenance may legitimately be `measured` (FR-30).
- **The banner condition narrows to *"no probability carries `measured`"*** — that is, every probability is `uniform-prior` or `absent`. The view then shows a **persistent, dismissible-per-session banner**. The banner states that the entire ranking rests on a uniform prior, and that relative ordering between Base Types is not evidence-backed.
- **The badge discriminates from day one, and it discriminates *between* Base Types rather than *within* one.** Revision 10 of this document expected within-a-Base-Type discrimination, on the ground that `weightSource` varies per tier. **That expectation is withdrawn, and the axis is restated here rather than quietly corrected**, because a builder who implements the old reading ships a badge that varies row by row inside one expansion and is simply wrong about what the data says. Provenance propagates **pool-wide** (FR-10, AD-10), so every probability on one Base Type carries one label: the Base Type's scoped pool is wholly `published` and reads `measured`, or it carries at least one invented tier and reads `uniform-prior` entire. The badge therefore separates trustworthy Base Types from placeholder ones, which is the comparison the ranking actually asks the player to make. The old warning about a `modelled-split` figure not triggering the banner retires with the label it was about.
- **The discrimination is coarser than revision 10 expected, and that is still a genuine improvement over `4.x`.** `4.x` expected one label across whole weapon classes; the unit is now one Base Type, which is the unit a ranked row already is. What the product gives up is any on-screen distinction between a pool that is one invented tier short of wholly measured and a pool that is invented throughout — both read `uniform-prior`. `[ASSUMPTION: a per-Base-Type Provenance badge is enough for the player to judge trust by, without a mixed-Provenance indicator that would distinguish a nearly-measured pool from a wholly invented one. No stronger UI affordance is required for v1.]`
- **The replacement warning inverts: do not read a `uniform-prior` badge as "this pool is invented".** Under pool-wide propagation a single `absent` tier governs the whole Base Type, so the badge states the **weakest** input and never the pool's general condition. A reader who infers that a `uniform-prior` Base Type rests on nothing measured reaches the wrong conclusion, and the honest reading is the literal one: something in this pool was invented, and the figure inherits that.
- The banner **disappears on its own** once any `measured` figure is present — that is, once **any one** Base Type's scoped pool is wholly published. The banner is a function of the data, and not a build-time constant that someone must remember to remove.
- The per-row badge is required regardless (FR-10). The badge is the discriminating signal the moment the first wholly-published pool arrives, and partial coverage across Base Types — not within one — is the likeliest shape of the first real file.
- Where the badge cannot yet discriminate, **freshness** is the genuinely discriminating per-row signal (FR-12). The view gives freshness the visual weight that Provenance has not earned.

#### FR-12: Show per-row freshness, and say which clock it is reading

Each row carries its own age. The age of an unpriced row is as meaningful as the age of a priced row.

**Consequences (testable):**
- A single dataset-level timestamp is insufficient and must not be the only freshness signal, because Chunked syncing guarantees that rows refresh at different times (AD-7, AD-10).
- **Which clock, always.** The view takes the age from the row's `observedAt` where there is an observation, and from the row's `lastAttemptedAt` otherwise (AD-9). This rule is unconditional and holds on every surface that shows an age.
- **Where an age appears is a freshness cut-off, not a blanket rule.** Every Tracked Entry carries an age **in the expansion**, wherever an age exists, with both clocks labelled. On the **collapsed ranked row**, a row younger than a declared freshness cut-off shows **no age at all**, and a row at or beyond the cut-off carries a visible stale mark with a word. **The cut-off is 48 hours**, chosen against the ~15-hour partial refresh cycle so that normal rotation never marks a row (UX memlog 46/47).
- **This is a deliberate departure from an earlier reading of this FR**, in which every row carried an age on every surface. The departure buys the ranked list a quiet default: a trust mark on the collapsed row then means something is wrong, rather than being present on all twenty rows and discriminating nothing — which is the same argument FR-11 makes about a Provenance badge identical on every row. **FR-12's intent is preserved rather than traded away.** The distinction this FR exists to protect — that the player can always tell an observation age from a last-attempted age — is fully carried in the expansion, where both clocks are labelled, and a *stale* row is never silent on either surface.
- A single dataset-level timestamp remains insufficient and must not be the only freshness signal (AD-7, AD-10). The cut-off suppresses an age on a **fresh** row; it never substitutes a dataset-level timestamp for a per-row one.
- **A never-synced row is the one case with no age at all.** The view renders a never-synced row as *never attempted*, and not as an age or as a blank. The row's `lastAttemptedAt` is genuinely absent, because only an issued request stamps that field (§3) and no request has been issued. There is therefore nothing to show and nothing to back-fill. This is the `not-yet-synced` reason `never-synced` (FR-9). It is also the same fact that FR-17 uses when FR-17 treats such an entry as **infinitely old** for ordering. An implementation could write a placeholder timestamp to satisfy a non-null field. That implementation would lie on screen and would also give the rotation a key that sorts wrongly.
- **The view labels which of the two ages it shows.** The two ages mean different things — *this price is three days old* versus *nothing has been found here for three days*. A `no-listings` row that the tool retried hourly all week is a different fact from a `no-listings` row that the tool last looked for in the previous league. A collapse of the two ages into one unlabelled "3d" would make the second row indistinguishable from the first row.
- A partially refreshed Dataset publishes and renders normally. Per-row freshness is what makes that honest (AD-19).

#### FR-13: Present estimates as asking prices, never as realised value

The view's language never implies that a player achieved a price.

**Consequences (testable):**
- The view labels prices as current asking prices from live instant-buyout listings (AD-12).
- No copy describes an estimate as "sells for", as "worth", or with any phrasing that implies an observed sale.
- This rule is the *only* mitigation in the system for Risk R-1 (§9). The player's manual loop had a real-sale correction, and the tool discards that correction. A copywriting rule does not replace the correction.

### 4.5 The Curated Tracked List

**Description.** The Tracked List is two things at the same time. The Tracked List is what the tool watches. The Tracked List is also the tool's entire request budget. Every Tracked Entry costs a search on every refresh. Therefore curation discipline is a permanent operating requirement, not a one-time tuning exercise. The Tracked List is a hand-owned, committed file. The browser never writes to the Tracked List (AD-15, AD-3). The system cannot discover a Combination that nobody tells the system to watch. v1 records that limitation and does not solve it. The Tracked List realises UJ-5.

**Functional Requirements:**

#### FR-14: Bound every request to one of four declared sources

Exactly four sources generate a trade API request. No other source generates a trade API request.

**Consequences (testable):**

| Source | Cadence | Cost |
| --- | --- | --- |
| `data/tracked.json` — the Combinations to price | every Chunk | one search + one fetch per entry |
| `data/currencies.json` — the currencies to price for Divine normalisation (FR-23) | every Chunk, **first** (FR-17) | small, fixed |
| League validation against the live leagues endpoint (FR-32) | once per run | one request |
| Catalogue refresh (FR-24) | explicit human-invoked command, patch cadence, **never on the Chunk path** | four requests |

- A full refresh must stay within **~1,500 searches**, against a measured ceiling of ~2,400 searches a day.
- **Three run-start gates precede any priced entry, and they do not share one consequence.** `sync` runs the catalogue check (FR-24), `core`'s cross-file validation — **all four of AD-17's checks as one gate** (FR-16, FR-29) — and the league check (FR-32). Only the league gate costs a request. A catalogue failure degrades **one entry** and the run continues; a cross-file or league failure invalidates the run's premise and **aborts** it non-zero. A builder who runs fewer than four cross-file checks here ships a gate that passes configurations `web` will refuse (AD-12, AD-17).

See ARCHITECTURE-SPINE.md AD-12 for the mechanism.

#### FR-15: Honour Curation Status as schema-level behaviour

`active`, `pinned` and `pruned` are schema members with defined effects, not conventions.

**Consequences (testable):**
- `sync` selects `pinned` entries **first in every Chunk**. A `pinned` entry never waits its turn in the `active` oldest-first ordering. `sync` refreshes every `pinned` entry in every Chunk that can afford the pinned set. A Chunk whose discovered allowance cannot also fund at least one `active` entry truncates the pinned set instead of freezing the rotation, and `sync` records the truncation in the Sync Report. **The cap and the truncation are stated normatively in `IMPLEMENTATION-NOTES.md` §6, binding under AD-0, where both of their owners are named; FR-19 carries the citation. This consequence is a summary and defers there rather than to FR-17** (FR-17, AD-12, AD-7).
- `pruned` entries are excluded from the sync workload **and** from the ranking sum. A `pruned` entry's last-good price never contributes to the ranking sum (AD-12, AD-17).
- A `pruned` entry carries its reason. Therefore a curator does not add the same Combination again and learn the same lesson again each league. The view shows that reason (FR-8).

#### FR-16: Reject an overlapping Tracked List at load

Tracked Entries for one Base Type must describe mutually exclusive outcomes, because the sum of FR-1 is over a partition rather than a list.

**Consequences (testable):**
- A **predicate defines overlap, not an enumeration**. An enumerated list of shapes has now missed a case twice (AD-17; the predicate's binding form is `IMPLEMENTATION-NOTES.md` §2.1, under AD-0):

```
overlap(a, b)  ⇔  slotOverlap(a.prefix, b.prefix) ∧ slotOverlap(a.suffix, b.suffix)

slotOverlap(x, y) =  true              if x is absent or y is absent
                     true              if x.statId != y.statId ∧ coOccur(x, y)
                     false             if x.statId != y.statId
                     true              if both are valueless
                     bands intersect   otherwise
```

- **Branch order is load-bearing.** The co-occurrence case sits **above** the inequality case. The co-occurrence case must catch exactly a pair of references on *different* `statId`s.
- An absent affix means *any roll in that slot*. For that reason the condition is a conjunction over both slots. The **both-valueless** branch is the one branch that a bands-intersect reading does not give a builder. Two valueless references have no bands to intersect. A builder without the both-valueless branch concludes that two identical valueless entries on one Base Type do **not** overlap. That builder then accepts a Tracked List that double-counts on the same partition that FR-16 protects.
- **`coOccur` stops the tool from counting one game modifier as two outcomes, and reads a direct fact of an entry's `lines`.** A Source Modifier may publish several Stat Lines that always roll together (§3), and under contract `5.0.0` those lines sit nested inside that modifier's own entry. A single item satisfies **both** of two references that name two of those Stat Lines. Therefore `x.statId != y.statId` is not on its own evidence of disjointness. `coOccur(x, y)` holds when some entry in the scoped Eligible Pool has a line contained by `x` **and** a line contained by `y`. **The Cohort clause retires with no condition lost** — it restated a property (one source row, one item-level scope) that the entry-per-tier shape now makes definitionally true, rather than adding a case to exclude (AD-17, AD-11; `coOccur`'s binding form is `IMPLEMENTATION-NOTES.md` §2.2, under AD-0).
- **`coOccur`'s scope `L` is the Base Type's own crafted Item Level Floor.** `L` is the same value that scopes every probability on that Base Type. FR-16 and FR-22 give a Base Type exactly one `L` (FR-29, AD-17).
- **The overlap check is a cross-file check, owned by `core`.** The overlap check stands on the same ground as FR-29's edge-alignment rule. Co-occurrence is a fact of `data/weights.json`, and the references are in `data/tracked.json`. Therefore the check belongs to the component that holds both sides. `core` reports the check against the Tracked Entry, not against either file. **`web` runs the check at load, and `sync` runs the same check as a run-start gate**, before any priced entry consumes budget, with a failure aborting the run — identical to FR-29's two of AD-17's four, and for the identical reason: an ungated `sync` run would spend a full refresh's budget on a Tracked List that a `coOccur` failure makes `web` refuse to load in its entirety, which is a worse waste than the per-entry failures those two checks catch (AD-17).
- **Where the pool cannot answer, `coOccur` is `false`, and the Tracked List still loads.** There are exactly two such cases. The first case is a Base Type **absent** from the Weights File. The second case is a Base Type whose pool is **`partial`**. The safe behaviour is **not** to refuse the Tracked List. FR-28 and FR-4 have already made such a Base Type Unrankable. Therefore the tool never sums the partition that `coOccur` protects for that Base Type, and a missed double-count cannot reorder anything. **A uniform-prior file is not one of these two cases.** Contract `5.0.0` requires `sourceModifierId` on every entry, whatever the file's Provenance. Therefore a bootstrap file that declares `complete` answers `coOccur` exactly like any other file, and its Base Types rank normally (FR-30). A refusal instead would stop the **whole site** over a Base Type that was never going to rank. FR-16 states this rule explicitly for a reason. Without the explicit rule, one builder short-circuits and renders the view while another builder rejects `data/tracked.json` site-wide, and **both readings satisfy the predicate as written** (AD-17).
- **One kind pairing is unreachable rather than handled.** A `statId` either rolls a value or does not roll a value. Therefore one `banded` reference and one `valueless` reference can never share a `statId`. `contracts` rejects that pairing within `data/tracked.json` at load, and does not let `core` pick a reading. The pairing is visible inside one file, so a per-file schema can see the pairing. Kind *agreement between files* is a different question — a `valueless` tracked reference against a `banded` Weights File line for the same `statId`, kind now read from a line's `ranges` rather than from a retired `kind` field. That question is a cross-file question, and `core` owns it. **`web` runs it at load, and `sync` runs it as a run-start gate**, gated identically to `coOccur` above and to FR-29's two checks — the four together being AD-17's whole set — with a failure aborting the run. **The quantifier is universal, not existential.** A `statId` either rolls a value or it does not, so **one** disagreeing line is a defect in the file however many lines agree; AD-17 states the quantifier because two builders split on it (FR-29, AD-17; the check's binding form is `IMPLEMENTATION-NOTES.md` §2.3, under AD-0).
- Four consequences follow. Successive enumerations missed the last two consequences:
  - **A curator may track adjacent disjoint tiers of one `statId` in one slot.** That is the point of AD-5's bands. Bands that *intersect* still overlap, and `core` still rejects them.
  - A **partial-affix entry subsumes a fuller entry**. An absent slot covers every roll in that slot.
  - **A prefix-only entry and a suffix-only entry on one Base Type overlap each other.** Neither entry subsumes the other entry, and no two bands intersect. But an item that carries both named modifiers satisfies both entries, and the sum counts that item twice.
  - **Two entries in *one* slot that name two Stat Lines of one Source Modifier overlap each other.** The `statId`s differ, so no bands intersect, and the slot-conjunction reading above does not apply. But the two Stat Lines always roll together, so a single item satisfies both entries. This is the same failure as the case above, reached from the other direction. In the case above, one item satisfies two entries across two slots. Here, one item satisfies two entries across two Stat Lines of one modifier. The `coOccur` branch catches this failure.
- **Separately, the crafted entries on one Base Type must share an Item Level Floor** (AD-17, FR-22). Entries at floors 75 and 82 are nested, not disjoint. The 75 search also matches every item that the 82 search returns. The rule has a second, independent reason. EV is an expectation over *one* crafting act on *one* item population. Entries at different floors describe crafts on bases of different item levels, and `core` normalises their `P` terms against pools of different scopes (FR-29). A sum over those entries is not an expectation over anything.
- **A Raw Base is exempt from that floor rule.** A Raw Base is never a summand (FR-3). Therefore a Raw Base's floor cannot break a partition that the Raw Base does not enter. That exemption lets a white base at item level 82 exist together with crafted entries on the same Base Type at a lower floor (AD-17).
- The tool rejects overlap at load and names the offending entries. The tool never reconciles overlap at ranking time.
- Double-counting increases that Base Type's `ΣP × price` by the measure of the overlap. Double-counting does damage even where `ΣP` does not exceed 1. A modest overlap on a high-priced Combination is enough to move a Base Type several places.

#### FR-17: Refresh the Tracked List in a defined, deterministic rotation

The player asks *how often does a row get re-priced?* about every figure on screen. Therefore the rotation is a requirement, not an implementation choice. A Chunk selects entries in exactly this order. A Chunk stops when the Chunk reaches any Chunk bound (AD-7, FR-19).

**Consequences (testable):**

| Order | Selected | Why it sits here |
| --- | --- | --- |
| 0 | **Currency rates**, always, before any priced entry in the same Chunk | FR-23 requires the currency rates. A rotation that omits them produces a Chunk of `not-yet-synced` entries by construction |
| 1 | Every **`pinned`** entry, every Chunk — subject only to the `pinned` cap of `IMPLEMENTATION-NOTES.md` §6, binding under AD-0 (FR-19) — **by oldest `lastAttemptedAt` first** | this is what `pinned` means (FR-15). FR-17 names the ordering key because under that cap a Chunk normally reaches every `pinned` entry, so the order looks immaterial. The key becomes load-bearing exactly when a Chunk cannot reach every `pinned` entry. The key makes the pinned tail rotate instead of starving behind a fixed key order |
| 2 | **`active`** entries whose Price State is not `unresolvable`, by **oldest `lastAttemptedAt` first** | the ordering is self-levelling. A full pass completes with no separate scheduler |
| 3 | Entries whose Price State **is** `unresolvable`, on a bounded retry — at most one attempt per entry per 24h | a patched-out modifier does not disappear from the rotation, and does not monopolise the rotation |
| 4 | **Never `pruned`** | excluded from the workload entirely (FR-15) |

#### FR-18: Surface the Tracked List's age

The player can see the time since anyone last reviewed the Tracked List.

**Consequences (testable):**
- The Sync Report records the date of the last tracked-list edit, and the view shows that date (AD-12).
- The tool derives that date from the git commit history of `data/tracked.json`, not from a hand-maintained field. A hand-maintained field would become stale exactly when the date mattered. `[ASSUMPTION: AD-12 requires the date be recorded but names no mechanism.]`
- The view shows the date unconditionally. A Tracked List that runs unattended for months is visible as such, and the player does not have to search for the date.

**Notes:** `[NOTE FOR PM]` The tool cannot show a Combination that nobody told the tool to watch (Risk R-2, §9). FR-18 exists so that the gap prompts a periodic deliberate review. FR-18 does not close the gap.

### 4.6 Background Price Sync

**Description.** A CLI does one bounded Chunk of work and then exits. The player's own scheduler starts the CLI again and again. A full refresh takes ~15 hours and uses ~62% of the daily search budget. That cost is acceptable, precisely because the CLI precomputes every figure and no figure is on a user-facing path. This section fixes how the tool estimates a price. This section does not leave that decision to whichever agent writes `sync`, because every downstream number inherits the estimate method.

**Functional Requirements:**

#### FR-19: Run as a bounded, resumable, single-instance Chunk runner

The sync process runs as a bounded, resumable, single-instance job: one invocation performs one Chunk and then exits. See ARCHITECTURE-SPINE.md AD-7 for the locking and Chunk-boundary mechanism, and `IMPLEMENTATION-NOTES.md` §6 for the `pinned` cap's inequality, its runtime truncation rule and the `minChunkSearches` seeding rule. §6 is the normative home of all three, which §3 *Curation Status*, §3 *Chunk*, FR-15, FR-17, FR-31 and FR-33 each summarise (binding under AD-0).

#### FR-20: Route all outbound trade traffic through one rate-limit-adaptive client

Exactly one adapter issues trade API requests, and that adapter is rate-limit-adaptive, so the tool never gets throttled or banned by the trade API. See ARCHITECTURE-SPINE.md AD-8 for the mechanism, and `IMPLEMENTATION-NOTES.md` §5.3 for the rate-limit buckets and the governance the client applies to them (binding under AD-0).

#### FR-21: Estimate a price as the median of the cheapest instant-buyout listings

For each Tracked Entry, one search and one fetch produce one Price Observation.

**Consequences (testable):**
- The search uses that Base Type. The search uses that entry's Item Level Floor. The search uses `magic` rarity for an entry with affixes, and `normal` rarity for a Raw Base. The search uses the entry's Modifier References as stat filters, **one filter per reference and shaped by the reference's kind**. The search asks for **instant buyout only**. The search is **sorted by price ascending** (AD-16).
- **The stat filter's shape follows the reference's kind** (AD-5, AD-16). A **`banded`** reference carries **both `min` and `max`** from the band. A **`valueless`** reference carries the stat id and **no edges at all**. A `min`/`max` filter for a stat that rolls no value is the operational half of the sentinel defect that §3's *Modifier Reference* rejects. Such a filter does not raise an error. Such a filter silently returns nothing, or returns the wrong population.
- The adapter passes a band's `max` as well as the band's `min`. That is what makes the priced population the same population that FR-29 computes a probability for. A min-only filter returns every higher tier and prices the band at the band's floor. A min-only filter is the defect that BQ-1 identified, reintroduced at the adapter (AD-5, AD-16).
- The Base Type goes in **`query.type`**, not in `type_filters.category`. `category` takes taxonomy ids such as `weapon.bow`, and no committed artifact maps a Base Type to that Base Type's leaf category. The Base Type alone is sufficient and exact (AD-16, AD-25).
- Instant buyout is the option labelled **"Buyout or Fixed Price"**. That option's `id` is JSON `null`. The adapter must emit that `id` explicitly, and a serialiser must not drop it. Instant buyout is **not** `priced_with_info`, whose live label is *"Price with Note"*. The wrong option raises no error. The wrong option silently admits unpriced listings and corrupts every estimate (AD-16; the four traps are `IMPLEMENTATION-NOTES.md` §5.2, binding under AD-0).
- **Whether the search must also carry `query.status`, and how that field interacts with the option above, is open as §10 OQ-20.** A live browser search sends one and this document has never specified one. The question is blocking for a correct first price and not for building, and `sync`'s builder owns it.
- The fetch retrieves the **cheapest 10 result ids**. The Price Observation is the **median of those listings' prices after normalisation to Divine**. `sync` records the Price Observation with the sample size that the fetch actually returned (AD-16).
- **On an even sample the median is the lower of the two middle values**, not the mean of the two middle values. Ten results is the common case, so an even sample is the normal path rather than an edge case. An unstated rule here is enough on its own to make two implementations return different prices from identical data. The lower value buys three things. **Every persisted price is a price that someone actually asked**, never a synthetic midpoint. **`sync` normalises and rounds each listing once at the sync boundary (FR-23), so a choice of one listing cannot leave the grid, where a mean could.** That argument holds at any precision, which is why this document states the argument without reference to the number. The lower value also leans very slightly cheap, in the same conservative direction as the ascending sort. The rule's binding form is `IMPLEMENTATION-NOTES.md` §4.3, under AD-0.
- Fewer than 10 results is valid, and `sync` records the true count. **Zero results is `no-listings`, never a price** (AD-9).
- **`sync` records the trade-site search identifier it issued, on every attempt.** Alongside `lastAttemptedAt`, `sync` writes **`lastSearchId`** — the identifier the trade site's search endpoint returned for that request — and **`lastSearchLeague`**, the league the request was issued against. Both fields sit on the **Dataset entry**, never on a Price Observation, because a `no-listings` entry has no Price Observation and needs the identifier just as much as a `priced` one does (§3 *Price Observation*).
- **The three fields are stamped together, or not at all.** `lastSearchId` and `lastSearchLeague` are written at exactly the moment `lastAttemptedAt` is written, and by the same rule: **only an attempt that issues a request stamps them** (§3 `lastAttemptedAt`). Offline work stamps none of the three — FR-24's catalogue validation above all. Tying the identifier to the attempt rather than to the outcome is what makes the field's presence decidable without reading Price State, which is the property FR-33's render rule depends on.
- **The identifier exists so that `web` can offer a link, and for nothing else.** `core` never reads it, and it enters no ranking term (AD-4). It is persisted rather than computed at view time because minting a fresh search would require a runtime call to pathofexile.com, which FR-33 forbids the page to make on its own behalf.
- Where a result set spans several listing currencies, `sync` takes the median over normalised values. The sample may therefore not be the globally cheapest ten. `sync` accepts and records that result. `sync` does not correct that result with extra requests.
- The ascending sort keeps stale overpriced listings out of the estimate. The instant-buyout-only filter removes listings priced below market, because a buyer would already have bought such listings (AD-16).
- **A multi-`#` stat filters on one derived value, and which derived value that is, is a measurement rather than a choice.** *"Adds # to # Lightning Damage"* rolls two numbers, and the filter compares one derived value. **The unit now binds two parties independently rather than one**: the producer's `ranges` must be read in that quantity for `core`'s derived interval to mean what the trade filter means, and this adapter's band edges must be expressed in **that quantity and no other**, because this adapter passes the band edges into the filter and FR-29 counts the population that comes back. A producer that picks a different quantity, or `core` that derives against a different quantity than the filter compares, prices the wrong population — and because the two parties now disagree independently rather than through one shared decomposition, a disagreement **fails loudly as an edge-alignment error rather than silently as a wrong population** (FR-29). **§10 OQ-12** identifies the quantity, and the weights scraper project owns OQ-12. The quantity is not an assumption to code around.
- **Band edges are numbers, not integers.** Under an averaged unit the value lattice is half-integers, so `56.5` is a legitimate edge (AD-11). Whether the trade filter accepts a non-integer `min`/`max` is part of OQ-12 and is unconfirmed. The exact shape that a `valueless` filter takes is also part of OQ-12 and also unconfirmed — whether the stat-filter object accepts a stat id with `value` omitted entirely, requires `{ "value": {} }`, or rejects the stat id. Both are live-payload facts of the class that this FR's other filter consequences exist to catch, and this document's account of both is **unverified**. `[ASSUMPTION: the valueless filter is emitted with the stat id and no value object. Verified for the four filter details above against live payloads on 2026-09-12; this one was not, and it is owned with OQ-12.]`
- **The estimator prices the cheap end of whatever band the estimator is given, and the homogeneity argument that once justified this is conceded rather than asserted.** Under `5.0.0` a curated band legitimately spans a run of adjacent tiers (FR-22), so the priced population is **deliberately wider** than the weighted population — the trade search returns a neighbouring tier's tail that FR-29's whole-tier containment counts none of. What keeps that mismatch cheap is not homogeneity, which contract `5.0.0` no longer buys the consumer: it is this FR's own **ascending sort**, which puts a tail excluded **at the band's ceiling** at the top of the band rather than the bottom — AD-11 claims this of the ceiling case and of no other — plus FR-29's edge-alignment check, which still rejects the band shape that would widen the gap. **Neither helps against a tier intruding at the band's floor, which this FR's ascending sort actively prices** (FR-29, §10 OQ-21). `[ASSUMPTION: the ascending sort and edge alignment keep the priced/weighted mismatch cheap enough to trade for contract 5.0.0 where the excluded tier is excluded at the ceiling, and floor-side intrusion is rare enough not to dominate the ordering. This is tagged as an assumption rather than asserted as a proven bound, because nobody has measured either frequency against a real 5.0.0 file (§7.2).]` (AD-16, AD-11).

#### FR-22: Derive each entry's Item Level Floor from its Accepted Tier

Each Tracked Entry declares the item level that the entry's search filters on. A stated rule gives that item level, not a global constant.

**Consequences (testable):**
- The **Accepted Tier** of a modifier is tier 1. The **exception** is a modifier whose tier 1 first becomes available at item level 81 or 82. Such modifiers are too rare to chase, and the curator accepts tier 2 instead.
- A Tracked Entry's **Item Level Floor** is the highest item level among that entry's affixes' Accepted Tiers. Worked example: on bows, critical hit chance tier 1 appears at item level 73. Increased physical damage tier 1 appears only at item level 82, and the curator rejects that tier 1 in favour of its tier 2 at item level 75. A bow entry that carries both affixes is therefore floored at **75**.
- The Accepted Tier decision and the Modifier Reference's **band** are **one act** — the trade API has no tier concept (AD-5) — but the mechanical meaning of "accept tier 2" depends on the modifier.
- **For a modifier whose text carries one `#`, tier and band coincide.** "Accept tier 2" means that the curator sets the reference's `valueMin` and `valueMax` to the tier 2 band's edges, exactly as before.
- **The instruction here reverses under contract `5.0.0`, and the reversal is written as a reversal rather than folded silently into the rule, because a curator working from memory would otherwise author exactly the band the old rule warned against and be right by accident.** `4.x` forbade writing a tier's own value range as the band, because the value axis was decomposed into cells and a tier's own range landed mid-cell. `5.0.0` withdraws the decomposition, and **requires the opposite**: the curator writes the tier's own declared value range as the reference's edges. Worked example, from the same Bows family the contract's worked overlap case uses: a curator chasing T8 writes `56.0 – 80.0`; a curator chasing T7 writes `43.0 – 56.5`. Each band necessarily admits the neighbouring tier's tail into the priced sample — T8's band overlaps T7's declared range, and T7's overlaps T8's — and counts none of that neighbour's weight, because **neither the search nor the curator can exclude it** (§3 *Eligible Pool*, FR-29). That inclusion is correct rather than a defect: the priced population and the weighted population remain the same population, which is the only property that FR-21 and FR-29 jointly require.
- **Curate to a whole tier, or to a run of adjacent tiers — never to a band that contains one tier and clips another.** `43.0 – 60.0` in the worked family is exactly what a curator must not write: it neither wholly contains T7 (which reaches 56.5) nor wholly contains T8 (which starts at 56.0), so it fails FR-29's edge-alignment check at load rather than silently mispricing anything. A band that wholly contains a run of adjacent tiers — `43.0 – 80.0`, spanning T7 and T8 both — is legal, and reads as the curator genuinely accepting that whole run (§3 *Accepted Tier*). **Request-budget pressure is relieved by this reversal, not added to it.** `4.x` needed a curator to isolate an interior cell to get a homogeneous population; `5.0.0` needs no finer split at all, because the tier itself is now the unit a curator tracks (FR-14).
- **None of this changes the request budget.** One tracked Modifier Reference is still one Tracked Entry and one search, whatever tier or run of tiers it names (FR-14).
- `itemLevelMin` is a declared field on the Tracked Entry, and a person authors the field by hand. Neither `sync` nor `core` infers `itemLevelMin`, and neither `sync` nor `core` adjusts `itemLevelMin`.
- **The curator declares `acceptedTier` per Modifier Reference, and nothing derives it.** A person authors the field by hand, in the same act that chooses the band. Neither `sync` nor `core` infers `acceptedTier`, adjusts `acceptedTier`, or checks `acceptedTier` against the band — exactly as neither infers or adjusts `itemLevelMin`. The field is display-only and `web` is its only reader (§3 *Accepted Tier*).
- **A declared label may name a run of tiers, and that is correct rather than sloppy.** `"T1–T2"` is legal. For a modifier whose text carries more than one `#`, tiers overlap in value space (AD-11), so a curator may genuinely be accepting a run of adjacent tiers rather than one. `WEIGHTS-FILE-SCHEMA.md` already names `"T7–T8"` as an acceptable spelling of the same idea. The view prints what the curator accepted, rather than rounding to a single tier. `[ASSUMPTION: acceptedTier has no formal grammar beyond this tier-prefix convention. Nothing in the trade API or the Weights File can adjudicate a curator's spelling, so nothing validates it.]`
- **A missing label is a curation gap, and never a validation error.** A Modifier Reference with no `acceptedTier` still loads, still prices and still ranks — the field feeds no ranking term. The view renders such a reference in a visibly-marked fallback form carrying the Trade Catalogue stat name and the value band, so the gap is noticed and filled. A hard error here would stop the product over a display string, which is the wrong trade for a field that reaches no number.
- Raw Bases are pinned to item level 82 (FR-3).
- **A Base Type has one Item Level Floor**, and the curator derives that floor in two steps, both by hand:
  1. Each crafted entry has a **candidate** floor — the highest item level among that entry's own affixes' Accepted Tiers, per the rule above.
  2. The Base Type's Item Level Floor is the **maximum candidate across its crafted entries**, and every crafted entry on that Base Type declares that floor.
- Step 2 is what makes the shared floor reachable rather than merely required: two bow entries that derive candidates of 73 and 75 both declare **75**. Without step 2, FR-16 would reject a Tracked List that FR-22 had just told the curator to author.
- A raise of an entry from that entry's own candidate to the Base Type's floor is **not cosmetic**. The raise widens that entry's scoped Eligible Pool and so changes that entry's probability (FR-29). The curator is choosing one crafting proposition for the base, which is exactly what AD-17 requires. Tracking of the same base at two genuinely different floors is deferred, not available.
- The Base Type's crafted entries share that floor, and the tool enforces the shared floor at load (FR-16, AD-17). A Raw Base at item level 82 is exempt, because a Raw Base is never a summand (FR-3).
- That floor is what scopes the Eligible Pool that normalises every probability on the Base Type (FR-29, AD-17). The floor is a valuation input, not only a search parameter.
- **Two References naming two Stat Lines of one Source Modifier cannot both be tracked in one slot.** The two References look independent — different `statId`s, no bands intersecting — but the two Stat Lines always roll together, so one item satisfies both References. FR-16 rejects such a pair at load through FR-16's `coOccur` branch. This is a **load-time rejection, not a budget question**: the curator is not trading a second search for a finer answer, the curator is writing a Tracked List that will not load. Where the conjunction is the thing that the curator actually wants to price, **isolation of the conjunction is deferred** (§7.2). The tool has no way to express *"I want both of these"* as one outcome, which is why FR-16 rejects the configuration rather than approximating it (AD-17, AD-11).

#### FR-23: Normalise every price to Divine at the sync boundary

Raw listing currency never enters valuation.

**Consequences (testable):**
- `sync` normalises all prices to Divine. Every price the player sees is a Divine figure.
- If a listing's currency has no current rate, `sync` writes the entry as `not-yet-synced` with reason `no-exchange-rate` rather than stores the entry unnormalised (FR-9).

See ARCHITECTURE-SPINE.md AD-20 for the precision and rounding rule, and `IMPLEMENTATION-NOTES.md` §4.2 for the binding form of the rounding itself (AD-0).

#### FR-24: Fail loudly on an unresolvable stat id or Base Type

`sync` never silently skips a Tracked Entry that references a `statId` or a Base Type that the trade API no longer exposes.

**Consequences (testable):**
- `sync` writes that entry's Price State as `unresolvable` **and** records that entry in the Sync Report (AD-9).
- `sync` never skips that entry, never defaults that entry, and never leaves that entry at its previous value. A patched-out modifier must not keep ranking on its last-good price forever (AD-9).
- `sync` detects the condition by validation against the **committed Trade Catalogue** (`data/catalogue/*.json`), before `sync` issues any request. `sync` never infers the condition from results. An empty result set is `no-listings` and never `unresolvable`. A tool that conflates the two states would report a patch-out every time a Combination simply had no sellers (AD-9).
- An **explicit human-invoked command at GGG patch cadence** refreshes the catalogue. A sync run never refreshes the catalogue (AD-25). The catalogue's diff is how a renamed `statId` or a new Base Type becomes visible — the same mechanism that fixtures use for response shapes (NFR-2).
- **Two checks, two surfaces.** `sync` checks every id in `data/tracked.json`, and a failure there becomes that entry's `unresolvable` state *and* a Sync Report line. `sync` checks every id in the Weights File, and a failure there becomes a Sync Report line **only** — `sync` reads the Weights File and never writes the Weights File, so `sync` reports the failure rather than repairs it (AD-9, AD-3).
- **An `unresolvable` entry does not necessarily carry a search identifier, and a builder must not assume otherwise.** Detection is offline and precedes any request, so an entry that is `unresolvable` the first time `sync` meets it has never had a search issued: it carries no `lastAttemptedAt` and no `lastSearchId`. An entry that went `unresolvable` later carries both, from the last run in which its ids still resolved. Neither case is an error, and the presence of the identifier — never the Price State — is what decides whether a link can be offered (FR-21, FR-33).
- `core` excludes `unresolvable` entries from valuation. The view surfaces the existence of those entries (FR-9).

#### FR-25: Publish a structured Sync Report

Every run's outcome is data that the view reads, not console output.

**Consequences (testable):**
- The report records requests consumed **per declared source** against the live bucket (AD-12, FR-14). The report records unresolvable entries (AD-9). The report records the date of the last tracked-list edit (AD-12). The report records the **pool-coverage fraction** measured against the loaded Weights File (FR-4, AD-27). The report records a **pinned-starvation** record where one arose.
- **The pinned-starvation record** is present only on a Chunk where the discovered allowance could not cover the pinned set plus at least one `active` entry (FR-17). The record carries `discoveredAllowance`, `pinnedCount` and `activeRefreshed`, which AD-7 names. The record also carries **`declaredMinChunkSearches`, `currencyCost` and `pinnedRefreshed`, which are this PRD's own additions** — no architecture decision requires those three fields. Those three fields are here because "the shortfall" is otherwise at least four different numbers, and because the declared yardstick beside the allowance actually observed is what turns the record from a symptom into a diagnosis (FR-19).
- **The pinned-starvation record is distinct from *entries not reached*, and the distinction is the whole point.** *Not reached* is a normal rotation outcome. Starvation is a **curation defect that the player must correct**. A report that folds the two together reproduces exactly the indistinguishability that the record exists to remove. Without the named shortfall, an oversized pinned set looks like a slow refresh (AD-7).
- **`web` surfaces the presence of the pinned-starvation record**, alongside the tracked-list age (FR-18) and the unresolvable count (FR-24). Those three figures are what tell a player that his list is not doing what he thinks it is. A report field that nothing renders is a field that nobody reads (AD-7).
- The report also records entries **not reached in this Chunk**. This field is **this PRD's own addition** — no architecture decision requires the field — and the field exists because a partially refreshed Dataset is otherwise indistinguishable from a stalled Dataset. *Not reached* is a **rotation outcome, not a skip**: AD-9 forbids a skip, and FR-17's defined order is what makes the phrase precise. The entry's turn has not come, and the report states that fact rather than implies that `sync` passed over the entry (AD-7).
- `sync` commits only the files that `sync` owns, by explicit path — never `git add -A` — so an automated commit never includes an in-progress curation edit (AD-3).
- A dirty working tree elsewhere does not block a sync, and a dirty working tree elsewhere does not enter the sync's commit.

**Description.** Craft Cost is the term that makes the ranking account for failures. The player pays Craft Cost on every attempt. Most attempts produce nothing worth selling, and the player pays Craft Cost on those attempts too. Craft Cost changes during a league, because currency prices change. Therefore `core` computes Craft Cost from synced rates, and nobody configures Craft Cost as a constant.

**Functional Requirements:**

#### FR-26: Compute Craft Cost in valuation, from synced rates

`core` derives Craft Cost. `sync` never stores Craft Cost.

**Consequences (testable):**
- A Craft Recipe is a currency composition. `data/recipes.json` defines each Craft Recipe. `core` computes a Craft Recipe's Craft Cost from synced exchange rates. `sync` never computes a Craft Cost (AD-3).
- v1 contains exactly **one** Craft Recipe: one perfect transmute plus one perfect augment. The file holds a list. Therefore more Craft Recipes need no code change.
- In v1 a Craft Recipe contributes **only a cost offset**. The distribution transform is the identity transform. Therefore the ordering does not change with the Craft Recipe, and two Craft Recipes differ only by the cost that `core` subtracts (AD-17). This is a documented limitation. ### 4.8 Weights File Consumption

**Description.** Probabilities depend on how likely each modifier is to roll. PoE2 does not publish that likelihood, and this app never produces it. This app consumes a file with a defined schema. This app does not care *which* producer satisfies the schema. This app does care that some producer satisfies the schema. The trade API exposes no pool membership, no tier, no item-level availability and no spawn weight. Therefore the Weights File is a **prerequisite** and not an enrichment, and without the Weights File nothing ranks (§7.3). Cadence justifies the separation: prices change every hour, but weights change only when GGG patches the game.

**Functional Requirements:**

#### FR-27: Consume a schema-conformant Weights File and never produce one

`core` reads Modifier Weights from a file that conforms to `WEIGHTS-FILE-SCHEMA.md`. `core` does the normalising itself, and never produces the file — the file is a hard v1 dependency (FR-30; see the release-gate framing in §0).

#### FR-28: Enforce the pool-completeness contract in both directions

The producer obligation and the consumer treatment are two halves of one rule. An implementation of only one half produces a ranking that is wrong and that carries no warning.

**Consequences (testable):**
- **Producer side:** a `(Base Type, slot)` declaring `poolCoverage: "complete"` must enumerate **every** modifier that can roll there **at any item level**. That enumeration includes worthless modifiers, and carries true weights and true `itemLevelMin` values. `weight: 0` means "cannot roll here" and is meaningful. A producer that omits the entry instead breaks the completeness claim. There is no third option. A producer that cannot guarantee completeness declares `partial`.
- **Completeness has two halves, and a producer must satisfy both.** The first half is **every rollable tier**: a `complete` pool enumerates every tier that can roll in that slot at any item level. The second half is **every one of that tier's lines**: a `complete` pool's entry carries every Stat Line the tier's source row publishes, not a subset. Therefore a producer that emits an entry for a tier but drops one of that tier's lines makes the same defect as a producer that drops the tier outright. Without this statement, a producer reading this FR alone can drop the second line of each of the 560 multi-stat rows and still believe it declared `complete` honestly. That omission shrinks **numerators** without touching the denominator, which is the one direction the plain-sum denominator does **not** protect against, because the denominator counts the entry once either way. `WEIGHTS-FILE-SCHEMA.md` states both halves of completeness. AD-11 supplies the underlying fact that one modifier may publish several lines.
- **An unresolved Stat Line does not make a pool `partial`, and a producer must not treat it as though it did.** A line whose `statId` the producer could not resolve is written `statId: null`, and the entry it sits on still counts fully toward `complete`. `statId: null` is data about the source, never a file error and never a completeness defect (§3 *Stat Line*, AD-11).
- **Neither a dropped tier nor a dropped line now has a mechanical check, and that gap is wider than `4.x`'s.** `4.x` had `statLineCounts` standing behind a dropped line within a row, and `cohortTotals` standing behind a dropped row within a family that carried a `modelled-split` entry. `5.0.0` withdraws both. A row dropped from a pool still declaring `complete` **shrinks the denominator and inflates every probability on that Base Type**, which reorders the ranked list. A line dropped from an entry that is otherwise present shrinks **one numerator**, and where that `statId` has a second publisher, does so **silently** and reorders that Base Type too (FR-29). **What stands between the file and either outcome is the producer's `poolCoverage` assertion alone**, which is the same trust already extended to every weight in the file, now carrying more of the weight of the claim than it did under `4.x`.
- **Completeness does not depend on item level.** A tier that only rolls at item level 82 belongs in a `complete` pool, and carries `itemLevelMin: 82`. `core` scopes that tier out for an entry floored below 82 (FR-29). A producer that omits the tier because "we only care about ilvl 75" breaks `complete`. The claim is about the slot, and not about one curator's floor.
- **An unnamed placeholder row still counts.** Where the producer's source publishes a modifier as an unnamed `TBD`, **the modifier exists and carries real spawn weight**. A producer that drops that modifier shrinks the denominator and inflates every other probability on that Base Type. The pool is therefore `partial`, not `complete`. The producer emits the rest of the pool and declares `partial`. The Base Type returns to the ranking when the source names the rows.
- **There is deliberately no field for anonymous weight.** A per-`(Base Type, slot)` scalar entering the denominator but never a numerator was considered and **rejected**. Such a scalar would let a producer hide an arbitrary share of the pool behind a number nobody can check. To add such a field is an architecture amendment, and not a producer convenience.
- This obligation binds an **external project** (§7.3). This document plus `WEIGHTS-FILE-SCHEMA.md` are that project's entire contract. This document states the obligation as a requirement rather than leaves the obligation as a schema footnote, and that statement is what gives the external project something to build to.
- **Consumer side:** a `partial` pool is a *lower bound on the denominator*. Therefore every probability derived from a `partial` pool is an **upper bound**. `core` assigns such probabilities Provenance `absent`, and the Base Type is Unrankable (FR-4). This path is the only path by which `absent` arises. Without this path, the weakest of §3's three Provenance values would be unreachable.
- A Base Type absent from the file entirely is likewise Unrankable. `core` has no other pool source, and `core` must not invent one (AD-17).

#### FR-29: Aggregate weights by tier within an item-level-scoped pool

This PRD specifies how to derive probability exactly. Two implementers cannot diverge.

**Consequences (testable):**
- A Modifier Reference's weight is the sum of the weights of every Weights File entry the reference **contains**, within that same `(Base Type, slot)`. Containment is evaluated on an entry's `lines`, and depends on the reference's kind (AD-5, AD-17). **A line's derived interval has one derivation, and `IMPLEMENTATION-NOTES.md` §1 carries it, binding under AD-0** — this PRD states what containment means and never re-derives the interval:

| Reference kind | Contains an entry when one of the entry's `lines` … |
| --- | --- |
| `banded` | carries `ref.statId`, has a **non-empty** `ranges`, and has a derived interval lying **wholly inside** the reference |
| `valueless` | carries `ref.statId` and has an **empty** `ranges` |

- **Whole-tier, once.** A contained entry contributes its **whole weight, once**. A merely-overlapping entry — one whose derived interval is not wholly inside the reference — contributes **nothing**, and that contribution of nothing is not an error: it is the ruling stated below. A line whose `statId` is `null` can **never** be contained, by either row of the table above, but that line's entry still enters the denominator like any other entry in scope. The `(Base Type, slot)` scoping is not optional. To ignore the scoping is the commonest way that two implementations diverge.
- **Both numerator and denominator are drawn from the same item-level-scoped pool**, scoped to the entry's Item Level Floor `L`: `scoped(base, slot, L) = { entry ∈ pool(base, slot) : entry.itemLevelMin <= L }`. `core` writes the conditional as `P(ref | base, slot, L)`. The conditional is over the **Modifier Reference**, which names a Stat Line (AD-17, AD-5).
- **The denominator has collapsed to a plain sum over entries, and that collapse is the whole of contract `5.0.0`'s consequence for valuation.** One entry is one source row, so there is no group to sum over and nothing left to reconcile:

```
                         Σ { e.weight : e ∈ scoped(base, slot, L) ∧ contains(ref, e) }
P(ref | base, slot, L) = ────────────────────────────────────────────────────────────
                                 Σ { e.weight : e ∈ scoped(base, slot, L) }
```

  `core` never reads `sourceModifierId` to compute this ratio. The invariant — `ΣP(ref) ≤ 1` over a partition — is unchanged, and is now **structural**: the double-counting reading that `4.x` had to rule out by checking one-Cohort-per-group no longer has a shape in the file that could reach it (AD-17, AD-11).
- **Whole-tier containment is the ruling, and the two rejected alternatives are recorded because a builder will otherwise reach for one of them.** Contract `5.0.0` hands the consumer overlapping raw tiers and states no math for them. **Pro-rating** — computing `P(value ∈ band | tier)` from a tier's raw `ranges` — was rejected because it re-sites the producer's withdrawn decomposition inside the browser, where nobody can diff it, and reopens a distinction between measured and modelled Provenance that this round retires. **Whole-tier inclusion** — letting every overlapping tier contribute its full weight — was rejected because it over-counts and inflates that base's `ΣP`. **Whole-tier containment** — a tier only partly covered contributes nothing — is the ruling, stated normatively above.
- **What the ruling costs, stated rather than implied.** The trade search returns the neighbouring tier's tail, and the filter cannot exclude it either, while `core` counts none of that tier's weight in the numerator. Every affected probability is therefore an **understatement**, and the error is uneven across Base Types, so it **reorders** the ranked list rather than shifts it uniformly. Two things **blunt** the damage, and they blunt it in one direction only. First, FR-21 sorts ascending and takes the **cheapest ten**, and a tier excluded **for reaching past the band's ceiling** sits at the top of the band — AD-11 scopes that claim to the ceiling case, and there the population dropped from the numerator is largely the population the price estimate never sees, so the two errors do not compound. Second, the edge-alignment rule below rejects a band whose ceiling reaches into a tier the band does not contain. **A tier intruding at the band's *floor* is the opposite case, and neither thing blunts it.** A scoped same-`statId` tier whose interval covers `ref.valueMin` is not contained, contributes nothing to the numerator, and sits at the **cheapest** end of the priced sample — which is the end the ascending sort takes ten of. There the two errors compound maximally: the band carries the tracked tier's weight while the estimate carries the intruder's price, and below the Payout Threshold the summand truncates and takes the tracked tier's mass out of the sum. That is BQ-1's shape, reached through a band that FR-22 instructs the curator to write and that edge alignment accepts (§10 OQ-21).
- **Neither is a bound, and revision 11 withdraws the claim that they were.** Revision 10 of this document asserted that those two things *bound* the damage. **That assertion is false as stated**, and it is corrected here rather than softened, because a reader who believes the error is bounded will trust an ordering that nothing entitles them to trust. Edge alignment compares a band only against its **own** containment set, so a scoped same-`statId` tier that intersects the band without being contained *and* shares an edge with it is invisible to the check — a **flush intrusion**, which can drop most of a pool's mass while the band aligns perfectly. Non-overlap withdrew with the decomposition, so nothing in the contract prevents that shape. **How far the understatement can run is therefore unmeasured and unbounded, and that is §10 OQ-21** (AD-11). **`[ASSUMPTION: the two mitigations above keep the understatement acceptable in practice for v1, at a frequency nobody has measured. This is an operating bet, not a bound, and OQ-21 is the measurement that would settle it against a real 5.0.0 file.]`**
- A Modifier Reference whose containment set is **empty** under that scope is a **validation error**, not a `P = 0`. The empty set means that the curator tracks a tier that cannot roll on the item being crafted. To contribute zero would hide that fact (AD-17).
- That error is against **`data/tracked.json`**, not against the Weights File. The error is therefore `core`'s, and `core` reports the error the way FR-24 reports a tracked-list failure. The empty-containment-set check is the second of this FR's cross-file checks, together with edge alignment. `core` runs both exactly alike — `web` at load, `sync` at run start — per the ownership clause below (AD-17).
- **The report must name both possible causes, because `core` cannot tell the two causes apart.** The usual cause is the curator's: a reference on a tier that cannot roll at this floor. The other cause is the **producer's**: a file that declares `complete` and dropped a tier or a line. Nothing mechanical now stands behind either cause (FR-28), so both present identically as an empty containment set. To blame the curator unconditionally would send him to hunt a defect in his own file for a pool that is genuinely missing a tier or a line. The error therefore names the reference, names the reference's floor, and states that the scoped pool contains no entry for that `statId`. The error leaves which document is wrong to the reader.
- **That error is only half the dropped-line story, and the half the error misses is the dangerous half.** The error fires only where the dropped Stat Line's `statId` had a **single** publisher. Where a **second Source Modifier publishes the same `statId`** — which AD-11 expressly permits (§3 *Eligible Pool*) — the other modifier still supplies entries. The containment set is then **not** empty, and `core` reports **nothing at all**. The reference's **numerator** silently loses that modifier's share. The probability deflates on that Base Type alone, so the deflation **reorders** the ranked list rather than shifts the ranked list uniformly. The Base Type still reads `complete` and still counts as covered under FR-4, because both of those are declarations rather than content. **Nothing now stands behind the silent case** — `statLineCounts`, the one thing that stood behind it under `4.x`, retired with the machinery it guarded (FR-27, FR-28). A builder who reads the empty-containment-set error as a complete defence reads a check that, for this case, cannot fire (AD-17, AD-11).
- **Treatment of an empty containment set as an error is deliberately harsher than FR-27's treatment of a Base Type missing from the file entirely**, which is merely Unrankable. A missing base is an absence that the curator can see in the Unrankable group. An unrollable band is a *silently* empty summand in a list that otherwise looks healthy.
- **A `banded` reference's edges must be edge-aligned to the scoped pool's contained tiers, retargeted from cell edges to tier intervals and now doing more work than before.** A requirement that `valueMax` is *present* closes only the **syntax** of an open top. Consider a curator who writes `valueMax: 9999`, or who writes `valueMin: 0` against a pool whose lowest tier starts at 40. That reference is schema-valid, passes containment, passes the empty-set check above, and passes FR-16's overlap predicate. `core` then sums more than one tier's weight, while FR-21's stat filter is **operationally min-only** and prices the cheapest tier in the span. That is BQ-1 verbatim, re-entered through a sentinel, with its worst consequence intact: below the Payout Threshold the blended summand truncates out of the sum and takes the jackpot mass with it (FR-1). The hole exists symmetrically at the **bottom**. To close one edge only would close half of a symmetric hole. So, for every tracked **`banded`** reference — a `valueless` one has no edges to align — these two conditions hold over its containment set under the item-level scope:

```
ref.valueMin == min { interval(line).min : line ∈ contained(ref) }
ref.valueMax == max { interval(line).max : line ∈ contained(ref) }
```

- A reference must begin exactly where its lowest contained tier begins and end exactly where its highest contained tier ends. A sentinel ceiling above the pool's top tier fails that rule, and a sentinel floor below the pool's bottom tier fails that rule too. Edge alignment also catches the **new mistake that whole-tier containment creates**: a ceiling that reaches partway into a neighbouring tier without wholly containing it, which is exactly the shape that would widen the understatement's gap beyond the two mitigations stated above. Like the empty-containment-set rule beside it, this rule is a **validation error against `data/tracked.json`**. It is not a wide band, and it is not a file error. The worked accept/reject cases, and the warning that the check is floor-scoped, are `IMPLEMENTATION-NOTES.md` §2.4, binding under AD-0; the empty-containment-set rule's is §2.5.
- **The straddle rule is withdrawn, and the withdrawal is forced rather than chosen.** With entries back to tiers and no partition cutting the value axis, no band can contain one tier's interval without either clipping or excluding its neighbour — edges are closed at both ends, and no pair of edges isolates a tier that overlaps its neighbour without touching it. Retaining the straddle rule would reject every crafted configuration on the 53 of 63 item classes that carry a multi-`#` modifier. **Non-overlap is withdrawn with it**, for the same reason it was only ever a proxy for the straddle rule it rode on.
- **Edge alignment is a cross-file check. `core` defines the check once, and every component that holds both files runs it.** The check reads `data/tracked.json` and `data/weights.json` together, so the check belongs to the component that holds both files — and **two** components hold both. `web` runs the check **at load**, which is what keeps an unrankable configuration out of the view. **`sync` holds both sides as well.** `data/tracked.json` is `sync`'s declared workload, and `sync` already reads the Weights File to validate its ids (FR-24). `sync` therefore runs **the same `core` check as a run-start gate**, after `sync` acquires the lock and before any priced entry consumes budget. That gate is in the same class as FR-24's catalogue check and FR-32's league check. This follows FR-24's pattern, which assigns a check by which component holds the file: one definition, two callers. **Two of AD-17's four cross-file checks are this FR's** — edge alignment and the empty containment set — and the straddle rule that once made a third of *these* is withdrawn. **The other two are FR-16's**, `coOccur` and kind agreement. AD-17 defines all four once in `core`, and AD-12 runs all four as one `sync` run-start gate (FR-14). A builder who reads this FR's pair as the whole register implements half the gate. A check re-implemented in either shell would be the divergence that this rule exists to prevent (AD-17, AD-12).
- **In `sync`, a failure aborts the run.** `sync` records the failure in the Sync Report and exits non-zero. `sync` leaves the progress file untouched. The configuration is wrong, not busy. FR-19's quiet exit on a held lock is therefore not the precedent here. FR-32's loud league failure is the precedent. `sync` never prices around the misaligned entry and never skips the misaligned entry silently into a partial Chunk (FR-25).
- **The `sync` gate prevents a wasted refresh, not a wrong number.** The gate is therefore an ordering rule rather than a further check. If the check were `web`'s alone, `sync` would price `min..9999` on Monday and `core` would refuse the configuration in the browser on Tuesday. The budget would be gone. The observation would be written, committed and ranked, and the row would be unrankable anyway. The defect would surface a day after `sync` spent the requests that proved the defect (AD-17, AD-12).
- **`core` evaluates alignment under the scope, and alignment is floor-dependent by design.** The containment set shrinks as the floor drops. A reference can therefore align at one floor and fail at a lower floor. That failure is the rule working: the curator has written a ceiling that the scoped pool cannot reach, which is the same defect as the empty-containment-set case. FR-16 and FR-22 give a Base Type exactly one crafted Item Level Floor. `core` therefore evaluates the check once per Base Type and never ambiguously. A builder who computes the containment set **unscoped** silently accepts exactly the references that this check catches (AD-17).
- Every Weights File entry carries `itemLevelMin`. An entry without `itemLevelMin` is a hard file error (FR-27), because the scoping above has no other source for the item level.
- `P(Combination)` treats prefix and suffix as independent draws: `P(prefix) × P(suffix)`. An absent affix takes `P = 1`. Mod-group exclusion makes the second draw weakly conditional. This PRD defers that refinement (§7) and does not overlook it.
- **A tier cannot be isolated, and a band spanning two tiers is legitimate.** Tiers overlap freely under `5.0.0`, and there is no partition left for one band to violate by spanning a boundary. What a band must not do is reach partway into a tier without wholly containing it — that is the edge-alignment failure above, not a file error and not a third cross-file check.
- `core` models the craft as a craft on a base at **exactly** the entry's Item Level Floor, while the `ilvl >=` search returns a slightly higher-level superset. This PRD accepts and records that difference. To correct the difference would need an exact-item-level filter that the trade API does not offer (AD-17).

#### FR-30: Depend on an externally produced Weights File as a v1 prerequisite

v1 ranks against a real file that satisfies the real contract. The external scraper project produces that file. **There is no fallback.**

**Consequences (testable):**
- The Weights File is a **release dependency**, not an enrichment (§7.3). The Weights File supplies pool membership, tier value ranges, `itemLevelMin` and weights. The trade API supplies none of those four, so nothing in this system can derive what the file carries (AD-11, AD-25).
- Until a conforming file exists, **every crafted Base Type is Unrankable** (FR-4). That is the honest outcome rather than a degradation to design around. There is no other pool source, and `core` must not invent one (AD-11, AD-17). Raw Bases are the exception and rank without the file, since a Raw Base carries no probability term (FR-3). What survives a missing file is therefore a white-base price list, not the product.
- A **uniform-prior variant** — every entry `weight: 1`, `weightSource: "absent"`, `producer.id: "uniform-prior"` — remains a legal file and a valid *weighting* placeholder. The variant is never a *sourcing* placeholder. The variant must still carry genuinely sourced pool membership and `itemLevelMin`, which are exactly the two fields that nothing can fake.
- Whatever the file's weighting, the system exercises the probability code path from day one. The ranking formula does not change shape when measured weights arrive.
- Every figure that a `weightSource: "absent"` entry influences carries Provenance `uniform-prior` (FR-10). FR-11's global caveat applies for as long as any such entry remains.
- Where the producer cannot guarantee completeness, the producer emits the affected `(Base Type, slot)` with `poolCoverage: "partial"`. The producer does not pretend to completeness (FR-28). The system measures the resulting coverage before any view work (FR-4, §10 BQ-3).

### 4.9 League Lifecycle

**Description.** Three or four league resets a year wipe prices entirely. The tool is least useful at league start, which is when the knowledge is worth the most. League resets are the central threat to the one-year horizon. The requirement is not to survive a league reset gracefully. The requirement is to fail *honestly*. An empty ranking is correct. Last league's numbers served as current are not correct. Realises UJ-6.

**Functional Requirements:**

#### FR-31: Refuse to value an observation from a different league

`core` treats a Price Observation from any league but the active one as absent rather than as stale-but-usable. Realises UJ-6.

**Consequences (testable):**
- The active league is configuration in `data/config.json`. Every Price Observation records the league it was observed in (AD-19).
- **`data/config.json` carries exactly three things: the active league, `minChunkSearches`, and `schemaVersion`.** `core` and `sync` read the first. **Only** the load-time `pinned`-cap validation in `sync` reads the second, and the inequality it evaluates is `IMPLEMENTATION-NOTES.md` §6's, binding under AD-0 (FR-19). NFR-8 requires the third of every artifact. The file is player-owned (NFR-5). `web` fetches and validates the file on load (FR-33), even though `web` reads neither of the first two for behaviour. **The file is not a settings bag. A fourth field is an architecture amendment**, not a config addition (AD-19, AD-7).
- `core` refuses to value an observation whose league differs from the active league. `core` treats such an observation as `not-yet-synced` with reason `league-mismatch` (FR-9) rather than as stale-but-usable.
- A league change is a config edit plus a natural re-sync. The ranking is honestly empty until data arrives, and the ranking refills without anyone rewriting the Dataset.
- `sync` does **not** filter the Dataset on write. League filtering happens once, in `core`, so a league change does not blank the site while a re-sync runs (AD-19). `[ASSUMPTION: this makes a league change a config edit plus a natural re-sync with no manual purge. It follows from AD-19 and AD-19 but has not been exercised against a real reset.]`

#### FR-32: Validate the configured league against the live leagues endpoint

`sync` checks that the configured league is real before `sync` spends any budget against that league.

**Consequences (testable):**
- `sync` validates `data/config.json`'s league against the live leagues endpoint before spending any budget, and refuses to proceed on a mismatch (AD-19). The player-visible consequence is covered by FR-31: the tool fails loudly and ranks honestly-empty rather than value against the wrong league.

### 4.10 Dataset Delivery

**Description.** How data reaches the view looks like an implementation detail, and it is not one. The delivery method decides whether a sync commit refreshes the site on its own or needs an application rebuild. That decision in turn decides whether the daily refresh is a background fact or a chore.

**Functional Requirements:**

#### FR-33: Fetch published artifacts at runtime as a consistent set

`web` reads its data at runtime rather than at build time.

**Consequences (testable):**
- `web` **fetches exactly eight artifacts** at runtime as separate cache-busted requests. `web` never bundles the eight artifacts into the JS, so a sync commit updates data without a rebuild of the app (AD-24). The eight artifacts are `dataset.json`, `sync-report.json`, `weights.json`, `recipes.json`, `tracked.json`, `config.json`, `catalogue/stats.json` and `catalogue/static.json`.
- The two catalogue files are what let the view render a `statId` and a currency as their human text **without a runtime call to pathofexile.com**, which is forbidden (AD-15, AD-25). **The two files carry different halves of that job, and only one of them has ever carried stat text.** `catalogue/stats.json` supplies a `statId`'s display text; `catalogue/static.json` supplies a currency's. Without `catalogue/stats.json` the view would show raw stat ids, which is the same list in a form the player cannot read.
- **v1 renders a currency as text, and not as an icon** (UX memlog 86). The view defines no icon token and no icon component for a denomination. **What `catalogue/static.json` is fetched for is the denomination's own label.** Verified live 2026-09-13, `/api/trade2/data/static` returns each currency's id, its label and an image path, and carries **no stat text at all**; `web` prints the label from that file rather than hardcoding a name the catalogue already owns, which is what keeps the artifact one the view reads rather than one the view merely fetches. **Currency id validation is not `web`'s share of this file** — that check is `sync`'s, against `data/currencies.json`, which `web` never fetches (AD-3, AD-24). The cost of dropping the icon is small by construction: FR-23 normalises every price to a single denomination, so there is at most one denomination on screen and an icon would distinguish nothing. A future multi-denomination view would revisit this, and would need no new artifact — the icons are already in the file that is already fetched.
- **FR-33's prohibition binds a request the page makes on its own behalf, and not a navigation the player chooses.** The forbidden thing is a fetch, XHR or WebSocket to pathofexile.com that the page's own rendering depends on — which is precisely what the two catalogue files exist to remove (AD-15, AD-25). A link the player clicks, which opens the trade site in a new tab (`target="_blank" rel="noopener"`), is a different act: the page issues no request, the page's rendering does not depend on the result, and the page is unchanged when the tab closes. **The view may therefore carry outbound links to the trade site**, and `{components.trade-link}` is v1's only one. The link's URL form is `IMPLEMENTATION-NOTES.md` §5.4, binding under AD-0.
- **This does not weaken AD-15, and the boundary is worth stating once.** The link adds no write path, no authenticated request, no server-side state and no credential. It also does not let `web` mint a trade-site search at view time: the search identifier is `sync`-sourced (see FR-21's `lastSearchId`), because minting one would require exactly the runtime call this consequence still forbids. That is the reason the field is persisted rather than computed.
- **The view offers a trade-site link exactly where the stored identifier is usable, which is a test on data and never on Price State.** `web` renders `{components.trade-link}` for a Tracked Entry if and only if that entry's `lastSearchId` is present **and** its `lastSearchLeague` equals the active league of `data/config.json`. Both halves are load-bearing:
  - **Presence** covers the never-attempted cases honestly. A `not-yet-synced` entry with reason `never-synced` has no identifier. So does an entry that was `unresolvable` on first sight (FR-24). A rule keyed on Price State would promise a link for the second and a builder would have nothing to render.
  - **League agreement** is what stops the page handing the player a link into the previous league's search. FR-31 already refuses to *value* such an observation; a link that survived the refusal would reintroduce exactly the stale answer the honest-empty state exists to prevent, in the one affordance that leaves the page. After a league reset the links disappear with the prices and return as the rotation refills.
- **A link is never offered on a `pruned` tombstone.** A `pruned` entry is dead by the curator's own decision, and an invitation to re-examine its market undercuts the reason it was pruned (FR-15, AD-12).
- **A stale identifier needs no further rule, and that is a consequence of the design rather than an omission.** An identifier is exactly as old as the attempt that produced it, and FR-12 already puts that attempt's age on the row. A player following a link from a row marked stale is told, before the click, how old the thing behind it is. **Expiry is stronger than that: it is a state this view cannot normally reach.** GGG expires a trade search roughly six months after its last use, and a temporary league's whole lifetime is shorter than six months — so an identifier that passes the league test above is necessarily younger than the expiry window (AD-24). **The one configuration that breaks the argument is a permanent league**, where `lastSearchLeague` can agree with the active league indefinitely. That case is accepted rather than handled: the cost is one wasted click onto the trade site's own explicit *"search is no longer valid"* page — not an empty result — which misleads nobody, because the page never claimed the search was live and FR-12 put the row's age on screen before the click.
- **Four** files are deliberately **not** fetched. `sync-progress.json` is internal to `sync`. Only `sync` needs `catalogue/items.json` and `catalogue/filters.json`. **`data/currencies.json`** is a sync-side workload declaration that `web` has no use for (AD-3, AD-24). The eight are the complete set. A ninth artifact is an architecture amendment.
- **Two rules depend on that last omission rather than merely tolerate it.** The Base Type cross-check of FR-24 belongs to `sync` because `web` cannot read `catalogue/items.json`. The load-time `pinned` cap of `IMPLEMENTATION-NOTES.md` §6 belongs to `sync` because `web` cannot read `data/currencies.json` and cannot know what the currency step costs in searches (FR-19).
- Each artifact carries `schemaVersion`, and `web` validates each artifact on load. `web` refuses to render an invalid artifact rather than degrade (AD-3).
- **"Refuses to render" applies to a *schema-invalid* artifact.** `web` reports a schema-valid artifact that fails a **cross-file policy check**, and never meets such a failure with a file-level refusal. The `pinned` cap of `IMPLEMENTATION-NOTES.md` §6 is such a check, and `sync` alone owns it (FR-19). Read together with the refusal rule and without this qualification, a builder could land on a refusal to render the entire site because the player pinned one row too many. That refusal would be a total outage of a product whose premise is a static page that always renders, over a sync-budget concern that the browser cannot even evaluate. FR-29's edge-alignment and empty-containment-set errors are cross-file checks of the same class, as are FR-16's `coOccur` and kind-agreement checks — AD-17's four. `core` defines all four, and **`web` reports them at load rather than meets them with a file-level refusal**. The same four abort the run in `sync`. That abort is not an exception to this rule but the other half of the rule: a shell that can still stop before it spends anything should stop, and a shell that can only render should render (FR-29, AD-3, AD-24, AD-7, AD-17).
- `web` renders from a **single consistent set** and does not mix artifacts across a refresh (AD-24).

## 5. Cross-Cutting NFRs

- **NFR-1 — Zero network in the test path.** No test at any level makes a real network call. MSW runs in `onUnhandledRequest: "error"` mode. An unfixtured request therefore fails loudly and does not escape (AD-13). This is the hardest requirement in the brief. It lets an agent iterate against a service that would otherwise rate-limit the agent into uselessness. It also makes a red test mean "the code is wrong" rather than "GGG was slow."
- **NFR-2 — Fixtures are real captured responses.** A fixture is a committed real payload, never a hand-written mock. Re-recording is a separate command that a human invokes explicitly. Re-recording is never part of a test run. The fixture diff that re-recording produces is the mechanism that makes GGG's changes visible (AD-13).
- **NFR-3 — Determinism.** Valuation is pure. Time, randomness and configuration enter only as passed-in values. No test depends on wall-clock timing. A test of rate-limit backoff injects header values and does not wait (AD-1, `AGENT-WORKFLOW.md`).
- **NFR-4 — Parallel worktree development.** Packages own disjoint directories with a one-way acyclic dependency graph. CI enforces the graph mechanically, rather than review enforcing it. Two agents in two packages therefore touch no common file (AD-1). `contracts` changes are **serialised and land alone, first**, and dependent work rebases onto those changes. `contracts` is the one package everything depends on, so a change there causes a broad rebuild and a likely conflict. **No worktree runs a live sync or a live catalogue refresh**: only the scheduled invoker on the player's machine runs `pnpm sync`, and `pnpm catalogue:refresh` is a human act on a game patch (FR-24). An agent that verifies sync behaviour uses `pnpm sync:dry`. `pnpm sync:dry` runs the full pipeline against recorded fixtures and writes nowhere. These partitioning rules are `AGENT-WORKFLOW.md`'s. AD-1 supplies only the dependency graph that the partitioning rules rest on.
- **NFR-5 — One writer per file.** Every shared file has exactly one writer. Hand-owned inputs belong to the player, and sync-owned outputs belong to the syncer. An agent that needs different data uses a fixture, never an edit (AD-3).
- **NFR-6 — Read-time budget.** A full ranking pass takes under 100 ms (§4.1).
- **NFR-7 — Static delivery, zero upkeep.** The view is a static bundle that CI deploys. There is no server to patch, no secret material, and no credential that expires (AD-15).
- **NFR-8 — Schema versioning at every trust boundary.** Every published artifact and input file carries `schemaVersion`, and the consumer validates the file on load. A consumer refuses an unknown major version rather than guessing. The producer validates before it writes (AD-3, and the spine's Consistency Conventions).
- **NFR-9 — Third-party citizenship.** Requests identify the tool and a contact address, pace from live rate-limit headers, and honour `Retry-After` (AD-8). The product must keep API access. This is a standing requirement, because the product depends entirely on API access (R-7).
- **NFR-10 — Accessibility floor.** AD-24 requires that colour alone must not carry the distinctions AD-10 mandates. This PRD **extends** that rule to every product-meaningful distinction — Price State (FR-9), crafted versus Raw Base (FR-3) and Provenance (FR-10). The reason AD-24 gives applies identically to all three distinctions. `[ASSUMPTION: the extension beyond AD-24's literal scope is this PRD's, not the spine's.]`

## 6. Non-Goals (Explicit)

- **Producing modifier weight data.** The scraper is a separate project. The app consumes a file and is indifferent to the producer of that file (AD-11). This is a non-goal for *this repository*. The file is not an optional input: the file is a release dependency (§7.3).
- **Advising whether to augment an item already in hand.** The player makes this decision dozens of times a session, far more often than the player reads the ranked list. The decision is excluded by design. The player can already tell that an increased-stun-threshold roll is dead. This decision is the strongest v2 candidate if the pickup list proves its value.
- **Loot filter export in v1.** PoE2's filter syntax has no working equivalent of `HasExplicitMod`. A generated filter can therefore express base type, item level and rarity, but never modifier Combinations. Loot filter export remains a **roadmap item** that automates the base-name half of the knowledge. It has a permanent ceiling: the modifier half stays in the web view. The web view is therefore the permanent product rather than an intermediate step toward another product. The brief's "eventually I won't have to memorize anything" outcome is not achievable.
- **Rare items.** Magic only: at most one prefix and one suffix.
- **Accounts, sharing, per-user preferences, anything multi-user.** Any requirement that appears to need a backend is escalated and not implemented (AD-15).
- **Visual design beyond an off-the-shelf framework.** Appearance is explicitly not a priority.
- **Price history features.** Git carries the history through sync commits. No v1 feature reads that history (AD-19). UJ-5's "returned no listings all league" judgment is therefore the player's own recollection plus the current Price State. That judgment is not a trend that the tool renders.
- **Market scanning as candidate generation.** Rejected on both shallowness and cost — see the brief's addendum.
- **Sell-through speed as a ranking term.** Considered and rejected: the player was explicit that sell speed is not a factor.
- **Ranking on variance, median outcome, or an exposed risk preference.** At ~144 crafting decisions an hour, attempt volume makes mean-based math sound.
- **Discovering Combinations the player did not think to track.** Recorded as Risk R-2 (§9), and not addressed.

## 7. MVP Scope

### 7.1 In Scope

- Magic Base Types — one prefix, one suffix — at per-entry Item Level Floors derived by the Accepted Tier rule (FR-22).
- Raw Bases at item level 82, threshold-truncated like any other outcome.
- Ranked Base Type list, bounded for readability, with chase Combinations, expandable to the full tracked Combination list including tombstones.
- Player-set Payout Threshold, re-ranking at read time.
- Background sync: unauthenticated, rate-limit adaptive, bounded, resumable, with a defined Refresh Rotation.
- Four-state pricing with reasons on `not-yet-synced`, and unknowns segregated from the ranking.
- Provenance and per-row freshness throughout, plus the global uniform-prior caveat.
- Curation through hand-edited committed files, surfaced read-only in the view with tracked-list age.
- One Craft Recipe with cost computed from synced rates.
- A defined Weights File **schema**, with its pool-completeness contract enforced in both directions. The **file** itself is an external deliverable, and is not in scope here (§7.3).
- Divine normalisation at the sync boundary, with exchange observations carried in Provenance.
- League-scoped observations with an honest empty state across a reset.

### 7.2 Out of Scope for MVP

- **A second Craft Recipe** — AD-17 makes ordering recipe-invariant in v1. A second recipe therefore adds a cost column and no ordering information. Revisit when distribution mechanics exist.
- **Producing Modifier Weights** — v1 ranks on whatever the scraper project delivers, gated by the coverage measurement of §10 BQ-3. The ranking improves as the file improves, and the app does not change. What is out of scope is this repo producing weights. The app having good weights is not out of scope.
- **Authenticated sync** — a quantified lever that would raise the rate limit. The cost is that authenticated sync reintroduces a credential that expires. Revisit only if a full refresh must exceed ~1,500 searches.
- **Mod-group conditional probability** — FR-29 assumes independent affix draws. Deferred until measured weights make the error estimable.
- **Pricing a deliberate conjunction of co-occurring stats** — a curator may genuinely want *"this base carrying both Stat Lines of this hybrid modifier"* as one priced outcome. v1 cannot express that outcome. The two Stat Lines share one Source Modifier — under `5.0.0`, one entry's `lines` — and one weight. FR-16 therefore rejects tracking the two Stat Lines as two entries, and there is no third form that means *both at once*. This record matters because the deferral is **why** FR-16 rejects a configuration that a curator will plausibly try, and **why** that rejection is not a defect (FR-22, AD-11).
- **Coarser fallback pricing for zero-listing Combinations** — widening the search to "base + this prefix, any suffix" as a marked estimate. Held as the named option if the unknown bucket proves unusable. `[NOTE FOR PM]` This is the likeliest thing to be missed if `no-listings` turns out to be a large fraction of the Tracked List. Check after the first full refresh (§10 OQ-6).
- **Spawn-weight disambiguation of the unknown bucket** — use of modifier rarity to separate "rare and unlisted" (plausible jackpot) from "common and unlisted" (junk). This is the only identified route that actually *resolves* a `no-listings` entry rather than segregates it, and it is contingent on measured weights arriving. It is the reason the weights deferral above has a cost beyond provenance labelling.
- **Re-seeding the Tracked List from community sources** — spawn weights for rarity, build popularity for demand. This is the most promising answer to Risk R-2, and the single largest gap v1 leaves open.
- **Repository split for the weights schema** — deferred until the schema stops moving. Extraction is then mechanical. `5.0.0` is the third breaking revision this schema has had in seven days.
- **A hosted syncer** — AD-7 makes a hosted syncer a configuration change rather than a rewrite. Revisit if a day-stale Dataset becomes intolerable.
- **Observability beyond the Sync Report** — a committed structured report is the whole story. There is no metrics stack.
- **Consumer-side pro-rating of an overlapping tier** — computing `P(value ∈ band | tier)` from a tier's raw `ranges`, rather than the whole-tier containment this round rules on (§3 *Eligible Pool*, FR-29). Rejected for now because it re-sites the producer's withdrawn decomposition inside the browser, where nobody can diff it, and because it reopens a Provenance distinction this round retires (§3 *Provenance*). **Gated on the measurement below**: pro-rating is worth adopting only if the containment understatement it would fix turns out to matter.
- **Measuring the understatement whole-tier containment produces** — §3 *Eligible Pool* and FR-29 state that a partially-overlapped tier's dropped weight understates every affected probability, unevenly, and that the residual is unmeasured. This item is the measurement: how large the understatement is against a real conforming file. **This is the cheap item of the three, and it gates the other two.** Revisit when the first conforming `5.0.0` file lands. **Revision 11 withdraws this item's original premise.** It was written on the assumption that the error is bounded and that the measurement would only size a residual inside known limits. FR-29 now records that neither mitigation is a bound and that a flush intrusion escapes both, so the measurement is answering a live question rather than sizing a known one: **how often that shape occurs, and how far it runs when it does**. The question is §10 OQ-21, owned by the spine with the player, and the deferral of the two items above is only as safe as OQ-21's answer turns out to be.
- **A mechanical guard on a dropped tier or line** — `5.0.0` withdrew `cohortTotals` and `statLineCounts`, and nothing now stands behind a source row or a Stat Line the producer's pipeline silently drops (FR-27, FR-28, FR-29). A guard here would need the measurement above first, to know whether the gap it withdrew is a gap worth re-closing at the cost of asking the producer to build something again.

### 7.3 Release Dependencies

One dependency sits outside this repository, and that dependency gates the release rather than merely enriches it. This section states the dependency, because a prerequisite left implicit inside an FR is discovered only at integration.

- **The Weights File, from the external scraper project (FR-30).** The Weights File supplies pool membership, tier value ranges, `itemLevelMin` and weights. The trade API supplies none of those four things (AD-25). Until a conforming file exists, every **crafted** Base Type is Unrankable (FR-4), and what remains is a Raw Base price list rather than the product. The dependency is **accepted rather than worked around**. The alternative is a locally generated file, and a locally generated file cannot honestly source the two fields that matter. **What is verifiable about the project's state is the contract, not the project's progress** — which version a file must satisfy, stated below at *A second breaking contract revision* (FR-27). The contract is the fact to plan against. Any characterisation of how near completion the project is would be undated the moment someone wrote it.
- **Its first gate is a measurement, not a delivery.** Pool coverage across the Tracked List is measured before any view work begins, and the result binds a layout decision — **FR-4 states the bands normatively** (§10 BQ-3 carries the argument). A file that arrives is not the same as a file that covers enough. The measurement is **not spent once**: the measurement recurs on every regeneration, and the bands bind on every measurement (FR-4).
- **Its second gate is an open question, owned by the same project.** **§10 OQ-12** asks which single quantity the trade stat filter compares for a multi-`#` modifier, and whether the filter accepts a non-integer `min`/`max`. OQ-12 is blocking for **correctness**, not for building. A producer that picks the wrong quantity emits a file that validates and prices the wrong population, silently, across 53 of 63 item classes. A file that covers enough is not the same as a file whose edges mean what `sync` thinks they mean.
- **A second breaking contract revision has landed against a near-complete producer.** The contract moved 3.0.0 → **4.0.0**, so a 3.0.0 file in flight is **refused at load** (FR-27). To satisfy 4.0.0, that project must add two things: a **`sourceModifierId` on every entry**, and **group consistency** — a source row's exploded Stat Lines must carry the source row's full weight, and their per-`statId` sums must agree. This PRD is the document that the project's owner reads for the version number. That is why this PRD states the version number here rather than leaves the version number to the contract alone (AD-11).
- **The contract then moved to `4.1.0`, a non-breaking minor that did not re-gate the release dependency**, before moving again. `4.1.0` was a conforming superset of `4.0.0`, and its optional `statLineCounts` declaration was effectively mandatory for any producer handling multi-stat rows, because it was the only check standing behind a silently dropped Stat Line.
- **A third breaking contract revision has landed, and this one *reduces* what the producer must build.** The contract moved `4.1.0` → **`5.0.0`** on 2026-09-18, withdrawing the value-cell decomposition, `cohortTotals`, the per-`statId` group-consistency check, `statLineCounts`, the `kind` field and band non-overlap entire. A `4.x` file is not a conforming `5.0.0` file, and a `5.0.0` file is not a conforming `4.x` file — the contract is breaking in **both** directions (FR-27). Unlike the first two breaking revisions, which asked the producer to build more, `5.0.0` asks the producer to build **less**: it reports poe2db's tier weights and stat ranges as published, plus trade-API identity, and nothing else. **The second gate has widened, and a third has appeared.** OQ-12's quantity question now binds `core`'s own derivation as well as the producer's, because `core` computes the filter-comparable interval that `4.x`'s producer used to compute (FR-21, FR-29). The third gate is **§10 OQ-19** — whether a Stat Line ever carries three or more `#`, which would make `core`'s derived edge inexact and fail edge alignment permanently. Both gates are blocking for correctness, not for building, exactly as OQ-12 always was.
- **It recurs on GGG patch cadence**, alongside the Trade Catalogue refresh (FR-24). Neither the Weights File nor the Trade Catalogue is on the Chunk path. A stale Weights File degrades Provenance, and a stale catalogue degrades id validation and display text. Neither stale file breaks the app, and both surface as a reviewable diff.
- **`partial` is a recurring state, not a transitional one.** A patch introduces modifiers that the producer's source publishes unnamed. The producer must drop those rows, and must correctly declare the affected pools `partial` (FR-28). **Freshly scraped classes may therefore go Unrankable immediately after a patch, until the source becomes current.** This is a known operating cost of the decision to decline an anonymous-weight escape hatch. It is also why coverage is re-measured and published rather than measured once (FR-4, FR-25).

## 8. Success Metrics

Behavioural, not numeric. There is one user, and instrumenting the tool would be more work than the signal is worth. Each metric is therefore observed by the player's own recollection — the only instrument available.

**Primary**
- **SM-1: The trade site stays closed mid-session.** The player stops opening the trade site to price-check while mapping. Validates FR-1, FR-2, FR-8.
- **SM-2: The mental top-five goes away.** The player stops keeping a list of chase bases in his head. Validates FR-1, FR-6.
- **SM-3: A league start costs days, not weeks.** The list is useful within days of a reset rather than after weeks of relearning. Validates FR-31, FR-32.
- **SM-4: The list holds up against reality.** Chase decisions made from the list match what actually sells. The player judges this by noticing that his sales agree with the list, because the tool observes no sale (Risk R-1). Validates FR-21, FR-1.

**Secondary**
- **SM-5: The tool is still running in a year.** No credential expired. No server needed a patch. No maintenance task was skipped until something broke. Validates NFR-7, FR-20.
- **SM-6: Agents ship without a human unblocking them.** Development proceeds with tests passing offline and no live API in the loop. Validates NFR-1, NFR-2, NFR-4.

**Counter-metrics (do not optimise)**
- **SM-C1: Searches per full refresh.** A larger Tracked List makes the tool appear comprehensive and makes a daily refresh impossible: ~10,000 searches would need ~4× the ~2,400 searches a day the measured rate limit allows. Held at ~1,500 **searches**, which is the quantity the rate limit actually constrains. A count of entries would miss a curator who splits one entry into two bands to isolate a jackpot tier. That split costs a second search while the entry count looks unchanged (FR-14). Counterbalances SM-4.
- **SM-C2: Refresh frequency.** A faster refresh spends budget that retries, currency rates and a second recipe need, and prices are stable at daily resolution. Counterbalances SM-1.
- **SM-C3: Number of ranked Base Types shown.** A longer list is not a better one. Bounded by FR-5. Counterbalances SM-2.
- **SM-C4: Apparent confidence.** Rendering `uniform-prior` figures as cleanly as measured ones would make the tool feel more authoritative and be more dangerous. Counterbalances SM-4, and is why FR-10 and FR-11 exist.

## 9. Risks

R-1 through R-6 are carried from the brief, which named them and did not solve them. R-7 is carried from the architecture. v1 closes none of them.

- **R-1 — Listings are supply, not demand.** Every price is what someone asks, filtered to be plausible. **No sale is ever observed.** The manual loop that the tool replaces had a correction that the tool discards: the player actually sold things and learned the result. Mitigation is honesty only (FR-13), not correction.
- **R-2 — The tool cannot discover what it is not told to watch.** A Combination that becomes valuable mid-league stays invisible. The list needs periodic deliberate review rather than unattended running (FR-18). Re-seeding from community sources is the identified answer, and re-seeding is out of v1.
- **R-3 — `measured` weights will carry the same listing bias.** Community weight sources derive from parsing trade listings, which skew toward desirable and higher-tier modifiers. `provenance: "measured"` therefore means *measured by someone*, not *ground truth*, and the honesty apparatus must not imply otherwise. This bias also independently validates FR-21's ascending sort — the same reasoning poe2db uses when it parses lowest-value listings.
- **R-4 — Request budget is the permanent binding constraint.** Every Tracked Entry costs a search every refresh. Discipline is an operating requirement, not a one-time tuning exercise (SM-C1).
- **R-5 — Zero-listing Combinations are unresolvable in v1.** A Combination with no listings is either a jackpot or junk, and listings cannot distinguish the two cases. Segregation (FR-9) keeps such Combinations out of the ranking without resolving them.
- **R-6 — League and patch churn.** Resets wipe prices, and patches move the modifier data underneath. The tool is least useful at league start, which is when the knowledge is worth most. This is the central threat to the one-year horizon.
- **R-7 — Every endpoint the product depends on is undocumented.** GGG's developer documentation covers the OAuth API and makes no mention of the trade or `trade2` endpoints. Search, fetch and all four catalogue endpoints are therefore unsupported surface that happens to work, and they may change or close without notice or deprecation (AD-8). Nothing in the product can prevent that change. What the product does instead is make a break **loud and cheap**: one governed client (FR-20), committed fixtures whose re-record diff exposes a reshape (NFR-2), a committed catalogue whose refresh diff exposes a rename (FR-24), and no user-facing path that calls the API live (NFR-7). Recorded so that nobody rediscovers the risk as a surprise.

### Open, and owned outside this repository

Two questions are live, and this document deliberately does not answer either. Both are facts about the trade API or its data, and whoever builds against them can measure the fact. The weights scraper project is the party that must measure each fact before the weights scraper project can emit a correct file.

12. **OQ-12 — Which quantity does the trade stat filter compare for a multi-`#` modifier, and does it accept non-integer edges?** *"Adds # to # Lightning Damage"* rolls two numbers, and the filter compares one derived value — average, first, second, sum or span. Band edges must be expressed in **that quantity and no other**. FR-21 passes the band edges into the filter, and FR-29 counts the population that comes back (AD-11, AD-16). The evidence that the quantity is an average is indirect but real: a tier edge of `56.5` can only arise from averaging two integers, which puts the value lattice on half-integers. Two facts are unconfirmed — **which quantity**, and **whether the filter accepts a non-integer `min`/`max`**. A third question follows from those two facts: what `sync` should do with a half-integer edge if the filter turns out to be integer-only. `sync` could round the edge, and then silently reprice a different population. `sync` could reject the edge at load. `sync` could refuse the file. **Consequence of getting it wrong:** a file that validates and prices the wrong population, silently, across 53 of 63 item classes. Every price on those item classes is then corrupted, and nothing reports the corruption. **Blocking for correctness, not for building**: `contracts` can land ahead of the answer, because band edges are typed as `number` rather than `integer` precisely so the answer does not reshape the schema. **Owner: the weights scraper project**, by live verification against `trade2` search and `/data/stats`. OQ-12 is the second gate on the §7.3 release dependency. The first gate is FR-4's coverage measurement. **Amended by revision 10:** under contract `5.0.0` the unit now binds **two parties independently** rather than one shared decomposition — the producer's `ranges` and `core`'s own derived interval must agree on the same quantity — and a disagreement between the two now **fails loudly as an edge-alignment error rather than silently as a wrong population** (FR-21, FR-29).
19. **OQ-19 — Does any single Stat Line carry three or more `#`, and if so, is its derived edge exactly representable?** AD-17 compares a curator's declared band edge against a derived tier edge for exact equality with no tolerance, and under `5.0.0` `core` computes that derived edge by dividing the line's `ranges` by the number of `#` the stat text carries. A stat carrying **two** `#` divides by two — exact in binary, lattice on half-integers, exactly as `4.x`'s cell edges were. A stat carrying **three or more** `#` divides by three or more, which is **not** exact in binary, and a reference against such a line would fail edge alignment **permanently**, with nothing a curator could write to satisfy it. Whether PoE2 publishes such a line is unknown: the producer's 2026-09-13 measurement counted rows by stat *count*, which is a different axis from `#`-count-per-stat. **Consequence of an unanswered yes:** every Combination on the affected Base Type becomes permanently untrackable at load, with no curation workaround. **Raised as a contract question, never as a `core` epsilon** — the same stance revision 6 took on the now-withdrawn sum rules, because tolerating an inexact edge would silently admit exactly the sentinel and heterogeneous-band defects the exact-equality rule exists to catch. **Owner: the weights scraper project**, by inspection of its own source data for a three-or-more-`#` line. OQ-19 is a **third gate** alongside OQ-12 on the §7.3 release dependency, both blocking for correctness and not for building.

### Open, and owned inside this repository

Two questions are live here, and neither blocks building. Each was raised by the reviewer gate on spine revision 10, and each asks for a measurement that nobody can take yet — one against a live endpoint, one against a conforming file.

20. **OQ-20 — What must `query.status` carry, and does it duplicate `trade_filters.sale_type`?** A captured live browser search sends `{"option": "securable"}` (`curl-creater-trade-search.txt`, in this PRD's own folder), and AD-16's search-construction rule has never specified `query.status` at all. *Verified live 2026-09-19:* `/api/trade2/data/filters` publishes `securable` under `status_filters` with the label **"Instant Buyout"** — so the value is documented by the very endpoint AD-25 commits as `catalogue/filters.json`, and its label matches what FR-21's instant-buyout rule intends. **Two things remain open.** First, what **omitting** the field does: a default could silently widen or narrow the population FR-29 weighs, which is the same class of defect as FR-21's `priced_with_info` trap — a wrong filter that raises no error and corrupts every estimate. Second, whether `status_filters.securable` and the `trade_filters.sale_type` value FR-21 already requires are **redundant, composing, or conflicting**. Only a live call distinguishes the three. **Consequence of getting it wrong:** every price in the Dataset rests on a population that is not the one FR-29 computes a probability for, with nothing on screen to reveal it. **Owner: `sync`'s builder**, by comparing result sets across the combinations. **Not blocking for `contracts`; blocking for a correct first price** (AD-16, AD-25).
21. **OQ-21 — How far can whole-tier containment understate, and does the gap need a check?** FR-29 records that containment understates unevenly and therefore **reorders** the ranked list, and that neither of its two mitigations is a bound. **Two shapes escape, and revision 12 adds the second.** The first is a **flush intrusion**: a scoped same-`statId` tier that intersects a tracked band without being contained *and* shares an edge with it, which edge alignment cannot see because it compares a band only against that band's own containment set. The second is a **floor intrusion**: a scoped same-`statId` tier whose interval covers the band's `valueMin` without being contained, sharing no edge. It is worse than the flush case, because FR-21's ascending sort prices the band **on the intruder** rather than merely failing to blunt the loss — the worked `T7 = [43.0, 56.5]` / `T8 = [56.0, 80.0]` pair of `IMPLEMENTATION-NOTES.md` §2.4 is exactly this shape, edge alignment accepts the `56.0 – 80.0` band that FR-22 tells a T8 curator to write, and below the Payout Threshold the T8 mass truncates out entirely. **Whether this second shape belongs inside this question or is a question of its own is for this question's owner to say**; it is recorded here rather than split off because it is the same measurement on the same pool, and because FR-29 previously ruled the non-flush case benign on a claim AD-11 makes only of the ceiling. **This question exists because revision 10's claim that the damage was bounded was false**, and §7.2's *measuring the understatement* item was written on that withdrawn premise. The question has two halves, asked of **each** shape: **how often it occurs in a real pool, and how far the error runs when it does.** The floor case additionally asks how far the *price* moves, which the flush case does not. The obvious remedy — reject any intersecting-but-uncontained tier — **must not be adopted without that analysis**, because it is the withdrawn straddle rule under another name and would again reject every crafted configuration on 53 of 63 item classes (FR-29). A narrower rule keyed on flush intrusion specifically may be satisfiable, and whether one exists is the open part. **Owner: this spine, with the player**, once the first conforming `5.0.0` file makes the frequency measurable. **Not blocking for building; blocking for trusting the ordering** (AD-11).

### Resolved by spine rev 2 — retained as the record of why the valuation model is shaped this way

These were defects in the **inherited** valuation model, surfaced by validation of this PRD, and raised against the spine rather than patched locally per `AGENT-WORKFLOW.md`'s definition of done. **Architecture Spine revision 2 absorbed all three.** The one-paragraph summaries below are kept only because they explain *why* a Modifier Reference must carry a ceiling and why the pool is item-level-scoped before it is summed — reasoning the amended decisions themselves no longer state; the full worked arguments are in git history.

1. **BQ-1 — A floor-spanning probability was multiplied by its lowest tier's price.** A Modifier Reference that summed T1+T2 weight into one probability, priced by an ascending-sort median, effectively priced only at T2 — understating or, below the Payout Threshold, zeroing out the T1 jackpot mass entirely. **Resolved** by AD-5: a Modifier Reference is a bounded band with a required `valueMax`, not an open floor, so tiers price separately. Reflected in FR-16, FR-21, FR-29.
2. **BQ-2 — The Eligible Pool had no item-level dimension**, so a probability normalised over a population the search did not actually return. **Resolved** by requiring `itemLevelMin` on every Weights File entry (so `core` can scope the pool to an entry's floor) and by requiring the crafted entries on one Base Type to share one Item Level Floor (so the partition is over one item-level population). Reflected in FR-16, FR-22, FR-27, FR-29.
3. **BQ-3 — Pool coverage was unmeasured, and it gates how much of v1 exists.** An incomplete pool makes its Base Type Unrankable rather than merely flagged, so the ranked list's size is a direct function of unmeasured Weights File coverage. **Resolved** by AD-27's coverage gate, measured before any view work and re-measured on every file regeneration, with bands at ≥80% / 50–80% / <50% that bind the view's layout. **FR-4 carries the current rule and is the copy to build to; this entry only records why the ordering, rather than a label, is what an incomplete pool costs.**
