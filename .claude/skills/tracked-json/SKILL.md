# tracked.json curation

You edit `data/tracked.json` in a loop: look up, edit, check. The two scripts print JSON to stdout. They only read.

- `pnpm tracked:lookup stat|base|class|mods|tiers ...` finds the ids and the tiers. Run it with no arguments to see the usage.
- `pnpm tracked:check` validates the file: the contracts schema, the pinned cap, catalogue resolvability and the six cross-file checks against `data/weights.json` (AD-17). It prints `{ok, checks, issues, unvalidated, unreachable}` and exits 0 when the file passes. Exit 0 does not mean every check ran, so read `checks` and `unvalidated`, not only the exit code. `cross-file` is `skipped`, and the exit is still 0, when `data/weights.json` is absent. `unvalidated` lists each crafted entry that no pool check covered, with its reason (`weights-absent` or `partial-pool`; `UnvalidatedMark` in `packages/core/src/cross-file.ts`). That list never fails the run, so an entry in it is unconfirmed: say so in the report. A class that is absent from the weights file, or that has a `partial` slot, gets no edge, containment or line-set check.
- `unreachable` lists each crafted entry that a recipe cannot reach, once per recipe and unreachable slot, with the `path`, `entryKey`, `recipeId` and `slot`. `tracked:check` exits non-zero while the list is not empty, and `pnpm test:data` fails on the same list (AD-17). `rank` keeps a backstop: one such entry makes the whole Item Class Unrankable under that recipe (`RECIPE_UNREACHABLE`).

## Rules for all steps

- Never open `data/catalogue/*.json` or `data/weights.json` directly. Get every fact from `pnpm tracked:lookup`. You can read `data/tracked.json` directly.
- `data/tracked.json` is a hand-edited input. Edit it directly and report the edit as the AGENT-WORKFLOW rule for hand-edited inputs requires (`AGENT-WORKFLOW.md`, *Parallel worktrees*, the `data/` writer rule). Do not edit any other file in `data/`.
- The entry shapes, the two kinds and the canonical key are AD-5, and `canonicalKey` in `packages/contracts/src/canonical-key.ts` builds the key. The contracts schema `TrackedFileSchema` is the reference for field names.
- The Accepted Tier rule, the band rule and the shared floor are FR-22 and AD-17. The floor derivation is *The floor rule* below, and `needs` in `packages/core/src/probability.ts` is its reference. How a tier's interval comes from its `ranges` is `interval` in the same file. Apply those rules as they are written there. Do not restate them in `data/tracked.json` or in your report.
- **The floor rule.** `itemLevelMin` is declared and no component derives it (AD-5). The tiers of a reference are the entries of the class's unscoped pool, in the entry's slot, that `isContaining` admits. `needs` is the highest `itemLevelMin` among those tiers for a banded reference, or a hybrid with a banded line. It is the lowest for a valueless reference, or a hybrid with only valueless lines. It is undefined, never `0`, when no tier is contained. An entry's candidate is the higher of its two `needs`, and the class floor is the highest candidate over its crafted entries. Read the band, never `acceptedTier`. A floor that is too low fails the cross-file checks at load. A floor that is too high passes every check and widens the pool, so you must state how you derived it.
- A crafted entry has exactly one prefix and exactly one suffix (AD-5). `tracked:check` refuses a crafted entry that lacks either slot.
- `tracked:lookup` derives no interval and no floor. `tiers` and `mods` print the weights data verbatim. You compute each band edge and the floor yourself, from the printed `ranges` and `itemLevelMin`, per `interval` and *The floor rule*. What the lookup adds comes from `core` and applies the null-line rule (`isUntrackable` in `packages/core/src/probability.ts`): a `mods` row is one family, a modGroup with one line set (`statIds`, sorted, `null` lines left out), with `trackable` and, for each untrackable tier, its `reason`. A `tiers` row adds its `lineSet` and its `untrackable` reason (`null` when the tier is trackable).
- A hybrid is one family whose `statIds` names more than one stat. Track it as one hybrid reference with one line per `statId` of the family (AD-5), never as one of its lines. A line of a tier with `statId: null` is an internal engine line: it is not in `statIds`, and it is not in the draft.
- Offer a family only when its `trackable` is `true`. For a family with `trackable: false`, name each tier in `untrackable` and its `reason`, and do not draft it. A row with no `statIds` has no stat to write.

## The loop

1. **Find the class.** `pnpm tracked:lookup class <query>` gives `{categoryId, categoryText, className}`. A crafted entry uses that `categoryId` and `className`. For a raw entry, find the base type with `pnpm tracked:lookup base <query>` and use its `type` as `baseTypeId`. Set `status` per AD-12 (FR-15): a new entry is `active` unless the player asks for `pinned`, which counts against the pinned cap that `tracked:check` enforces.
2. **Find the stat.** `pnpm tracked:lookup stat <query>` gives `{id, text, type}`. Use an `explicit.*` id for an affix. Output is capped at 50 matches. When `truncated` is not 0, use a narrower query. A crafted entry needs one affix in each slot, so do steps 2 to 6 for the prefix and again for the suffix. To track a hybrid, take its `statIds` from the `mods` row (`pnpm tracked:lookup mods --class <className> --slot <slot>`): all of them are in the reference.
3. **List the tiers.** `pnpm tracked:lookup tiers <statId> --class <className>` lists, per slot, each tier that carries the stat: `tierLabel`, `itemLevelMin`, `weight`, `modGroup`, the verbatim `lines`, `lineSet` and `untrackable`. For a hybrid, run it for any one of its `statIds` and keep the rows whose `lineSet` equals the family's `statIds`. A row whose `untrackable` is not `null` cannot be tracked: tell the player its reason. If the class name is in more than one category, add `--category <categoryId>`. If `tiers` is empty, first confirm the id with `pnpm tracked:lookup stat <statId>`: an unknown or mistyped id also prints `tiers: []`. `stat` matches substrings, so the id resolves only when one match has an `id` exactly equal to `<statId>`. When the id does not resolve, fix it and go back to step 2. Only when the id resolves and the stat has no tier in the slot you want, the pair is not possible on this class. Tell the player. Do not write the entry.
4. **Write the reference.** When every scoped line of the stat prints `ranges: []`, the reference is `valueless` (AD-5): write `kind: "valueless"` with no edges, and skip step 6. When the stat has a `ranges: []` tier beside banded lines, a valueless reference fails kind agreement: to track the valueless tier, write a `banded` reference with `valueMin: 1` and `valueMax: 1` (`kindAgreement` in `packages/core/src/cross-file.ts`). Otherwise choose the Accepted Tier per FR-22 and write a `banded` reference: `valueMin` and `valueMax` per FR-22 and `interval`. FR-22's default is tier 1; accept tier 2 instead only where tier 1 first appears at item level 81 or 82.
   **A hybrid takes one reference with every line.** Write `kind: "hybrid"` with one line for each `statId` of the family. Choose the Accepted Tier per FR-22 over the hybrid's own tiers (the rows whose `lineSet` equals its `statIds`), not over the tiers of one line's pure modifier. Derive each line's band from that line's `ranges` over the accepted hybrid tiers, per `interval`. Write a line as `{statId, valueMin, valueMax}`, or as `{statId}` when every accepted tier prints `ranges: []` for that line. The kind rule (`kindAgreement`) applies to each line, so a valueless line beside a banded tier of the same `statId` fails it. A line carries no `acceptedTier`: the label belongs to the whole hybrid (step 6). The reference names every `statId` of the family, because a subset fails line-set completeness (`lineSetCompleteness`).
4b. **Check for a same-`statId` collision.** `ModifierReference` carries no `modGroup` (AD-5): a reference names a stat line, not a game modifier. For each `statId` in your reference, re-run `pnpm tracked:lookup tiers <statId> --class <className>` and scan every tier of every `modGroup` and both slots listed for it.
   - **A hybrid tier shares the `statId` with a single-line pick.** If your band meets the derived interval (`interval`) of that hybrid tier's line, do not write the single-line reference: its search would also match the hybrid item (AD-17). Offer the hybrid family instead (it is a row of `mods` with more than one `statIds`), and let the player decide whether to track the hybrid or to drop the pick.
   - **Another family in the same slot shares the `statId`.** If any such tier's derived interval is not wholly outside your band (it overlaps), tell the player before writing the entry: the trade search cannot tell the two families apart, so listings from the other family's tier will surface too. Let the player decide whether to proceed, narrow to a different pick, or drop it.
   - **A recipe cannot reach the pick (do this before you write or draft the entry).** Every `tiers` row carries `recipes`: for each recipe, `reached` says whether that recipe can roll the tier. The recipe floor follows AD-17. Take the rows your band contains (`isContaining`, as in step 4). If, for some recipe, none of them has `reached: true`, that recipe cannot roll the pick, and `tracked:check` refuses the entry. Tell the player which recipe and which affix. Let the player decide whether to drop the pick or choose another. Do the same for each other crafted entry of the class that you add in the same batch. `recipes` is absent when `data/recipes.json` is unusable: say that this check did not run.
   - **The `statId` is also in the other slot of the entry.** It is then a summed pair (AD-16, AD-17): sync sends one filter whose edges are the sums of the two bands. Both lines must be banded. A valueless line, or a missing bound on either operand, is invalid. Tell the player that the sum is wider than the two tracked bands, and that the price describes that wider population.
5. **Write the floor.** Derive `itemLevelMin` by *The floor rule* and AD-17. For a hybrid reference, `needs` runs over the hybrid's containment set (`isContaining`), not over the tiers of one line. Read every other crafted entry on the same class in `data/tracked.json` first, including any you are adding in this same batch. The floor is one number: the max over **every** crafted entry on the class, old and new, not a per-entry figure. When the derived floor changes, write it on all of them and say so in the report. A raw entry takes no part in the floor rule: its `itemLevelMin` is the Raw Base item level of the PRD glossary (FR-3).
6. **Write the label.** Set `acceptedTier` to the tier label of the band per AD-5, for example `T1` or `T1-T2`. A hybrid has one label for the whole reference.
7. **Check.** Run `pnpm tracked:check`. On `ok: false`, fix each item in `issues` (`check`, `path`, `message`) and run it again until it exits 0. Then read `checks`: a `skipped` `cross-file`, or a class with no pool check, is not confirmed. Say so in the report. An entry in `unreachable` also fails the check: prune it (see *Changing or removing an entry*) or ask the player for another pick, and run the check again until the list is empty.
8. **Report.** Name the file, each change (which entries you added, changed or removed, with the band, the tier label and the floor), and the reason for each change. A pass does not confirm that a floor is the one the floor rule derives: a floor declared too high passes every check (AD-5), so state how you derived each floor.

## Changing or removing an entry

- To remove an entry, set its `status` to the `pruned` tombstone that the spine defines (AD-12), with its reason. Do not delete the entry.
- After you add, change or remove a crafted entry, re-derive the floor for every other crafted entry on that class (loop step 5). A change or a removal can move the class's shared floor (AD-17).
- Then do steps 7 to 8 of the loop.

## Interactive mode

Use this mode when the player asks which mods are possible ("show me which mods are possible", "what can I craft on ...") and wants to choose. Offer each choice as a short numbered list of plain text, never the question-asking tool: mod counts routinely exceed that tool's 4-option limit. Wait for the player's answer after each step. Do not choose for the player.

1. **Offer the classes.** Run `pnpm tracked:lookup class <query>`. Use the player's words as the query, or `""` to list every class. Read `data/tracked.json` and mark each class that already has a crafted entry. The player picks a class.
2. **Offer the prefixes.** Run `pnpm tracked:lookup mods --class <className> --slot prefix`. Show each row's `modGroup` (the row's `text` repeats it), `tierCount` and `tierLabels`, and name each stat of `statIds` with `pnpm tracked:lookup stat <statId>`. A hybrid is one row with more than one `statIds` entry. Show it as one choice, with all its stats named. Rows that share a `modGroup` are separate mod families; show each one. Offer only the rows with `trackable: true` and a non-empty `statIds`. A row with `trackable: false` has an untrackable tier (the null-line rule): do not offer it, and when the player asks about it, give each `untrackable` tier and its `reason`. The player picks one or more prefixes. If the slot offers no row, tell the player that the class cannot hold a crafted entry, and stop.
3. **Offer the suffixes.** Run `pnpm tracked:lookup mods --class <className> --slot suffix` and show it the same way. The player picks one or more suffixes. If the slot offers no row, tell the player that the class cannot hold a crafted entry, and stop.
4. **Pair the picks.** A crafted entry holds exactly one prefix and one suffix (AD-5), so every drafted entry is a prefix × suffix pair. When the player picked one prefix and one suffix, the draft is one pair entry. When the player picked more than one in a slot, ask whether to write every prefix × suffix pair or only the pairs the player names, and state the entry count, for example "2 prefixes × 3 suffixes: 6 pair entries". Do not choose a default. When a slot has no pick, ask once for a pick in that slot. If the player declines, write nothing and say so. Never draft an entry with one affix.
5. **Suggest the bands.** For each pick, run `pnpm tracked:lookup tiers <statId> --class <className>`. A hybrid pick is one reference with a band (or the valueless form) for every one of its `statIds`: suggest every line, with the FR-22 Accepted Tier of the hybrid's own tiers as the default. Do not ask the player to choose one line of a hybrid. Suggest the reference and the floor per steps 4 to 5 (including 4b's collision check and its summed pair rule) of the loop. When a prefix pick and a suffix pick share a `statId`, say that the pair is a summed pair.
6. **Show the draft.** Show each entry exactly as it will be written in `data/tracked.json`. Name every pick that a recipe cannot reach (loop step 4b, the recipe-reach rule) next to its entry, with the recipe, and say that `tracked:check` refuses it. Show the shared floor as one number derived across every drafted entry plus every existing entry on the class (loop step 5), and any existing entry whose floor changes. Wait for the player to confirm. If the player changes something, show the new draft and wait again. **Do not edit `data/tracked.json` before the player confirms.**
7. **Edit, check and report.** Write the confirmed entries. Then do steps 7 to 8 of the loop.
